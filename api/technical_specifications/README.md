# MVP технических заданий

Рабочее пространство для ТЗ из девяти разделов. Согласования нет: чат готовит
предложение, одно действие применяет проверенный результат. Комментарий не
изменяет документ. Редакция документа отличается от версии его проекции и от
версии страницы Eva.

Полная постановка: [требования, процессы, DoR/DoD, интерфейсы и алгоритмы](REQUIREMENTS.md).
Критерии TZ-01–TZ-40 и точные проверки находятся в
[матрице приёмки](../../test/fixtures/technical_specifications/requirements_traceability.md).
Матрица связывает требования с тестами; результаты выполнения фиксируются отдельно.

Редактор и предпросмотр сохраняют переносы Markdown/HTML и исходные позиции цитат,
включая CRLF. Mermaid/PlantUML отображаются как очищенный SVG; код доступен под
диаграммой и остаётся источником для LLM и Markdown-выгрузки. При ошибке рендеринга
показывается код. Служебные обёртки, изображения SVG и кнопки в документ не записываются.
Модель получает точный сохранённый Markdown/HTML без предварительного переписывания.
Точечная Markdown-правка внутри одного HTML-текстового узла приводится к inline HTML;
атрибуты, код, незатронутый текст и проверки точных цитат сохраняются.

## Архитектура

React → HTTP → `Specifications` → хранилище и модель через переданные зависимости.
Домен содержит только значения и правила формата. Вызовы Peewee, настройки модели
и HTTP живут в адаптерах. `runtime.py` собирает зависимости. API и дальнейшие
фоновые потребители должны вызывать ту же прикладную реализацию.

Модуль — локальное расширение. В upstream необходимы только регистрация моделей,
маршрут SPA и пункт навигации. Таблицы автоматически создаются существующим
инициализатором. Существующий процесс БТ не изменяется.

Раздел «Технические задания» имеет отдельный ключ `technical_specifications`
в видимости навигации и группах доступа. Он защищает меню, прямой маршрут SPA
и API ТЗ независимо от `business_documents`. Настройки навигации до версии 6
сохраняют прежнюю видимость ТЗ при включённых бизнес-документах; группы получают
право на ТЗ явно. Доступ к общим проектам разрешён из раздела ТЗ, а поиск и
операции с источниками по-прежнему требуют раздел `search`.

Права на документы наследуются от существующего рабочего пространства источников. Владелец
и редактор изменяют ТЗ; участники с правом чтения просматривают его и хранят свои
личные черновики. Все серверные операции повторяют проверку доступа; знание ID
документа не даёт доступ к другому проекту или организации.
Активный системный администратор (`is_superuser`) видит все проекты и может
читать их ТЗ, историю и выгружать Markdown без участия в проекте или организации.
В таком проекте он получает роль читателя; существующая роль владельца/редактора
сохраняется при действующем доступе к организации. Изменение документов и
управление проектом по-прежнему требуют соответствующей роли проекта.
Личные черновики других пользователей администратору не раскрываются.

## Данные

- `TechnicalSpecification`: проект, заголовок, версия проекции, номер редакции,
  девять разделов, история сообщений, комментарии, предложения и связь Eva.
- `TechnicalSpecificationRevision`: неизменяемый снимок разделов, номер,
  автор, причина и время. Восстановление создаёт новую редакцию.
- `TechnicalSpecificationDraft`: отдельный черновик пользователя в документе,
  собственная версия, текст, область, исходная редакция, цитата и окружение.
- Уникальный ключ происхождения ограничивает активную привязку страницы
  пределами организации. Для личного проекта без организации областью является
  его владелец. Независимая копия сохраняет происхождение и не получает активную
  связь. Если связанное ТЗ находится в другом доступном проекте, открывается оно;
  если доступа нет, идентификатор и содержимое не раскрываются.

Содержимое ограничено 100 000 символов. Проекция с историей — 2 МБ. Предложения
чата хранят только изменённые разделы относительно неизменяемой исходной редакции;
API восстанавливает полный результат одним пакетным чтением этих редакций.
Сохранённые полные предложения читаются и при следующей записи переводятся в это
представление без изменения текста. История и контекст не обрезаются молча.
Каждый принятый запрос резервирует 800 КБ под полный допустимый ответ и правку
с учётом JSON-экранирования. При нехватке места запрос отклоняется до запуска модели.
Параллельные записи учитывают резерв; уменьшение уже переполненной старой проекции
разрешено. Долгое обсуждение может потребовать отдельного хранения сообщений.

## Алгоритмы

Сохранение выполняется в транзакции: проверка прав → сравнение версии → запись
проекции через CAS → добавление редакции при изменении текста. Модель и Eva
не вызываются внутри транзакции. Параллельное изменение отклоняет запись.

Чат получает полный текст ТЗ, историю и точный контекст сообщения. Предыдущие
предложения передаются модели как изменённые разделы и замечания без повторных
копий незатронутого текста. Ответ модели должен быть завершённым JSON с точечными
заменами однозначных цитат сохранённого снимка. Тот же доменный алгоритм применяет
замены чата и объединения: он запрещает отсутствующие/неоднозначные цитаты и
пересечения, сохраняет весь текст вне замен. Прикладной сценарий получает прежний
формат полных изменённых разделов; формат сохранённых предложений и HTTP не меняется.
Правки за пределами выбранной области отклоняются, включая замену другого
вхождения выделенной цитаты.
При явном исправлении неприменённого предложения модель может выбрать его ID
как исходник точечных замен. Сервер разрешает только предложения чата текущей
редакции в состоянии ready/needs_resolution и сохраняет все их прежние изменения.
Новое предложение по-прежнему хранится относительно сохранённой редакции.
Выход сохранённых правок прежнего предложения за выбранную область также требует
«Всё ТЗ»; ссылка не расширяет права и не позволяет брать за основу предложение Eva.
Для Ollama и OpenAI-совместимого транспорта запрашивается JSON-режим; это не
заменяет проверку завершённости, разбора и допустимой области изменения.
В ответе модели обязательным является список всех разделов, необходимых для
выполнения просьбы (`required_sections`). Для вопроса список пуст. Правка без
объявленного раздела отклоняется как некорректный ответ. Если объявленные разделы
выходят за выбранный контекст, доменное правило возвращает ответ о выборе
«Всё ТЗ» без предложения и без частичных правок. Контекст не расширяется
автоматически. Это проверка явно объявленной области; правильность смыслового
определения связанных разделов всё ещё зависит от модели и проверяется отдельно.
Сообщение с полным контекстом сохраняется до вызова модели. Состояния запроса:
`processing`, `completed`, `failed`; ID попытки защищает результат от устаревшего
исполнителя. Повтор выполняющегося запроса возвращает его состояние. После сбоя
можно повторить сохранённое сообщение; прерванный перезапуском запрос доступен для
повтора после истечения шестиминутной аренды. Это восстановление по действию
пользователя, без отдельной фоновой очереди. Комментарии не отменяют результат
генерации. Ответ к прежней редакции сохраняется, но его предложение неприменимо.
Ошибка записи результата переводит исходное сообщение в `failed`, если хранилище
доступно. Повтор сохраняет ID сообщения; завершённый ответ не дублируется. При
полной недоступности хранилища действует та же аренда восстановления после сбоя.

Предложение хранит исходную редакцию и ID породившего его сообщения. Применение
читает просьбу и контекст из сохранённого сообщения, а прежние просьбы — для
понимания ссылок. Позднейшие сообщения и параметры клиента не подменяют этот запрос.
Проверка оценивает его полноту и согласованность результата; явно запрошенная
замена формулировки не становится ошибкой лишь из-за отличия от исходника.
Сохранённые предложения без ID сообщения проверяются без приписывания им запроса;
повреждённая ссылка нового предложения блокирует применение до вызова модели.
Применение проверяет всё результирующее ТЗ
на противоречия, затем повторяет проверку версии при записи. Ошибка, отмена или
таймаут не сохраняют частичный ответ помощника. Качество смысловой проверки зависит от
модели и требует отдельной проверки на реальных примерах.
Проверка получает по каждому разделу отдельно обозначенные исходные версии и
итоговый текст. При объединении передаются полные B/L/R и выбор пользователя;
исправленные противоречия исходника не должны считаться ошибками результата.
Дополнительно передаются явные замены каждой стороны относительно B, включая
удаления. Модель сначала кратко сопоставляет факты по требованиям целиком:
упоминания одного лимита в настройке, сценарии и API относятся к одному факту.
Выбор стороны действует на конфликтующие новые значения; независимое изменение
другого требования сохраняется даже внутри того же раздела. Результат собирается
обычным трёхсторонним слиянием, а модель возвращает только точечные замены цитат
этого снимка. Сервер проверяет однозначность и отсутствие пересечений всех замен
до их применения; текст за пределами цитат не генерируется заново. Потребители по-прежнему
получают полные девять разделов. Верификатор сравнивает нормализованные единицы
и возвращает только подтверждённые ошибки, без стилистических замечаний.
Чат в контексте «Всё ТЗ», объединение и проверка запрашивают поддерживаемый Ollama режим thinking;
служебный канал рассуждения исключается из структурированного JSON штатным
параметром транспорта. Недоступность метаданных не понижает режим молча.
Генерация и проверка выполняются по одному разу, без скрытых повторов ответа.
Замороженная синтетическая приёмка конкретной модели описана в
`test/evals/technical_specifications/README.md`; её успешный результат не заменяет
браузерную приёмку и проверку внешней публикации.

Цитата привязывается по полному совпадению с окружением. Сдвиг фрагмента допустим;
удаление или неоднозначное совпадение блокируют отправку. Переход на весь раздел
выполняется только явным действием. Локальная копия полного черновика сохраняется
сразу, серверная — с задержкой; конфликт черновиков не заменяет локальный текст.
При конфликте интерфейс показывает серверный вариант и ждёт явного выбора.
Второй вариант сохраняется на устройстве целиком и доступен для восстановления.
Ошибка синхронизации останавливает очередь до повторного чтения серверной версии.
Если не удалось сохранить и локальную копию, интерфейс сообщает об этом явно.

Ручные правки заголовка и разделов сохраняются на устройстве вместе с исходной
редакцией. Обновление серверного снимка переносит независимые изменения разделов;
пересекающиеся изменения требуют явного выбора. При недоступном локальном
хранилище все переходы маршрутизатора, включая общую навигацию и «Назад»,
блокируются до сохранения ТЗ. Для чата достаточно подтверждения сохранения полного
текущего черновика на сервере либо локальной копии; подтверждение более старого текста
не освобождает новый черновик. Несохранённые комментарии также блокируют переход.
Восстановление локального хранилища позволяет сохранить копию при повторном переходе.
Выход через браузер вызывает стандартную защиту от потери изменений.

Черновики комментариев разделены по области и ветке ответа. Отправка очищает
только отправленный вариант, сохраняя текст, набранный во время запроса.
Повтор комментария или ответа с тем же ID не создаёт дубликата; смена текста,
контекста или ветки с уже использованным ID отклоняется.

Общее текстовое объединение находится в `api/document_exchange/merge.py` и не
знает о ТЗ, БТ или согласовании. Оно сравнивает B/L/R, переносит непересекающиеся
правки строк и сохраняет все варианты пересекающихся правок. Неоднозначное
удаление среди повторяющихся строк считается конфликтом. Полностью повторяющийся
текст проверяется до дорогостоящего сопоставления. Позиции блоков не
используются как их идентичность. Смысловая проверка связанных разделов относится
к продукту ТЗ, а не к транспорту Eva.

## HTTP

Префикс: `/api/v1/source-workspaces/{workspace}/technical-specifications`.

| Операция | Метод и путь |
| --- | --- |
| Список и создание | `GET/POST /` |
| Просмотр и сохранение | `GET/PUT /{id}` |
| Личный черновик | `GET/PUT /{id}/draft` |
| История и снимок | `GET /{id}/revisions[/{number}]` |
| Чат | `POST /{id}/chat` |
| Комментарии, ответы, решение | `POST /{id}/comments` |
| Применение | `POST /{id}/apply` |
| Восстановление | `POST /{id}/restore` |
| Выгрузка сохранённой редакции в Markdown | `POST /{id}/export` |
| Импорт или независимая копия Eva | `POST /import-eva` |
| Состояние личного импорта | `GET /import-eva/{operation_id}` |
| Отмена импорта или получение уже созданного ТЗ | `POST /import-eva/cancel` |
| Поиск страницы Eva по названию или ссылке | `GET /eva-pages?query=...` |
| Привязка существующей страницы Eva без замены текста | `POST /{id}/connect-eva` |
| Обновление связанной страницы Eva | `POST /{id}/publish-eva` |
| Получение изменений Eva | `POST /{id}/pull` |
| Выбор значений в объединении | `POST /{id}/resolve-eva` |

Изменения принимают текущую `version`. Черновик принимает собственную версию
и целиком объект `draft`: `message_id`, `text`, `context`. ID сохраняется до успешной
отправки и меняется вместе с текстом или контекстом. Повтор отправки возвращает
сохранённый ответ; прежний ID с другим содержимым отклоняется. Новый черновик
имеет ожидаемую версию 0. Ошибки содержат
машинный `error_code`; 409 обозначает конфликт версии, контекста или предложения.

Выгрузка принимает `revision`, повторно проверяет доступ на чтение и отдаёт
имя файла, MIME-тип и Markdown выбранной сохранённой редакции. Имя файла содержит
название и номер редакции; внутри файла ровно девять разделов без преамбулы.
Чат, комментарии, предложения и личные черновики
в файл не попадают. Кнопка «Выгрузить .md» недоступна при несохранённых ручных
правках и конфликте редактора. При устаревшей редакции сервер возвращает 409;
файл не создаётся. Права редактора для выгрузки не требуются. Это самостоятельная
выгрузка в файл; обновление связанной страницы Eva выполняется отдельной кнопкой.

## Приёмка

Обязательны сценарии: девять разделов и преобразование Markdown; чат без
автоматического применения; одна новая редакция после применения; запрет
устаревших предложений; независимые и пересекающиеся правки; проверка связанных
ограничений; отсутствие перезаписи при гонке; восстановление черновика с цитатой;
изолированные черновики пользователей; комментарии без изменения текста;
история и восстановление как новая редакция; права и отзыв членства.

Поиск и чтение Eva используют `api/document_exchange/pages.py` с личным токеном.
Список выбора показывает ID, пространство, версию страницы и существующую связь
с ТЗ. Поисковая строка ограничена 500 символами, ссылка — 2000 символами,
выдача — 20 страницами. Занятость
проверяется одним пакетным запросом, права — по уникальным проектам результата.
Недоступный связанный документ не раскрывается. Изменение запроса сбрасывает
выбор и отменяет старый запрос; запоздавший ответ игнорируется. Перед импортом
сервер проверяет выбранные ID и версию. Существующее доступное ТЗ открывается
без перезаписи и повторного импорта его текста. Импорт
проверяет идентичность страницы и уникальность связи; повтор открывает документ.
Клиент сохраняет запрос импорта на устройстве до отправки: ID операции, выбранную
страницу, версию и режим копирования. После потери ответа или перезагрузки
«Продолжить импорт» использует тот же запрос. Подтверждённое создание открывает
существующее ТЗ; незавершённый запрос повторяется с прежним ID.
Если результат завершённого импорта удалён или стал недоступен, интерфейс
сообщает об этом без раскрытия документа, закрывает сохранённый запрос и
возвращает форму выбора страницы. Повторное создание автоматически не запускается.
Новый импорт доступен после завершения или подтверждённой отмены предыдущего. Ошибка или
некорректный ответ не удаляют сохранённый запрос. При недоступном локальном
хранилище новый импорт не отправляется. Запоздавший ответ не меняет маршрут
после ухода с экрана и не отменяет более новое решение пользователя.
Отмена доступна во время импорта. Если создание уже завершено, она открывает
созданное ТЗ; иначе запрещает запоздавшую запись. Протокол журнала и транзакций
описан в `api/document_exchange/README.md`. Для API без `operation_id` сервер
создаёт ID самостоятельно; восстановление повтором требует сохранённого клиентом ID.
Получение изменений сохраняет предложение, а не перезаписывает локальное ТЗ.
Выбор конфликтных значений подготавливает полный результат с сохранением
независимых правок; применение проверяет связанные ограничения, выбранную сторону
и повторно читает внешнюю версию до и после проверки моделью. После применения
базой становится R. Найденное противоречие переводит предложение в состояние
выбора и сохраняет конкретные замечания для интерфейса и следующего запроса чата.

История показывает различия выбранной и текущей редакций: название, добавленный
и удалённый текст. Полный снимок выбранной редакции доступен отдельно.
Запоздавший ответ не подменяет выбор; восстановление использует показанную
редакцию и текущую версию ТЗ и создаёт новую редакцию.

Выгрузка в Eva обновляет ту же связанную страницу штатным API, как в БТ.
Для локального ТЗ можно сначала указать существующую страницу и выполнить
«Связать страницу»: текст ТЗ при этом сохраняется, занятость страницы другим
документом проверяется общей привязкой. Затем «Обновить в Eva» выгружает текущую
сохранённую редакцию без согласования. Несохранённый текст сначала нужно сохранить.

Применяются личный токен, проверка версии и чужого черновика, запись черновика,
публикация и проверка результата. После выгрузки показан номер отправленной
редакции; более поздние локальные правки остаются в редакторе. Ошибка или потеря
ответа предлагает проверить Eva; ручной повтор сначала читает текущий результат.
Сервер Eva не изменяется. Граница обычного API описана в
`api/document_exchange/README.md`. Сквозная браузерная приёмка обмена остаётся
обязательной перед объявлением MVP готовым.

## Регрессионные проверки

Сценарий проверки: автор редактирует ТЗ, обсуждает его в чате и комментариях,
восстанавливает контекст после перезагрузки и обменивается с той же страницей Eva.
Наблюдаемый результат — девять разделов, одна редакция на применение и отсутствие
потери независимых правок или личного ввода. Ошибки модели, сети, версии и прав
не должны выдавать успех или выполнять частичную запись. Потребители общего
обмена — ТЗ и БТ; их проверки выполняются вместе при изменении этого модуля.

## Проверка соответствия БТ

Редактор ТЗ предоставляет отдельную панель «Соответствие БТ». Автор выбирает
согласованные основания через поиск и страницы каталога. Проверка запускается
для сохранённой редакции с версией документа и стабильным request_id. Повтор
запроса не запускает модель повторно. Читатель может просматривать доступную
историю; запуск требует права редактирования рабочего пространства.

API: `GET .../business-sources?query=&page=1`, `GET|POST .../<id>/alignment`.
POST принимает `version`, `request_id`, `business_document_ids` (1—16 уникальных
ID). Основания фиксируют согласованную редакцию и событие согласования.
Актуальность и доступ повторно проверяются перед публикацией результата и
при чтении. Обычная проекция ТЗ не содержит внутренних оснований и отчётов.

Смысловая оценка и доказательства исполнения показаны отдельно. Для проверенного
native Ollama 0.32.14 адаптер сопоставляет полный эффективный вход в двух окнах,
точный серверный счётчик из типизированного отказа, digest и восстановленный
контекст. Любой неподтверждённый шаг оставляет INCOMPLETE; один положительный
смысловой ответ не подтверждает соответствие. Thinking не попадает в audit.
Явные полные маркеры отсутствия требований получают NO_REQUIREMENT только под
каноническими заголовками шаблона либо отдельным полным абзацем. Все фрагменты
остаются в отчёте; нормативный или смешанный текст требует обычной проверки.
Полный [проект проверок](../../test/evals/technical_specifications/alignment/README.md)
фиксирует эту границу и правила ночной/релизной квалификации.
