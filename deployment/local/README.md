# Локальный деплой без служебных веток

## Обновление HTTP без плановой недоступности

Сценарий: пользователь продолжает работать и получать SSE-ответ во время
обновления приложения. Приёмка: внешний listener остаётся тем же, новые запросы
идут в готовую версию, принятый старой версией поток завершается. Неготовый образ
и ошибка проверки после switch сохраняют/возвращают прежний маршрут.
Права и tenant-проверки остаются в приложении. Потребители: браузер, API/SDK,
встроенные ASR/переводчик и фоновые задания.

`deploy.ps1` по умолчанию использует `-Strategy BlueGreen` с неизменяемым
Feature/Candidate/Release image. `Auto` выбирает Candidate. Fast и dev bind mounts
запрещены: общий checkout менял бы обе версии. Первый перенос порта `9380`
с единственного контейнера на постоянный nginx требует окна обслуживания.
Без явного `-InitializeBlueGreen` скрипт останавливается до backup/переключения.
После обычных проверок образа и согласования окна:

```powershell
.\deployment\local\deploy.ps1 -Mode Feature `
  -FeatureImageReference '<immutable-image-id-or-digest>' `
  -FeatureSourceId '<source-id>' -InitializeBlueGreen -CheckOnly
.\deployment\local\deploy.ps1 -Mode Feature `
  -FeatureImageReference '<immutable-image-id-or-digest>' `
  -FeatureSourceId '<source-id>' -InitializeBlueGreen
```

Первый кандидат сначала сверяет схемные исходники с работающим контейнером;
при отличии нужна отдельная миграция до переноса порта. Он прогревается до
остановки прежнего контейнера. После переноса
прежний контейнер сохраняется с `restart=no`. Повторные поставки выполняются
без `-InitializeBlueGreen`. Нужен образ с web-only startup из этой версии.

Контроллер создаёт `web-blue`, `web-green`, непубликуемый `worker` и постоянный
`gateway` в существующем Compose project, сохраняя инфраструктуру. В web отключены
task executor, datasync, каналы, Business Documents/linked-document workers и
quality scheduler. Они работают только в worker. Его обновление после switch
может кратко приостанавливать обработку и вызывать повтор заданий по существующим
механизмам восстановления; непрерывность активного вычисления не гарантируется.

После Docker healthcheck проверяются `nginx -t`, graceful reload и публичный
JSON health с уникальным header нового маршрута. Прокси не буферизует SSE и не
повторяет запросы. Старый web остаётся запущенным. Перед повторным использованием
слота контроллер ждёт завершения прежних nginx workers; при таймауте он отказывает
в поставке, не обрывая их. Vite assets накапливаются в отдельном volume для lazy
imports открытых вкладок: `/assets/`, `/entry/` и `/chunk/` обслуживаются с gzip
и годовым кешированием, отсутствующие файлы возвращают 404 вместо HTML SPA.
Перед switch сохраняются также файлы текущей версии, включая первый переход
с volume без JS. Прежняя структура хранения `/assets/` сохраняется;
совпадение имени с другими байтами блокирует деплой.
Файл публикуется атомарно после копирования во временный файл того же каталога.
Ошибка записи или прерывание процесса не оставляют неполный JS под итоговым
именем и не блокируют повторную поставку. После принудительного завершения
может остаться временный файл; повторная попытка его не использует.
Совместимость старого JS с новым API проверяется отдельно для конкретного релиза.

Параметры окружения, конфигурационный mount и подключения к общим хранилищам
должны сохраняться между версиями; смена этих настроек требует обслуживания.
Хеш файлов моделей/миграций и initialization inputs из фактического образа
должен совпадать с активной поставкой. Отличия блокируются: init/migrations
здесь не запускаются. Изменения схемы и инфраструктуры требуют отдельной
проверенной процедуры обслуживания. В legacy-проекте для неё доступен
`-Strategy Recreate`. В мигрировавшем проекте Recreate запрещён: порт принадлежит
gateway. Не запускайте обычный Compose up для старого `ragflow-cpu` поверх него.

Конфигурации и журнал намерения находятся в
`.local/runtime/<project>/blue-green`. Не удаляйте `pending.json` вручную.
После прерывания восстановите прежний маршрут и worker под блокировкой:

```powershell
.venv\Scripts\python.exe -B deployment/blue_green.py --recover `
  --project ragflow-local --runtime .local/runtime/ragflow-local/blue-green
```

При первом переносе recovery возвращает исходный контейнер. Ошибка recovery
сохраняет журнал и блокирует новую поставку. Откат маршрута не восстанавливает
БД из backup. Ротация самого gateway и очистка накопленных assets требуют
отдельного обслуживания с учётом открытых вкладок.

CI `build_image` запускает `test-blue-green.py` на базе candidate image:
отдельный Docker project/loopback port, два HTTP stand-in образа, настоящий nginx.
Проверяются запросы во время switch, SSE, старые assets, отказ readiness,
прерывание копирования JS и повторная поставка, rollback после switch и recovery.
Stand-in не доказывает работу бизнес-обработчиков,
БД и LLM. Отчёт с SHA образа и controller входит в qualification packet;
collector/publisher отвергают отсутствующее, чужое или частичное доказательство.
Previous-image upgrade отдельно читает обновлённую схему прежним образом.
Существующие API/browser/live lanes сохраняются. Linux installer/remote upgrade
этим локальным Windows entrypoint не переключаются.

## Временные файлы задач

Все разовые снимки, сборки и проверки размещаются в `S:\tmp\ragflow`, без новых
каталогов в корне диска. Перед задачей зарезервируйте каталог:

```powershell
.\deployment\local\temp.ps1 -Name load-new-run
```

Команда возвращает путь и ставит `.keep` для активной задачи. Резервирование,
окончательная проверка защиты и удаление используют одну блокировку каталога:
во время удаления резервирование завершается ошибкой, не объявляя задачу активной.
Перед завершением
сохраните уникальные результаты в `.local/archives`, резервные копии — в
`.local/backups`, затем выполните `temp.ps1 -Name load-new-run -Complete`.
Рабочий каталог удаляется сразу. Не оставляйте завершённые сборки под `.keep`.
`-Name <задача> -Complete` завершает только эту задачу и её записи восстановления;
чужие каталоги, recovery-записи и общий кэш не очищаются. Для общей уборки и
`-CleanCache` используйте отдельный запуск без `-Name`.
`.keep` защищает задачу до явного завершения независимо от возраста, в том числе
во время ожидания решения пользователя. Непомеченные каталоги также сохраняются.
Сборки создают `.ragflow-temp` версии 2, `.process-job` и держат открытым `.lease`.
Сборочные команды запускаются через `start_process`: дочерний процесс назначается
в Windows Job Object атомарно при создании через `CreateProcess`. Он учитывает всё
дерево процессов: после сбоя родителя живые
дочерние процессы сохраняют защиту workspace и общего кэша pnpm. Дочерние процессы
не завершаются при закрытии Job Object. Один наблюдатель на процесс сборки держит
дескриптор группы до выхода родителя и всех потомков, затем завершается сам.
Старые маркеры без этой защиты не удаляются
автоматически. Аварийные остатки удаляются после 2 дней
без изменений либо при превышении общей квоты 10 ГиБ, начиная с самых старых.
Пути процессов и Docker-монтирования дополнительно защищены; при ошибке их
проверки удаления нет. Для просмотра — `temp.ps1 -WhatIf`.
Git-репозитории, любые вложенные `.keep`, резервные копии и неизвестные ссылки вне
`node_modules` блокируют удаление; обычные исходные `.sql` таким запретом не являются.
Pytest-ссылки `<имя>current` на соседний каталог `<имя><номер>` внутри задачи
удаляются только как ссылки, включая висячие после удаления цели. Внешние цели,
цепочки ссылок, junction вместо pytest-ссылки и несовпадающие имена защищены.
Ссылки зависимостей pnpm внутри `node_modules` удаляются только как ссылки:
обхода и изменения их внешних целей нет. Окончательная проверка выполняется в том
же helper, что и удаление; каждый удаляемый элемент повторно проверяется, чтобы
сохранить защищённые файлы, появившиеся после предварительного обхода.
Перед удалением рядом с workspace создаётся `.ragflow-cleanup-<id>.json` с
идентификатором каталога и процесса сборки. Запись сохраняется при частичном
удалении; следующая уборка повторяет проверки защиты и завершает удаление даже
без внутренних маркеров. Новый каталог с прежним именем такой записью не
разрешается удалять. Ошибка удаления даёт неуспешный результат автоочистки.
Повтор той же команды `-Complete` после ошибки завершается успешно, если recovery
уже завершил удаление этой задачи. Новый каталог с прежним именем сохраняется:
такой повтор требует отдельного решения для нового поколения каталога.

Постоянные данные находятся внутри checkout: `.local/runtime/ragflow-local`
(конфигурация, логи, свидетельства поставок), `.local/runtime/quality-watchdog`
и `.local/quality` (закрытый корпус проверок). `.local` исключён из Git и
Docker-контекста. Рабочие снимки и зависимости в этих каталогах не хранятся.

`tools.quality.frontend_artifact build` удаляет свой workspace при успехе и ошибке.
Сохраняются проверяемый архив SPA, receipt и соседний `<archive>.logs.zip`.
Единый пакетный кэш `.local/cache/pnpm` используется под файловой блокировкой,
очищается после 7 дней простоя и ограничен 5 ГиБ. Для диагностики используйте
архив логов, а не сохранённое дерево `node_modules`.
Ссылки регистрации проектов pnpm `v<версия>/projects/<32-значный хеш>`
учитываются без обхода их целей: содержимое рабочих каталогов не входит в квоту
и не удаляется при очистке кэша. Неожиданные ссылки блокируют очистку.

Установить еженедельную автоочистку для текущего пользователя:

```powershell
.\deployment\local\install-temp-cleanup.ps1
```

Задача Windows `RAGFlow Temporary Cleanup` работает в текущем пользовательском
сеансе без сохранённого пароля и повышенных прав; пропущенный запуск выполняется
при доступности сеанса. Параллельные запуски запрещены. `sweep-temp.ps1` очищает
только управляемые временные сборки и пакетный кэш под его блокировкой; не обновляет
время использования кэша. Отчёт перезаписывается атомарно в
`.local/maintenance/temp-cleanup/last-run.json`, история логов не накапливается.
Постоянный checkout нужен для работы задачи. Резервные копии, закрытые корпуса и
результаты в `.local/archives`, `.local/backups`, `.local/runtime`, `.local/quality`
не входят в область удаления.

## Быстрый образ из текущего checkout

Повторная подготовка Feature автоматически переиспользует готовый образ, когда
совпадают байты снимка, версия, build profile, immutable базы, native-библиотеки,
toolchain и флаги. Git commit/dirty сами по себе не требуют пересборки тех же
байтов. Результат содержит `cache_hit`, исходный `source_id` и точный `image_id`;
при переиспользовании передавайте в деплой именно возвращённую пару. Отсутствующий
образ, повреждённая/незавершённая запись или изменившиеся входы означают cache miss.
Go/C++ и Docker-слои при этом используют свои существующие независимые кэши.

Для Docker Desktop доступен тот же сборщик без SSH и registry push:

```powershell
.venv\Scripts\python.exe -B deployment\local\build-feature.py --local
```

Native-библиотеки берутся из `~/ragflow-native-libs` (`RAGFLOW_NATIVE_CACHE`),
артефакты/Go modules/build — из `~/.cache/ragflow-go-builder`
(`RAGFLOW_GO_CACHE_ROOT`). Результаты локального сборщика и проверок находятся в
`.local/cache/deploy`, удалённого — `~/.cache/ragflow-feature`. Базы фиксируются
по digest установленного образа; отсутствующие базы загружаются один раз.
Для обновления mutable base tag сначала явно выполните `docker pull <base>`;
новый digest автоматически изменит ключ. `--force` повторяет сборку образа и
его import probe, сохраняя обычное кэширование слоёв и native-артефактов.

Feature и `build-go-linux.sh` используют общий `deployment/runner/go_builder.py`.
На Linux контейнер работает с UID/GID вызывающего пользователя; HOME и пути
native-библиотек/кешей одинаковы для обоих запусков. На Docker Desktop используются
те же mounts без подстановки несуществующего Windows UID.

Детерминированные локальные проверки запускайте через кэш успешных результатов:

```powershell
.venv\Scripts\python.exe -B -m tools.quality.check_cache -- .venv/Scripts/python.exe -B -m pytest <нужные-тесты>
```

Ключ включает команду, executable, исходники/тесты, установленное Python-окружение,
платформу и хеш переменных окружения. По умолчанию берутся все Git source-файлы,
включая новые; `--input <путь>` можно повторять только при известной полной границе
зависимостей проверки, включая её тесты, конфигурацию и общие fixtures. Внешние
файловые входы также должны быть представлены в выбранной границе. При неизвестной
границе используйте default, а при внешнем состоянии запускайте проверку напрямую.
`--force` повторяет проверку. Ошибка, прерывание или изменение входов во время запуска
не сохраняют PASS. Запись не является CI-квалификацией и не заменяет release gates.

Если установленные Python distributions имеют неполные метаданные, команда
выполняется напрямую: результат содержит `cacheable: false` и
`incomplete_environment`, прежний PASS не используется и новый не кешируется.

`deploy.ps1` автоматически переиспользует успешный import probe неизменяемого
image ID на том же Docker engine; `-ForceChecks` повторяет его. Проверки source/image
identity, актуальной конфигурации, backup и текущего здоровья runtime выполняются
при каждой установке. Live/API/DB/browser-приёмка и миграции зависят от текущего
состояния и через кэш детерминированных проверок не запускаются.

Когда для проверки фичи нужен полный Linux-образ, а не bind-mount цикл, запустите
сборку из текущего checkout без commit и push:

```powershell
.venv\Scripts\python.exe deployment\local\build-feature.py
```

Новые файлы нужно перечислить по одному: `--include admin/server/new_module.py`.
Скрипт откажется собирать образ, если остались неучтённые untracked-файлы. Он
создаёт проверяемый снимок отслеживаемых файлов и явно выбранных новых файлов,
передаёт его по SSH на `192.168.1.175`, собирает Docker-образ, проверяет
метаданные и импорт приложения, затем публикует образ
`192.168.1.175:8443/docker-hosted/ragflow:dev-<source_id>` в Nexus. В выводе есть
полный digest для точного повторного pull. Образ имеет метку
`org.ragflow.validation=feature-build-only` и `SOURCE_REVISION=unverified`;
он не является релизным кандидатом. При ошибке сборка или публикация завершается
без успешного digest. Требуются SSH-ключ
`~/.ssh/ragflow_nuc8_ed25519`, подготовленные native/Go-кэши на Ubuntu и доступный
Nexus. Полная регрессия выполняется релизным workflow; вручную её можно запустить
через `workflow_dispatch`.

C++ и Go собираются одним вызовом `build-go-linux.sh --artifacts`. При неизменных
нативных исходниках, ресурсах, библиотеках и toolchain он восстанавливает бинарники
и статическую библиотеку из кэша с проверкой SHA-256. Изменение Python, интерфейса
или номера приложения не требует их перекомпиляции. Docker независимо кэширует
Python, браузеры и frontend; итоговый образ всегда собирается от `runtime-base`,
без слоёв предыдущей версии приложения. Состав runtime и релизные проверки
сохраняются. Подробности и процедура сравнения — в
[руководстве builder](../runner/README.md#incremental-application-builds).

Для локальной проверки опубликованного dev-образа используйте оба значения из
вывода сборки — `DIGEST` и `SOURCE_ID`:

```powershell
.\deployment\local\deploy.ps1 -Mode Feature `
  -FeatureImageReference '<DIGEST>' `
  -FeatureSourceId '<SOURCE_ID>' `
  -CheckOnly
.\deployment\local\deploy.ps1 -Mode Feature `
  -FeatureImageReference '<DIGEST>' `
  -FeatureSourceId '<SOURCE_ID>'
```

`Feature` принимает digest из Nexus или полный локальный image ID вида
`sha256:<64 hex>` из `docker image inspect --format '{{.Id}}' <образ>`.
Локальный образ должен быть уже собран и загружен в Docker Desktop; для него
pull и публикация в registry не выполняются. Метки и `SOURCE_ID` проверяются
так же, а image ID должен точно совпасть с результатом inspect.
Перед изменением локального Docker
Desktop он сверяет хеш снимка, метки dev-образа, архитектуру, `VERSION`,
`SOURCE_REVISION=unverified` и импорт приложения. Затем применяет тот же
проверяемый backup и health checks, что и Candidate, с переключением BlueGreen
по умолчанию либо legacy recreate при явном выборе этой стратегии. `-CheckOnly`
проверяет параметры и Compose без pull и без переключения контейнеров; полная
проверка образа происходит при выполнении деплоя. В `deployment.json` dev-образ
помечается полями `feature_*` и не получает статус релизного кандидата.
Для `Feature`, `Candidate` и `Release` скрипт копирует шаблон конфигурации по
SHA-256 и хранит его вместе с логами в `.local/runtime/<ProjectName>`
внутри текущего checkout (`.local/runtime/ragflow-local` по умолчанию).
Контейнер монтирует эти постоянные пути. Временную область сборки после деплоя
можно удалить; постоянный checkout и его `.local` должны сохраняться. Скрипт откажется
использовать ранее сохранённый шаблон, если его содержимое изменилось.
`Auto` не выбирает `Feature`: для каждого нового dev-образа передайте его digest
и `SOURCE_ID` явно.
В legacy-проекте при обслуживании инфраструктуры используйте `-Strategy Recreate`
и перечислите проверенные сервисы через `-Services`: Feature сохраняет список, который должен
включать `ragflow-cpu`. Для сервисов observability также передайте `-Observability`.
Перед пересозданием выбранных сервисов выполняется тот же проверяемый backup;
образы должны быть уже собраны или загружены, автоматический pull отключён.
Для контейнеров без Docker healthcheck отчёт записывает `health=none`; готовность
их HTTP/API нужно проверить отдельно.
На этой Windows-машине Docker уже авторизован в Nexus отдельным пользователем
с правами только на чтение `docker-hosted`; на другом компьютере потребуется
собственный `docker login 192.168.1.175:8443`.

Обычный локальный деплой выбирает неизменяемый CI-кандидат и BlueGreen:

```powershell
.\deployment\local\deploy.ps1
```

Скрипт отвечает за применение и проверку runtime; исполнитель завершает успешную
поставку коммитом и обязательным push по [единой политике публикации](../../AGENTS.md#deployment-and-publication).
Дополнительное разрешение на push после успешного деплоя не требуется.
Скрипт сам не выполняет commit/push и не создаёт и не переключает ветки, worktree или tag. Для Fast-режима
источником служит текущий checkout. Candidate/Release получает готовый образ из
`192.168.1.175:5443` по полному Git SHA и отключает development bind mounts.

По умолчанию цель — локальный Docker Desktop Compose project `ragflow-local`.
Только в legacy-стратегии `Recreate` изменённые пути определяют действие автоматически: frontend
собирается без пересоздания контейнера, смонтированный Python-код получает restart,
ASR пересобирается отдельно, а несмонтированный runtime-код требует CI-образ.

## Стандартный цикл

1. Определить поставляемый исходный код и выполнить узкие проверки его поведения.
   При чистом checkout сравнить выбранный commit/image с работающим runtime:
   отсутствие diff само по себе не означает, что деплой не нужен. Для уже
   закоммиченной поставки используется существующий SHA без пустого коммита.
2. Проверить конфигурацию без изменения runtime:

   ```powershell
   .\deployment\local\deploy.ps1 -CheckOnly
   ```

3. Выполнить локальный деплой:

   ```powershell
   .\deployment\local\deploy.ps1
   ```

4. В legacy-проекте принудительно проверить или применить быстрый режим
   с допустимым перерывом обслуживания:

   ```powershell
   .\deployment\local\deploy.ps1 -Mode Fast -Strategy Recreate
   ```

5. Для диагностики запустить `tests` с профилем `targeted`. Полный candidate
   квалифицируется через `release` с `dry_run=true`; он не публикуется автоматически.
   Проверенный image digest указан в schema 2 receipt.

6. Для локального Release скачать из **неизменяемого опубликованного** комплекта
   форка `meownm/ragflow` три файла в одну папку:
   `candidate-receipt.json`, `publication-receipt.json`, `release-manifest.json`.
   Скрипт проверит их digest через GitHub API доверенного repository, SHA и image;
   самодекларации receipt недостаточно. Нужны `gh` и Python.

   ```powershell
   $releaseTask = .\deployment\local\temp.ps1 -Name release-install
   gh release download <immutable-release-tag> --repo meownm/ragflow `
     --pattern candidate-receipt.json --pattern publication-receipt.json `
     --pattern release-manifest.json --dir $releaseTask
   .\deployment\local\deploy.ps1 -Mode Release -CandidateRevision <full-40-char-sha> `
     -CandidateReceipt (Join-Path $releaseTask 'candidate-receipt.json')
   ```

   После проверки результата и завершения публикации сохраните уникальные
   свидетельства в `.local/archives`, затем освободите задачу:
   `.\deployment\local\temp.ps1 -Name release-install -Complete`.
   При ошибке сначала сохраните нужную диагностику; незавершённую задачу
   не объявляйте завершённой автоматически.

   Runtime загружается по digest. Nightly разрешается через annotated `nightly`
   Git tag с JSON message, который указывает конкретный immutable release tag.
   `latest` относится только к stable. Новые выпуски требуют schema 2; исторический
   schema 1 допускается только для явного восстановления с `-AllowHistoricalReceipt`.

7. Для возврата получить три assets предыдущего квалифицированного комплекта,
   проверить совместимость его runtime с данными и указать его receipt/SHA.
   Возврат image не восстанавливает PostgreSQL автоматически. Если новая версия
   несовместимо изменила схему, сначала остановить записи и восстановить проверенный
   pre-upgrade backup по процедуре PostgreSQL; сохранить SHA256 и RPO. Новые записи
   после backup потеряются при таком восстановлении. До выпуска это проверяется
   `deployment/runner/test-qualified-upgrade.py` на disposable копии.

До пересоздания контейнеров скрипт проверяет итоговый Compose config и делает
проверяемый PostgreSQL dump. После переключения он ждёт container health и
`/api/v1/system/healthz`, записывает restart count, image identity и итоговый health.
Для Candidate/Release он сверяет image ID запущенного `ragflow-cpu` с только что
проверенным образом и записывает `candidate_revision`, `candidate_image_id` и
доступные registry digests в `deployment.json`.
`Release` до переключения контейнера сверяет SHA, успешность обязательных CI jobs,
registry digest загруженного образа и затем image ID контейнера. `Candidate`
разрешает исследовательский запуск без receipt и помечает доказательства как
неполные. После выпуска отдельный `tools/quality/release_evidence.py verify`
собирает `release-evidence.json` из receipt, применимых живых отчётов качества и
`deployment.json`; отсутствие отчёта, backup или здоровья не считается успехом.
Evidence сохраняется в `output/local-deploy/<timestamp>/`.

`-SkipBackup` не отключает защиту безусловно: он разрешён только при наличии свежего
backup с повторно проверенным SHA-256. Для Release и database-sensitive изменений
backup всегда обязателен.

Observability выключен по умолчанию. Для явного запуска Compose с Grafana, Loki,
Tempo, Prometheus и OpenTelemetry используйте `-Observability`; все эти сервисы
дополнительно защищены профилем `observability`.

Однократно установите CA локального TLS registry и перезапустите Docker Desktop:

```powershell
.\deployment\local\install-candidate-registry-ca.ps1
docker desktop restart
```

Для stable выпуска commit и версионный tag предшествуют CI квалификации:
`release.yml` проверяет этот source SHA и публикует проверенный комплект. Локальный
Release устанавливает уже опубликованный комплект и записывает отдельный результат
deployment. Незакоммиченные изменения проверяются как Feature с явно неполной
квалификацией и точным SOURCE_ID. Candidate использует committed source SHA;
ограниченная диагностика не является опубликованным выпуском. Отдельная integration-ветка или worktree нужны для обновления
upstream, конфликтующей интеграции или отдельно обоснованной изоляции кандидата.

Удалённая поставка использует отдельный документированный процесс
`deployment/linux-pg/`; она запускается только по явному запросу на remote deploy.
