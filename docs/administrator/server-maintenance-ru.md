# Обслуживание логов и Elasticsearch

Сценарий: администратор задаёт хранение логов за 60 дней и еженедельную
проверку возможности освобождения места Elasticsearch. В разделе
«Админка → Состояние сервисов → Обслуживание сервера» видны политика,
объём индексов, свободное место, следующий запуск и последний результат.
Обычный пользователь получает 403, без авторизации — 401. Отсутствующий
отчёт означает «не настроено», ошибка чтения — 503, отчёт старше двух часов
помечается устаревшим.

## Хранение логов

Python-процессы RAGFlow ротируют свои файлы ежедневно в полночь UTC вместо
ограничения пятью файлами по 10 МБ. Сохраняются 60 архивов. Каждый час
обслуживание сжимает завершённые дневные файлы gzip и удаляет архивы,
весь интервал которых старше 60 дней. Активные файлы и старые числовые
архивы не изменяются. Логи прежних контейнеров с другим именем процесса
также обслуживаются по дате в имени архива.

В Loki установлен `retention_period: 1440h`, удаление выполняет compactor.
Это максимальная глубина хранения; потерянные до настройки записи
восстановлены не будут. Для вступления изменений в силу нужны перезапуск
Python-процессов RAGFlow и Loki с новой конфигурацией.

Исходные stdout/stderr Docker используют отдельный драйвер и его ограничения.
Внешний logrotate для `/var/lib/docker/containers/*-json.log` не применяется:
этими файлами управляет Docker. Эта настройка не обещает хранение исходных
буферов Docker за 60 дней. Системные журналы хоста также имеют свою политику.

## Еженедельное обслуживание индексов

Расписание: воскресенье, 03:30 `Europe/Moscow`, systemd timer
`ragflow-maintenance-elastic.timer`, с догоняющим запуском после простоя.
Проверяются только индексы `ragflow_<tenant-id>` и
`ragflow_doc_meta_<tenant-id>` с 32-символьным шестнадцатеричным tenant ID.

Слияние с `only_expunge_deletes=true` допустимо, если индекс открыт,
имеет здоровье green, явно закрыт для записи (`index.blocks.write` или
`index.blocks.read_only`), доля помеченных удалёнными записей более 10%,
диск заполнен менее чем на 85% и свободно не менее трёх размеров индекса
и 1 ГиБ. Аварийная блокировка `read_only_allow_delete` сама по себе не
считается разрешением на обслуживание. Индексы не закрываются для записи
автоматически. Данные и индексы не удаляются. Максимальное число сегментов
не задаётся. Перед запуском проверяются уже выполняющиеся force merge.

Это соответствует [рекомендации Elasticsearch 8.11 о force merge](https://www.elastic.co/guide/en/elasticsearch/reference/8.11/indices-forcemerge.html).
Активные индексы освобождают место обычным автоматическим слиянием сегментов.
Нулевое число удалённых записей означает отсутствие работы, а не ошибку.

## Установка и проверка

После доставки проверенного инкремента и конфигурации:

```bash
bash deployment/linux-pg/install-maintenance.sh
sudo systemctl start ragflow-maintenance-elastic.service
systemctl list-timers 'ragflow-maintenance-*'
sudo journalctl -u ragflow-maintenance-elastic.service
```

Скрипт требует `sudo -n`, systemd, Docker и Python 3 стандартной библиотеки.
Пароль Elasticsearch берётся из окружения его контейнера, в отчёт не попадает.
Общий файловый lock исключает одновременное обновление отчёта и слияние.
Состояние атомарно сохраняется в
`docker/ragflow-logs/maintenance/status.json`; админский API только читает его
из существующего монтирования логов и не получает доступ к Docker socket.

При обновлении каталога установки сохраняйте каталог логов и установленные
systemd units. Программа обслуживания установлена отдельно в
`/usr/local/lib/ragflow-maintenance/maintenance.py` и не исчезает при замене
каталога приложения. При изменении пути установки повторите установку таймеров.

Проверки инкремента: сценарии допуска/отказа Elasticsearch, работа с архивами
на границе 60 суток, атомарный отчёт и ошибки, авторизация admin endpoint,
отображение ненастроенного, ошибочного и устаревшего состояния в UI,
совместимость сжатых архивов с Python-ротацией. На целевом сервере отдельно
проверяются timer, первый запуск, фактические конфигурации и здоровье сервисов.

## Хранение двух вариантов отката

Только после успешного обновления `upgrade.sh` запускает `ragflow-retention.service`.
Служба использует `/usr/local/lib/ragflow-maintenance/retention.py` и общий
с обновлением lock. Периодического запуска нет; установщик удаляет ранее
установленный `ragflow-retention.timer`.

Сохраняются текущая установка и два последних подтверждённых отката. Источником
служат существующие `UPGRADE.env`, `UPGRADE-COMPLETED.env`, `config/docker.env`
и их `SHA256SUMS` в резервных копиях. Отдельный реестр версий не создаётся.
Незавершённое восстановление, несовпадение версии или контрольных сумм,
отсутствующий образ/каталог отката и нездоровый сервис запрещают очистку.

Удаляются только более старые подтверждённые каталоги и связанные с ними образы
RAGFlow. Образы всех контейнеров, сохранённых откатов и неизвестных установок
защищены. Изменяемые теги старых образов не считаются доказательством их личности.
Неизвестные каталоги, ссылки, смонтированные и открытые процессами пути, а также
каталоги с возможными резервными архивами не удаляются автоматически.

После удаления старых образов освобождается связанный с их сборками устаревший
кэш: только неиспользуемые записи, не разделяемые с образами, из цепочек сборок
RAGFlow, созданные до соответствующего старого обновления. Массовый `system prune`
и удаление томов не используются. Состояние контейнеров, томов и контрольные
суммы резервных копий и сохранённых откатов сверяются после очистки.

Результат находится в `docker/ragflow-logs/maintenance/retention.json` и журнале
`journalctl -u ragflow-retention.service`. Ошибка очистки видна как ошибка этой
службы и не превращает уже завершённое обновление в ошибку восстановления.
Для просмотра плана без удаления:

```bash
sudo python3 /usr/local/lib/ragflow-maintenance/retention.py
```
