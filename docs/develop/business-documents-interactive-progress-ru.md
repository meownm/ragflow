# Интерактивный анализ и внесение правок в бизнес-документ

## Сценарии применения

Автор видит сохранённую ревизию и отдельное обсуждение с вопросами, предложениями и комментариями. Тело документа доступно только для чтения; изменение текста проходит через проверенный план и атомарное сохранение.

- Основная кнопка «Применить исправления» отправляет `APPLY_CHANGES` после актуального анализа замечаний. Worker готовит и проверяет общий план, затем атомарно сохраняет результат. Отдельной кнопки подтверждения результата нет.
- Опубликованные API-команды `PREPARE_CHANGES`, `CONFIRM_PREPARED_CHANGES` и `DISCARD_PREPARED_CHANGES` сохраняют контракты для внешних клиентов и ранее подготовленных вариантов. Если такой вариант уже есть, основная кнопка «Применить исправления» сохраняет его через `CONFIRM_PREPARED_CHANGES` без повторной генерации.
- Кнопка «Принять» отправляет `DECIDE_PROPOSAL` с `decision=ACCEPTED`. Команда атомарно сохраняет решение и событие; задача не создаётся, текст и ревизия не меняются. `ACCEPT_PROPOSAL` сохраняет такое же решение для существующих API-клиентов.
- `DECIDE_PROPOSAL` с `decision=REJECTED` сохраняет отказ. Повтор с тем же ключом идемпотентности возвращает прежний результат; новая команда не перезаписывает существующее решение.
- `CANCEL_PROPOSAL_ACCEPTANCE` возвращает неприменённое принятое предложение в ожидание решения, только если нет активной задачи и документ находится в `REVIEW`. Текущая строка решения удаляется, события принятия и отмены сохраняются. Повторное принятие создаёт новое событие-основание. Отмена делает подготовленный план и оценку ревью неактуальными.

Открытые вопросы не блокируют применение готовых оснований после актуальной оценки ревью. Они запрещают завершить согласование: оставшиеся вопросы и предложения сохраняются в том же цикле. Комментарии с `NEEDS_QUESTION` не применяются и не подтверждаются как учтённые без правки.

## Отображение результата

Проекция документа опрашивается раз в две секунды, пока операция активна. Интерфейс показывает фактическую стадию, время ожидания и попытку; процент отражает контрольные точки, а не долю готового текста. Целевые разделы замечаний ещё не означают, что эти разделы будут изменены.

При потоковой подготовке проверенные по форме фрагменты отображаются непосредственно в соответствующих разделах с пометкой «предварительно». Под разделом показано «Было → стало» только для изменённых блоков; основания и ссылки на источники доступны отдельно. Полный результат проходит смысловую проверку до автоматического сохранения результата. В истории и экспорте остаются сохранённые ревизии. Комментарий к изменяемому фрагменту можно привязать после применения; неизменённые разделы сохраняют обычное выделение.

Каждый блок AST имеет стабильный `id`. При чтении старой ревизии без ID сервер детерминированно дополняет проекцию, не переписывая сохранённую ревизию; новая ревизия сохраняет ID. Модель получает весь AST и контекст оснований, но возвращает только `INSERT_BLOCK`, `REPLACE_BLOCK`, `DELETE_BLOCK` либо `ADD_SECTION`. Замена сохраняет ID, вставка получает ID от сервера. Точка вставки относится к исходной ревизии (`after_block_id: null` — начало); несколько вставок после одного блока следуют порядку операций. Повторная правка одной цели, неизвестный ID и устаревший хеш отклоняются до записи. Сохранённые планы замены разделов читаются для совместимости с историей.

Ответы `CONFIRM_PREPARED_CHANGES`, `DECIDE_PROPOSAL` и `ACCEPT_PROPOSAL` содержат актуальную проекцию `document` с правами вызывающего пользователя. После применения интерфейс сразу показывает сохранённую ревизию. При завершении фоновой задачи событие `applied` обновляет документ и историю ревизий; опрос проекции служит резервным способом обновления. При принятии предложения интерфейс обновляет статус решения; текст остаётся прежним и задача не запускается. Если канонический AST уже совпадает с результатом плана, операция разрешает использованное основание без создания дублирующей ревизии; изменение ссылок evidence остаётся изменением AST.

У принятого предложения отдельно показаны ожидание, выполнение, повтор, ошибка или применение. Ошибка не меняет прежний текст и не удаляет принятие. Пользователь может отдельно повторить подготовку исправлений либо отменить неприменённое принятие после завершения задачи. Кнопки немедленного применения в карточке предложения нет. Состояние определяется по заданию именно этого события принятия, а не по посторонней последней операции.

## Сохранение и восстановление

Проверенный общий план хранится в результате `PLAN_CHANGES`. Предпросмотр действует 24 часа и только для своей базовой ревизии, версии состояния, цикла ревью и текущей политики промптов. Сохранение проверяет источники и актуальность под блокировкой документа. Для опубликованного API предпросмотра подтверждение дополнительно повторно проверяет доступ. Изменённый AST сохраняется одной новой ревизией; совпадающий AST фиксируется событием без новой ревизии.

Источники плана ограничены активными событиями неизменяемого снимка. Смысловая проверка получает полный набор подтверждённых оснований, разделы до/после и неизменённый контекст без усечения и пакетного разбиения. Сходство разделов служит кандидатом для проверки переноса, разрешённого копирования или ссылки, а не самостоятельным запретом. Корректный смысловой `FAIL` завершает задачу и не запускает автоматическое переписывание требований.

Известные временные ошибки могут повторить текущий этап. Кандидат плана сохраняется до смысловой проверки, поэтому повтор верификации не генерирует новый план. На каждый этап допускается одно исправление формата. Общий бюджет — шесть вызовов и 900 секунд вместе с ожиданием в очереди; оставшийся тайм-аут передаётся адаптеру и обёртке записи модельных вызовов.

SSE-события содержат монотонный номер, `job_id`, попытку и базовую ревизию. Повторная попытка, исправление формата или окончательная ошибка очищают временные фрагменты. После обновления страницы доступные события восстанавливают предварительный вид. Потеря lease останавливает последующие вызовы и сохранение. Частичные ответы не попадают в ревизии или экспорт.

## Проверка границ

| Граница | Ожидаемый результат |
| --- | --- |
| Авторизация | Читатель не изменяет документ; чужое редактирование без роли отклоняется. Команды, задания и подтверждение проверяют права на сервере. |
| Конкуренция | Устаревшие состояние, базовая ревизия, цикл, хеш или lease не допускают запись. Идемпотентный повтор команды не создаёт вторую задачу или ревизию. |
| Полнота | Пропущенное принятое предложение, неучтённое применимое основание и неизвестный источник отклоняются. Открытые вопросы и неоднозначные комментарии остаются в REVIEW. |
| Отмена принятия | Активная задача, уже применённое или отклонённое предложение не допускают отмену. Отозванное событие не может разрешить новый план; исходный аудит сохраняется. |
| Recovery | Временный сбой верификатора повторяет проверку того же кандидата; смысловой отказ завершается без повторной генерации. Исправление формата сохраняет исходный вход и диагностику. |
| UI | Предпросмотр отделён от сохранённой ревизии, история не показывает частичный ответ, итоговая ревизия обновляется после применения, источник правки доступен из обсуждения. |

По `test/REGRESSION.md` используются сценарные тесты команд и worker, проверки HTTP-контракта, golden-сценарии, тесты M06 и frontend-взаимодействий. Изолированный браузер проверяет построенную SPA с перехваченным API; он не заменяет живую приёмку модели, EVA или PostgreSQL-конкуренции. Сохранённый отчёт M06 проверяет последовательность вызовов, полный вход верификации и конечный PASS, включая разрешённые повтор и исправление формата. Живые тесты выполняются только в отдельном тестовом контуре.


## Требования к процессу и приёмочные сценарии

| Действие или ситуация | Ожидаемый результат |
| --- | --- |
| Принять одно или несколько предложений | Записать решения и автора в протокол. Сохранённый текст, номер ревизии и состояние операции не меняются. Никаких вызовов модели и задач изменения текста. |
| Отклонить или оставить без решения | Эти предложения не разрешают изменения в плане. |
| Новые ответы, решения и комментарии | Отдельный анализ замечаний проверяет актуальный набор оснований и при необходимости задаёт уточняющие вопросы. |
| Применить исправления | Только явная команда после актуального анализа запускает подготовку, проверку и сохранение общего плана. Каждая правка связана с активным основанием. Принятые предложения нельзя молча пропустить. |
| Предварительный поток текста | Показать фрагменты в соответствующих разделах как предварительные; сохранённая ревизия, история и экспорт остаются прежними. |
| Подготовка и проверка завершены | Автоматически сохранить результат без дополнительного действия пользователя. При изменении содержимого создать одну ревизию и сразу показать её. Совпадающий результат фиксируется без лишней ревизии. |
| Уже сохранённый результат требует корректировки | Начать следующий цикл внесения изменений; принятые и применённые основания сохраняются в истории. |
| Отменить принятие до применения | Вернуть предложение в ожидание решения. Сохранить историю; аннулировать актуальность анализа и предпросмотра. |
| Появилась новая обратная связь или изменилась ревизия | Не сохранять устаревший результат. Новая обратная связь требует повторного анализа перед запуском внесения исправлений. |
| Ошибка модели, проверки или сохранения | Сохранить прежний текст и решения. Повтор внесения запускается отдельно; повтор завершения задачи не создаёт вторую ревизию. |
| Остались вопросы или нерешённые предложения | Допустимо применить готовую часть после анализа, сохранив `REVIEW` и оставшиеся вопросы/предложения в том же цикле. |
| Завершены все вопросы и решения | После применения и выполнения правил готовности перейти в `AGREED`. Новые правки начинают новый цикл. |
| Чужой документ, недостаточные права, устаревшая версия | Отклонить команду без изменения текста и решений. |

Уже сохранённые задания с `apply_proposal_id` завершаются по своему неизменяемому
снимку. Принятие больше не создаёт таких заданий; изменение исходного кода само по
себе не отменяет ранее запущенные задачи.
