# Работа с макетами RAGFlow в Figma

Это проектное руководство для человека и агента. Оно связывает макеты с текущим
интерфейсом, задаёт организацию файла и проверяемый результат задачи.
Технические правила Figma API остаются в подключённых Figma skills.

## Состояние подготовки

На 22 октября 2026 года подготовлены структура файла, правила изменений,
карта исходников, начальное соответствие токенов, шаблон задания и критерии
готовности. Вход для агента: [ragflow-figma](../../.agents/skills/ragflow-figma/SKILL.md).

Применение структуры в Figma **не выполнено**: `get_metadata` вернул сообщение
об исчерпанном лимите Figma MCP; `whoami` подтвердил Starter.
Проверка текущего содержимого файла, создание страниц, привязка variables,
сборка компонентов и визуальная проверка в Figma остаются невыполненными.
Подключение не предоставляет Code Layers и Specs; этот процесс рассчитан
на обычные Design-слои и не требует этих возможностей.

Историческая точка входа для ТЗ:
[макет подготовки ТЗ](https://www.figma.com/design/KXjapVwsOznZQqp6BrYxBm?node-id=22-2461).
В предыдущей задаче использовались узлы `22:2461`, `22:2561`, `22:2629`.
Их актуальность и доступ в этой подготовке не подтверждены. Это ссылка для
поиска существующей работы, а не назначенный главный файл всей системы.

Исходники для подготовки прочитаны из checkout с базой
`f4e95aeb224a45f48a55e8447d5f8c30563e2642`; дерево содержало посторонние
незакоммиченные изменения. Данные ниже описывают прочитанный checkout,
не подтверждают версию запущенного приложения и требуют сверки перед переносом.

## Организация файла

Сначала используй существующий файл нужного модуля. Новый файл нужен, если
пользователь выбрал его или подходящего файла нет. Не объединяй файлы БТ, ТЗ
и SQL и не перестраивай существующие страницы только ради одинаковых названий.
Предлагаемая структура для нового файла или отсутствующих разделов:

| Страница | Содержание |
| --- | --- |
| `00 — Начало` | Назначение файла, ссылки на руководство, исходники и рабочие экраны; краткая легенда статусов |
| `01 — Основы` | Используемые цвета, типографика, размеры, правила тем и ссылки на источник каждого токена |
| `02 — Компоненты` | Компоненты и варианты, которые действительно нужны экранам файла; ссылки на библиотеку и код |
| `10 — Текущий интерфейс` | Проверенный снимок существующего сценария с датой, источником и состояниями |
| `20 — Проектирование` | Новые варианты, открытые вопросы и изменения относительно текущего интерфейса |
| `30 — К реализации` | Выбранные пользователем варианты с поведением, состояниями и привязкой к коду |
| `90 — Архив` | Заменённые варианты, только когда они действительно появились |

Создавай страницы по мере появления содержимого. Для первого экрана достаточно
начала, текущего интерфейса и проектирования; не заполняй библиотеку заглушками.
Если в файле уже есть подходящие разделы, используй их и добавь навигацию
на странице начала. Старые ссылки и исходные узлы сохраняй.

Внутри страницы группируй кадры по пользовательскому сценарию.
Имя кадра: `ТЗ / Редактирование / Без источников / 1280 / Light`.
Для варианта добавь понятный суффикс, например `Вариант B`.
Обозначай назначение слоёв: `Header`, `Document`, `Discussion`, `Composer`,
а не случайные имена из импорта. Видимые пользователю тексты — на русском,
если задача не задаёт другой язык.

Статусы: `Текущее` — проверено по источнику; `Предложение` — вариант;
`К реализации` — пользователь выбрал вариант; `Реализовано` — сверено с кодом
и интерфейсом; `Архив` — заменено. Агент не назначает согласование сам.
Для индивидуальной работы отдельные роли и этапы командного согласования не нужны.

## Источники истины и владельцы

- При переносе существующего интерфейса основа — выбранная версия приложения
  и её исходники. Сначала установи, совпадают ли runtime и checkout.
- При проектировании нового поведения задача пользователя определяет результат;
  отличия от реализации помечай как предложения.
- Выбранный макет определяет визуальную цель реализации, но не заменяет API,
  авторизацию и правила сохранённых данных. Найденные противоречия фиксируй явно.
- Снимок экрана — визуальный ориентир. Рабочий макет состоит из редактируемого
  текста, компонентов и векторов. Растровая копия не считается переносом экрана.

## Основы и компоненты

Сначала проверь библиотеки целевого файла. Используй существующие variables,
стили и instances. Если они отсутствуют, переноси только основу нужного экрана
из кода; не создавай параллельную универсальную дизайн-систему.

Ниже начальная карта значений из `web/tailwind.css`, а не созданная библиотека.
Перед применением проверь CSS и переопределения целевого экрана.

| Имя в Figma | CSS | Light | Dark |
| --- | --- | --- | --- |
| `color/bg/base` | `--bg-base` | `#FFFFFF` | `#161618` |
| `color/bg/component` | `--bg-component` | `#FFFFFF` | `#202025` |
| `color/bg/input` | `--bg-input` | белый, alpha 0 | белый, alpha 0.05 |
| `color/bg/canvas` | `--bg-canvas` | `#F6F6F7` | `#000000` |
| `color/text/primary` | `--text-primary` | `#161618` | `#F6F6F7` |
| `color/text/secondary` | `--text-secondary` | `#75787A` | `#B2B5B7` |
| `color/text/disabled` | `--text-disabled` | `#B2B5B7` | `#75787A` |
| `color/border/default` | `--border-default` | чёрный, alpha 0.2 | белый, alpha 0.2 |
| `color/accent/primary` | `--accent-primary` | `#00BEB4` | наследуется из `:root` |
| `color/state/success` | `--state-success` | `#3BA05C` | наследуется из `:root` |
| `color/state/warning` | `--state-warning` | `#FAAD14` | наследуется из `:root` |
| `color/state/error` | `--state-error` | `#D8494B` | наследуется из `:root` |

Учитывай alpha и фон родителя: прозрачное поле не становится белым само.
Нативное имя переменной сохраняй в CSS code syntax или описании variable.
При создании variables используй ограниченные scopes и режимы Light/Dark
в пределах доступного тарифа; если режимы недоступны, явно раздели коллекции.
Размеры и цвета связывай с variables там, где это поддержано, а не только
показывай таблицей образцов.

Шрифт приложения — Inter с InterVariable в поддерживающем браузере.
В Figma сначала проверь доступные семейства и начертания. Размер, вес,
межстрочный интервал бери из конкретного потребителя; не заменяй все тексты
экрана одним размером. Если точного шрифта нет, обозначь замену и предел
визуальной точности.

Для кнопок используй реальные варианты `Button`:
`default`, `secondary`, `accent`, `outline`, `ghost`, `destructive` и другие
только по потребности экрана. Текущие размеры по высоте: `xs=24`, `sm=28`,
`default=32`, `lg=40`, `xl=48` px. Радиусы берутся из Tailwind-конфигурации:
например, `rounded=6`, `rounded-sm=5`, `rounded-lg=7`, `rounded-xl=8` px.
У потребителя могут быть собственные className и стили; они имеют значение.

Компоненты называй по назначению: `Button`, `Input`, `Dialog`,
`Discussion/Composer`. Отражай только применимые свойства: например,
`Variant=outline`, `Size=default`, `State=disabled`. Не создавай декартово
произведение всех вариантов заранее. В описание компонента добавляй источник
в коде, назначение и отличия. Текст и иконки должны заменяться в instance
без отсоединения. Доменный составной блок держи в своём модуле.

Изменение общего Figma-компонента затрагивает его instances: сначала установи
потребителей и нужный масштаб изменения. Изменение `web/src/components/ui/`
регулирует [web/AGENTS.md](../../web/AGENTS.md); подготовка дизайна не разрешает
такое изменение кода автоматически. Code Connect используй при наличии
настроенного соответствия; обычная ссылка на исходник сама по себе не Code Connect.

## Рабочий цикл

1. Уточни результат из запроса и доступного контекста. Запиши короткий бриф.
   Не спрашивай повторно о уже заданных решениях и разрешениях.
2. Прочитай целевой файл, его разделы и библиотеки; найди владельца интерфейса
   и реальные состояния. Сохрани ссылку на исходный кадр перед изменениями.
3. Для переноса нового веб-экрана используй capture как ориентир и создай
   редактируемую структуру. Для изменения существующего макета работай с его
   узлами; повторный импорт всего файла не нужен.
4. Собери выбранный сценарий из существующих компонентов. Используй Auto Layout
   для связанных элементов, Hug/Fill/Fixed по роли, явные правила прокрутки
   и минимальной ширины. Абсолютные координаты оставь для необходимых наложений.
5. Добавь применимые состояния и переходы, проверь структуру и изображение.
   После исправления визуального дефекта перепроверь затронутый результат.
6. Передай ссылки на кадры и коротко опиши изменения, проверки и пробелы.
   Статус «К реализации» назначай только выбранному пользователем варианту.

Не перезаписывай чужие варианты, не удаляй исходники и не меняй доступ/публикацию
библиотек ради организации. При частично выполненном вызове сначала прочитай
результат, затем продолжай по конкретным узлам. При отсутствии доступа или
исчерпанном лимите останови операции с файлом, сохрани подготовку и назови
точно, что осталось применить. Повторные вызовы без изменения условий не помогают.

## Состояния и адаптивность

Выбирай по сценарию, не рисуй одинаковую полную матрицу для каждой правки:

- Основной путь; пустое состояние с понятным следующим действием.
- Загрузка или длительная операция; успех, ошибка и повтор, если они существуют.
- Disabled с причиной, read-only и отказ в доступе там, где они различаются.
- Длинные русские тексты, много элементов, прокрутка и переполнение.
- Для сохранения: изменённое, сохраняется, сохранено, ошибка; конфликт версии
  и восстановление — если это часть сценария.
- Для ИИ: ожидание, ответ/предложение, ошибка, отмена и применение результата
  по реальному контракту модуля. Не добавляй новое подтверждение изменения
  документа, если сценарий его не предусматривает.

Для ТЗ отдельно проверь состояния источников Eva/БТ/без источников, если
затронут этот блок. Для БТ — документ и обсуждение с изменяемой шириной,
поле ввода и чтение истории, если задача относится к ним. Для SQL различай
подготовку проекта и готовый результат; перенос одного не заменяет другое.

Начальные контрольные ширины для нового desktop-макета: 1440 и 1280 px;
1024 и 768 px — когда затронута компоновка или предполагается такой сценарий.
375 px добавляй при мобильном объёме задачи. Это точки проверки, не новые
breakpoints: Tailwind и локальные CSS могут переключать раскладку иначе.
Например, у ТЗ есть пороги 1150 и 760 px; при правке этой раскладки проверяй
обе стороны соответствующего порога. Высоту выбирай по сценарию и фиксируй
в брифе; проверь доступность нижних действий и вложенную прокрутку.

## Шаблон задания

Скопируй и заполни только применимые поля в описании задачи. Это не отдельный
обязательный документ для каждой мелкой правки.

```text
Сценарий: кто, что делает и какой результат получает.
Режим: перенос текущего интерфейса / новый вариант / реализация в коде.
Цель Figma: ссылка на файл и кадр; существующий или новый раздел.
Источник: маршрут, исходники, commit + dirty state, версия runtime, дата.
Разрешённые изменения: экран / доменный блок / общий компонент.
Сохранить: действующее поведение, исходные кадры и иные ограничения задачи.
Состояния: основной путь, нужные ошибки, доступ, сохранение и отмена.
Размеры и темы: ширина × высота; Light/Dark по объёму задачи.
Наблюдаемый результат: что должно стать возможно увидеть, изменить, выполнить.
Проверки: структура, variables/instances, изображение, переходы; код — если меняется.
Передача: ссылки на итоговые узлы, отличия и непроверенные условия.
```

Пример запуска: «Перенеси текущий экран подготовки ТЗ в существующий файл
редактируемыми слоями. Сохрани исходные кадры. Покажи блок источников в трёх
состояниях: Eva, БТ, без источников. Проверь 1280×960 и 1440×960, Light.
Примени проектные правила Figma».

## Критерии готовности

- [ ] Целевой файл и исходный сценарий установлены; источник и дата записаны.
- [ ] Текущее поведение и предложения различимы; исходные кадры сохранены.
- [ ] Тексты редактируются, иконки доступны как векторы; экран не плоская картинка.
- [ ] Составные блоки используют подходящую раскладку; изменения текста не ломают её.
- [ ] Использованы имеющиеся компоненты и токены; новые имеют источник и назначение.
- [ ] Нужные состояния, размеры и темы проверены; исключения перечислены.
- [ ] Снимок итогового макета просмотрен: нет обрезки, наложений и недоступных действий.
- [ ] Прототипные переходы проверены, если входили в задачу; статика обозначена.
- [ ] Выбранный вариант имеет понятную связь с кодом и описание отличий.
- [ ] Переданы ссылки на итоговые узлы и честный статус непроверенного.

Для переноса достаточно подтвердить визуальное соответствие и редактируемость
в заявленных пределах; макет не доказывает работу API, модели, Eva или SQL.
Для реализации в коде дополнительно выполни узкие проверки по
[test/REGRESSION.md](../../test/REGRESSION.md) и визуальную проверку интерфейса.
При чисто документационной подготовке тесты приложения не нужны.

## Применение подготовленной структуры

После восстановления доступа к Figma:

1. Проверить существующий файл модуля и исторические ссылки; определить целевой
   файл по актуальному запросу и контексту.
2. Сопоставить его страницы с предложенной структурой. Добавить только отсутствующее
   и нужное для первого сценария, без перемещения исходных кадров.
3. На странице начала разместить ссылки на руководство, источник и рабочие кадры.
4. Проверить библиотеки; перенести нужные токены и компоненты из текущего кода.
5. Выполнить один реальный сценарий по шаблону и критериям готовности.
6. Заменить статус подготовки выше фактическими ссылками и результатами проверок.
