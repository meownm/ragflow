# Продуктовые и визуальные правила интерфейсов RAGFlow

Профиль RAGFlow для общего skill `frontend-product-design`, ролей проектирования
интерфейсов и предметных ролей заказчика/конечного пользователя.
Общие правила установлены в Codex пользователя;
этот файл хранит проектные решения и связи с кодом. Если общего skill нет в другой
среде, сообщи об этом и используй этот профиль и AGENTS.md для текущей задачи,
не устанавливая зависимости автоматически.

Роли оформлены персональными TOML-файлами в `~/.codex/agents/` по
[официальной документации OpenAI](https://learn.chatgpt.com/docs/agent-configuration/subagents).
Они наследуют настройки основной сессии; отдельные модели и разрешения не заданы.

## Применение и ответственность

Профиль применяется к пользовательским экранам `web/` и приложениям, открываемым
в оболочке RAGFlow, включая ASR и переводчик. Статус документа: начальные правила
и ориентиры; окончательные эталоны появятся после визуальной приёмки пилота.
Предложения и текущий runtime сами по себе не являются утверждённым дизайном.

Предметный аналитик представляет рабочую потребность и проверяет полезность
результата. Продуктолог определяет продуктовый сценарий, состав, тексты и приёмку.
UX/UI-дизайнер проектирует экраны, переходы и состояния. Арт-директор проверяет
иерархию и общий визуальный язык. Основной агент владеет итоговым изменением,
проверками и отчётом. Для узких правок он применяет правила самостоятельно.
На сложном новом сценарии роли полезны до реализации и при проверке результата;
делегирование подчиняется запросу и AGENTS.md, а не запускается для каждой кнопки.

Роли по умолчанию читают код и доказательства; запись разрешена только в явно
порученные документы/макеты. Создание ролей и обзор не разрешают менять продукт,
общую библиотеку, настройки моделей, данные или выполнять деплой.

## Предметные роли по разделам

Для раздела назначается основная предметная роль; её рабочая задача уточняется
в брифе. Это аналитик как заказчик или конечный пользователь продукта, а не ещё
один разработчик и не согласующий начальник. В режиме «заказчик» он формулирует
нужный профессиональный результат и приёмку; в режиме «конечный пользователь»
проходит путь и проверяет полученный артефакт. По умолчанию используется второй.

| Раздел и маршруты | Основная предметная роль | Что проверяет как пользователь/заказчик |
| --- | --- | --- |
| Главная `/`, `/home` | `business_analyst` | Может найти нужный инструмент и продолжить свою работу; для задачи другой профессии выбирается её персона |
| Бизнес-требования `/business-documents` | `business_analyst` | Вводные, цель, сценарии, полнота требований, замечания, основания и сохранённая редакция |
| Технические задания `/technical-specifications` | `systems_analyst` | Переход от БТ к ТЗ, контракты/данные/состояния, противоречия, источники и пригодность для разработки |
| SQL-проекты `/sql-projects`, источники `/sql-sources` | `data_analyst` | Вопрос к данным, схема/связи, состав запроса, выполнение, корректная интерпретация таблицы и сохранение результата |
| Каталог `/openmetadata` | `data_analyst` | Поиск подходящих данных, смысл полей, происхождение и актуальность; `systems_analyst` подключается для интеграционных контрактов |
| Конструктор `/document-constructor`, `/business-documents/constructor` | `systems_analyst` | Структура шаблона и сохранение/повторное использование; для SQL-пути — `data_analyst`, для состава БТ — `business_analyst` |
| Связанные документы `/source-workspaces` | `business_analyst` | Источники, подготовка документа, основания изменений; для ТЗ — `systems_analyst`, для работы с данными — `data_analyst` |
| Базы знаний `/datasets`, `/dataset`, просмотр фрагментов | `data_analyst` | Подходящие источники, готовность и доступность материала, область поиска; настройка ingestion рассматривается отдельно от чтения |
| Поиск `/searches`, `/search` | `business_analyst` | Может найти ответ/документ по рабочему вопросу и проверить основания; для исследования данных выбирается `data_analyst` |
| Чаты `/chats`, `/chat` | `business_analyst` | Контекст, ответ с основаниями, продолжение работы и перенос результата; технические/аналитические задачи получают свою персону |
| Агенты `/agents`, `/agent`, шаблоны и журналы | `systems_analyst` | Сборка и запуск понятного рабочего процесса, вход/выход, ошибки и состояние; результат бизнес-процесса проверяет `business_analyst` |
| Память `/memories`, `/memory` | `systems_analyst` | Что сохраняется и используется, область видимости, управление и влияние на последующую работу |
| Расшифровка `/transcription`, `/asr/` | `business_analyst` | Как сотрудник получает пригодный текст встречи из записи, понимает ошибку и использует результат |
| Переводчик `/translator`, `/translate/` | `business_analyst` | Как сотрудник переводит рабочий материал, понимает язык/ограничения и получает результат нужного формата |
| Файлы `/files` | `business_analyst` | Как сотрудник находит, загружает и использует материал; для подготовки наборов данных — `data_analyst` |
| Вход, профиль, настройки | Персона целевого сценария; для технических настроек — `systems_analyst` | Вход и возврат к работе, понятное сохранение настроек, ограничения прав; не требовать знания реализации от обычного сотрудника |
| Админка `/admin` | `systems_analyst` как технический заказчик | Проверяет задачи управления и технические контракты; при проверке конечного пути явно задаётся персона администратора |

Матрица — начальное назначение проверяющего, а не утверждение, что у всех разделов
только одна аудитория. Если задача называет другого реального пользователя,
он важнее назначения по умолчанию. Для переводчика аналитик оценивает рабочий путь,
а точность перевода требует отдельной языковой проверки. Для ASR пригодность
сценария не доказывает точность распознавания. Эти роли не получают дополнительных
прав в приложении и не заменяют проверку на реальных пользователях.

Результат предметной проверки: профессиональная задача и режим, шаги получения
результата, препятствия с доказательствами, проверяемая приёмка и неизвестные
сведения. Аналитик не назначает палитру и не утверждает макет от имени заказчика.

## Язык и уровни подробности

Основной пользовательский путь описывается по-русски через действие и результат.
Роль и задача определяют нужную глубину: сотрудник работает с документом,
автор ТЗ — в том числе с кодом и схемами, администратор — с состоянием системы.

| Информация | Правило |
| --- | --- |
| Название, редакция документа, автор, статус сохранения | Показывать в рабочем контексте; различать текст документа и служебное состояние операции |
| Код бизнес-функции из каталога, SQL, API в тексте ТЗ | Сохранять, когда это предметные данные; не удалять вместе с диагностикой |
| Внутренний `state_version`, UUID задания или исполнителя | Переводить в понятный смысл; при необходимости оставлять безопасную диагностику в подробностях |
| Модель, ограничения поиска, подключение к EVA | Показывать там, где пользователь принимает соответствующее решение; причину ограничения объяснять через доступное действие |
| Сбой сервиса | Объяснить недоступность, судьбу работы и действительный способ продолжения; не выдавать nginx/исключение за рабочий экран |

Не своди все названия к одному слову механически. В проверенном пилоте БТ применена
«Редакция» для сохранённой версии документа, согласованная с ТЗ;
backend-поля не переименовывались. Изменение пилота пока не развёрнуто.
«Рабочее пространство», «подборка» и «проект» требуют проверки
смысла в своём сценарии перед унификацией. Термины «Принять» и «Применить изменения»
не взаимозаменяемы: решение по предложению и запись результата имеют разный смысл.

Подробности по запросу не заменяют серверных прав. Сохраняй разграничение tenant,
проверки актуальной редакции, историю и защиту от повторного применения.
Не добавляй второй шаг подтверждения обычного сохранения ради нового процесса.

## Правила композиции

- Оболочка сохраняет навигацию, тему и узнаваемые действия. Рабочая область
  может иметь свою плотность и панели, сохраняя типографическую иерархию,
  семантические цвета и варианты компонентов.
- Заголовок показывает рабочий объект. Статус сохранения и номер редакции
  различимы; технический счётчик не выглядит второй версией документа.
- БТ показывает все разделы и подразделы опубликованного шаблона в его порядке,
  включая пустые. Для действительно пустого тела выводится «Требований нет».
  Явное содержимое «Требования не определены» сохраняет свой смысл незакрытого
  вопроса. Пилотные примеры и снимки тоже обязаны сохранять полный состав;
  номера и заголовки берутся из шаблона, а не копируются в отдельный список.
- Семантический токен сам по себе не гарантирует читаемость. Для мелкого
  значимого текста проверяй контраст с фактической подложкой в обеих темах;
  локальная подложка с прозрачностью тоже влияет на результат.
- Встроенный инструмент не получает собственный конкурирующий бренд и огромный
  вступительный блок без потребности сценария. Его standalone-режим учитывается
  отдельно: единый стиль не требует общего фреймворка или копирования React.
- Для редактора проверь документ, обсуждение, историю и ввод вместе; для списка —
  заголовок, поиск, фильтры, карточки/строки и пустое состояние.
- Для каждого изменения нужны применимые состояния: загрузка, пусто, успех,
  ошибка, ограничения прав, конфликт актуальности. Не все состояния обязательны
  для косметической правки, но затронутые состояния нельзя считать проверенными
  по одному успешному скриншоту.

Проверки выбираются по [test/REGRESSION.md](../../test/REGRESSION.md).
Для документации и конфигурации ролей достаточно разбора форматов, ссылок,
diff и независимой проверки инструкций. Изменения приложения требуют отдельных
проверок поведения и браузера; создание этих файлов их не заменяет.

## Как поручать работу

Пример: «Попроси `business_analyst` пройти сценарий замечаний к БТ как конечный
пользователь; `product_manager` уточнит продуктовые решения, `ux_ui_designer`
спроектирует взаимодействие, `art_director` проверит визуальную согласованность.
Сейчас нужен обзор без правок приложения; основной агент объединяет решения».
Не все роли нужны для каждой задачи: выбирай их по затронутому риску.
Если среда ещё не загрузила
новые роли, открой новый чат; доступность роли не следует из одного наличия TOML.

Обзор, сценарий и результаты исполненного пилота:
[пилот бизнес-требований](frontend-pilot-business-documents-ru.md).

Уточнение приёмки: [полнота разделов БТ](frontend-pilot-complete-outline-20261023-ru.md).
