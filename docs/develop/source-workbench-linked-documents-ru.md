# Связанные документы: этапы 1–3

Раздел `/source-workspaces` поддерживает рабочие документы, неизменяемые редакции,
типизированные основания и предложения правок при изменении непосредственных
источников. Правки применяются только после решения назначенного согласующего.

## Пользовательский сценарий

1. Создать рабочее пространство. Базы знаний можно подключить позднее.
2. Создать ТЗ, инструкцию или другой документ либо открыть сохранённый черновик.
3. Во вкладке поиска выбрать статьи и подключить их как снимки источников.
   Рабочий документ также может служить источником для другого документа.
4. Настроить направление связи, обязательность, разделы источника и получателя,
   событие актуализации и ответственного. Обязательные связи настраивает владелец.
5. Нажать «Проверить источники» и «Подготовить предложения».
6. Просмотреть правки в соответствующих разделах; прежний текст остаётся доступен.
7. Подтвердить применение или отклонить предложение. Решение и комментарий
   сохраняются. Отклонение не подтверждает отсутствие влияния.
8. Сравнить редакции во вкладке истории. Сохранение текста и утверждение
   редакции — отдельные действия.

Если изменился срок хранения в бизнес-требованиях, система сначала сохраняет
новый снимок источника, затем готовит правку раздела ТЗ. До подтверждения ТЗ
не изменяется. Незатронутые разделы сохраняют текст и идентификаторы.

Независимые группы можно выбрать отдельно. Операции по одному основанию
применяются вместе; выбранная часть проходит отдельную смысловую проверку без
повторной генерации. Отложенные источники остаются неразобранными.

## Типы и полномочия

Тип содержания не определяет приоритет или разрешение на изменение.

* Типы: бизнес-требования, ТЗ, архитектура, БД, API, инструкция, испытания,
  регламент, справочный и другой документ.
* Политики: рабочий, изменение по согласованию, зафиксированный.
* Отношения: задаёт требования, ограничивает решения, детализируется,
  отражает результат, проверяется, используется как справка.
* Актуализация: после сохранения, утверждения или подтверждения реализации источника.
* Сопровождение: по запросу либо автоматическая подготовка предложений.

В режиме «Рабочий документ» ручное сохранение создаёт редакцию сразу. В режиме
«Изменения по согласованию» оно создаёт неизменяемое предложение с автором,
базовой версией и полным текстом правки. Текущий документ остаётся прежним.
Назначенный согласующий принимает или отклоняет предложение целиком. Применение
создаёт одну редакцию и записывает решение; повторное подтверждение не дублирует
редакцию. После отклонения можно представить исправленный текст повторно.
Изменение документа, политики, согласующего или оснований делает предложение
устаревшим. Старый API черновиков использует тот же сценарий согласования.

Принятие ручного текста не подтверждает полноту требований: влияние оснований
остаётся открытым до отдельной проверки. Утверждение редакции сохраняет этот
контроль. Ручные предложения не проходят генерацию моделью и не допускают
частичного применения; для другого текста сохраняют новое предложение.

Автоматическое задание запускается только изменением связи с автоматическим
сопровождением. Другие доступные основания остаются контекстом проверки.
Исторические источники продолжают участвовать в проверке доступа после удаления
связи, но их новые версии не блокируют работу с действующими основаниями.
Очистка области поиска не закрывает доступ к ранее сохранённым черновикам;
для них проверяются собственные основания.

Владелец управляет пространством и обязательными связями. Редактор готовит и
сохраняет рабочие редакции. Согласующий принимает предложения и утверждает
назначенные ему документы. Читатель просматривает доступные документы.
Изменение согласующего, политики или связи инвалидирует подготовленный результат.

Пространство имеет организацию. При создании она выбирается автоматически
только при единственном активном членстве пользователя. У старых пространств
организация остаётся неопределённой; перед приглашением участников владелец
явно выбирает её. Заменить уже назначенную организацию нельзя. Приглашать можно
только активных участников этой организации. Отзыв членства блокирует доступ.

Роль пространства не предоставляет доступ к закрытым базам знаний. Проверяются
также исторические основания и источники сохранённых предложений, даже после
удаления связи. Старые API черновиков применяют те же ограничения на изменение
и сохраняют редакции через тот же механизм.

## Владение и данные

`linked_domain.py` содержит правила версий, подтверждения, операций и областей
связей. `linked_application.py` координирует сценарии без импортов ORM, Quart,
модели или сетевого клиента. `linked_storage.py` реализует запросы, блокировки
и записи. `linked_runtime.py` явно собирает зависимости для REST и исполнителя.

Существующая таблица `source_workspace_draft` расширена до проекции рабочего
документа. Отдельного изменяемого хранилища документов не создаётся. `content`
является текущей текстовой проекцией; каноническое содержание редакции — разделы
с устойчивыми идентификаторами в `source_document_revision`.

| Таблица | Назначение |
| --- | --- |
| `source_workspace` | Поисковая подборка и организация пространства |
| `source_workspace_member` | Полномочия участников |
| `source_workspace_draft` | Проекция документа, тип, политика, текущая и утверждённая редакции |
| `source_document_revision` | Неизменяемые разделы, хеш, автор и метаданные снимка источника |
| `source_document_dependency` | Направленная связь, её версия и проверенная пара редакций |
| `source_document_input` | Основания конкретной редакции и настройки связей на тот момент |
| `source_document_impact` | Влияние версии источника на определённую редакцию получателя |
| `source_document_change` | Структурированный кандидат, основания и результат проверки |
| `source_document_decision` | Решение, автор, время и комментарий |
| `source_document_job` | Задание, аренда, попытки, отмена и сохранённый кандидат |
| `source_document_event` | Причины изменения и аудит |

Для внешнего источника сохраняются индексированный текст, хеш, идентификаторы
базы и статьи, признак версии, название, URL и время получения. Это снимок
индексированного представления, а не восстановленная вёрстка оригинала.
Повторный импорт использует тот же документ внутри пространства. Переиндексация
с неизменным текстом не создаёт новую содержательную редакцию.

У предложения различаются происхождение `model` / `manual` и автор. Поле
`candidate_sections` хранит полный текст ручного предложения; `HUMAN_REQUIRED`
означает ожидание человеческого решения, а не результат модельной проверки.
Миграция добавляет эти поля и к существующей таблице предложений, сохраняя
прежние записи как предложения модели.

Подборки поиска сохраняют ограничение совместимости embedding-моделей.
Это ограничение запроса поиска; уже подключённые документы из разных подборок
можно связывать между собой.

## Применение и фоновые задания

План содержит добавления, замены и удаления разделов, ссылки на основания и
объяснение влияния каждого доступного источника. Возможные итоги:
`changes_required`, `no_impact`, `conflict`, `insufficient_data`.
Конфликт и недостаток данных блокируют применение.

После генерации выполняются структурные проверки и одна смысловая проверка.
Входы не обрезаются для получения PASS. При недостатке контекста задача
завершается явной ошибкой; область источников можно сузить до разделов.
Смысловая проверка является суждением модели, а не формальным доказательством.

Исполнитель запускается вместе с сервером. Задания хранятся в БД, имеют аренду
60 секунд с продлением и восстанавливаются после истечения аренды. Сохранённый
кандидат повторно используется при восстановлении проверки. Устаревший исполнитель
не может завершить задание или опубликовать результат. Закрытие страницы не
отменяет задание; отмена выполняется отдельной командой.

Модель и индекс вызываются вне транзакций. Перед сохранением предложения и
применением проверяются актуальные версии. Применение блокирует затронутые
документы в устойчивом порядке и атомарно записывает редакцию, основания,
решение и событие. Повторное подтверждение не создаёт вторую редакцию.
Результат `no_impact` требует подтверждения, но не создаёт дубликат текста.

Проверка основания относится к паре редакций «источник — получатель».
Поэтому ручная правка ТЗ после проверки снова открывает влияние основания,
даже если сам источник не изменился.

## HTTP-контракт

Все пути ниже начинаются с `/api/v1/source-workspaces/{workspace_id}`.
Используется существующий конверт `{ "code": 0, "data": ... }`.

| Метод и путь | Действие |
| --- | --- |
| `GET/POST /documents` | Список метаданных / создание документа |
| `POST /documents/import` | Снимок индексированной статьи |
| `GET/PUT /documents/{id}` | Чтение / новая ручная редакция или настройки |
| `GET /documents/{id}/revisions/{revision_id}` | Неизменяемая редакция |
| `POST /documents/{id}/dependencies` | Добавление связи |
| `PUT/DELETE /documents/{id}/dependencies/{dependency_id}` | Настройка / удаление связи с сохранением истории |
| `POST /documents/{id}/refresh` | Проверка прямых источников |
| `POST /documents/{id}/prepare` | Подготовка предложения, ответ `202` |
| `POST /documents/{id}/changes/{change_id}/selection` | Проверка выбранных групп, ответ `202` |
| `POST /documents/{id}/changes/{change_id}/decision` | Подтверждение или отклонение |
| `POST /documents/{id}/approve` | Утверждение редакции |
| `POST /documents/{id}/baseline` | Явное принятие текущих источников старого черновика владельцем |
| `POST /documents/{id}/jobs/{job_id}/cancel` | Отмена задания |
| `GET/PUT /members` | Участники и полномочия |
| `GET/PUT /organization` | Организация пространства |
| `PUT /datasets` | Изменение области поиска |

Создание ТЗ:

```json
{"title":"ТЗ подсистемы хранения","document_type":"technical_specification","content":"# Хранение\nХранить данные 30 дней.\n"}
```

Связь с бизнес-требованиями:

```json
{"source_id":"source-document-id","expected_version":2,"relation":"requires","required":true,"source_scope":[],"target_scope":[],"refresh_on":"approved","maintenance":"manual","blocks_approval":true}
```

Подготовка и подтверждение:

```json
{"expected_version":3,"prompt":"Учесть новый срок хранения, сохранив остальные требования."}
```

```json
{"action":"accept","comment":"Новый срок согласован."}
```

Выбор части правок перед отдельной проверкой:

```json
{"selected_sections":["section-id"]}
```

Чтение документа возвращает текущие разделы, заголовки истории, связи, влияния,
предложения, решения и публичное состояние заданий. Содержимое исторической
редакции загружается отдельно. В предложения не копируются полные тексты
снимков; они доступны через неизменяемые редакции источников. Аренды и внутренние
контрольные точки не возвращаются клиенту.

Ошибки включают `VERSION_CONFLICT`, `SOURCE_CHANGED`, `STALE_CHANGE`,
`STALE_POLICY`, `STALE_SCOPE`, `DOCUMENT_LOCKED`, `PERMISSION_DENIED`,
`BASELINE_REQUIRED`, `UNRESOLVED_DEPENDENCY`, `SOURCE_NOT_APPROVED`,
`DEPENDENT_OPERATIONS` и ошибки бюджета контекста. Конфликты версий имеют HTTP 409;
ошибки прав — 403 либо 404 при отсутствии доступного объекта. Клиент не должен
повторять применение к новой редакции автоматически.

## Миграция и проверка

`init_database_tables()` вызывает `migrate_linked_documents()` после текущих
миграций. Новые столбцы и таблицы создаются идемпотентно. Перенос каждого старого
черновика атомарен. Текст, промпт, версии и исходные ссылки сохраняются; первая
известная редакция не изображает утраченную историю.

Если исторических текстов источников нет, документ получает состояние
`unresolved`. После явного подтверждения владелец принимает сегодняшние снимки
как новую базу. Обязательность связей при этом не назначается автоматически.
Новые результаты существующего редактора статей сразу сохраняют действительные
снимки и не нуждаются в таком подтверждении.

Проверки из корня репозитория:

```powershell
.venv\Scripts\python.exe -B -m pytest -q test/unit_test/api/apps/source_workbench test/unit_test/tools/quality/test_owned_boundaries.py
```

`test/integration/test_source_document_migrations.py` выполняет реальные проверки
PostgreSQL: исходная схема, повторная миграция, прерывание переноса,
восстановление, обновление ТЗ и конкурентное сохранение. Он требует собственной
одноразовой БД `linked_test` на `127.0.0.1`, флага
`RAGFLOW_LINKED_TEST_DISPOSABLE=1` и порта в `RAGFLOW_LINKED_TEST_POSTGRES_PORT`.
Рабочее хранилище раздела — PostgreSQL; SQLite используется в изолированных
модульных и HTTP-тестах. Не направлять интеграционные тесты на общую БД приложения.

Проверки интерфейса находятся рядом с компонентами Source Workbench. Модельные
ответы в детерминированном сценарии контролируются: это проверка оркестрации,
сохранения и применения, а не оценка качества действующей модели.

## Цепочки, факт реализации и обязательный комплект

Обзор во вкладке «Документы» рассчитывает причины состояния и следующее действие
без изменения данных и вызова модели. Фильтр по умолчанию — «Требуют внимания»;
доступны «Мои задачи», «Все» и поиск по названию. Источники и зависимые документы
открываются из редактора; переход с несохранённым текстом требует сначала сохранить
или отменить правки. На узком экране список и формы сохраняют те же действия.

Проверка циклов выполняется под блокировкой пространства. Чисто справочная связь
(`reference`, необязательная, без блокировки утверждения, с ручным сопровождением)
не входит в граф актуализации. Старые циклы сохраняются, видны в обзоре и
останавливают подготовку; ошибочную связь можно удалить. Подготовленное предложение
не распространяется дальше по цепочке до подтверждения его применения.

Ответственный редактор подтверждает реализацию последней утверждённой редакции
целиком. Перед действием форма показывает номер редакции. Владелец и согласующий
не получают это полномочие автоматически. Новая рабочая редакция не наследует
реализацию; прежнее подтверждение утверждённой редакции остаётся в истории.
Комментарий и ссылка необязательны, причина отмены обязательна. Повторная отправка
того же подтверждения или отмены не создаёт второе событие.

Связь `refresh_on=implemented` использует подтверждённую реализованную редакцию
и ID её подтверждения. Одного утверждения ТЗ недостаточно для её запуска.
Отмена делает старые предложения неприменимыми и открывает повторную проверку
оснований, сохраняя уже применённый текст. Повторное подтверждение той же редакции
имеет новый ID и также требует новой проверки. Внешние источники не могут иметь
событие реализации: реализацию подтверждают у локального рабочего документа.

Владелец в свойствах локального документа отмечает «Входит в обязательный комплект».
«Документы согласованы» требует утверждения текущих редакций отмеченных документов
и разбора их обязательных оснований, включая цепочки через неотмеченные документы.
«Сопровождение завершено» дополнительно учитывает ожидание реализации и актуализации.
Пустой комплект не считается готовым. Обычная неотмеченная заметка сама по себе
не блокирует комплект. Сводки вычисляются из фактов; отдельного изменяемого статуса нет.

## Источники Business Documents

Подключение доступного документа сохраняет неизменяемый снимок последней доказуемо
согласованной редакции и ссылку на оригинал. Новый черновик не заменяет согласованное
основание. Доказательство — событие `ReviewAgreedWithoutChanges` либо `ChangesApplied`
с буквальным `review_continues=false`, с существующей редакцией того же документа.
Одного состояния `AGREED` или произвольной записи истории недостаточно.

Это только читающая интеграция с интерфейсом владельца Business Documents.
Права общего каталога сохраняются; дополнительный фильтр по организации пространства
не добавляется. При подключении, чтении, подготовке и применении проверяются доступ
и существование оригинала. При применении согласованная редакция повторно проверяется
под блокировкой оригинала в общей PostgreSQL-транзакции. Сохранённый текст и старый
API черновиков не обходят отзыв доступа. Обновление согласованной редакции видно
в обзоре даже при ручном сопровождении, без автоматического изменения снимка.

Повторное подключение возвращает тот же источник пространства. При обновлении
доказательства согласования создаётся новая редакция снимка даже для одинакового
текста; прошлое доказательство остаётся в истории. Ни текст, ни статус оригинала
из Source Workbench не изменяются.

## Дополнительные контракты

Все пути ниже относительны к `/api/v1/source-workspaces/{workspace_id}`.
Команды возвращают свежую проекцию; UI отображает её без дополнительного чтения текста.

| Маршрут | Доступ и результат |
| --- | --- |
| `GET /document-overview` | Читатель пространства; метаданные, причины, действия, две сводки. Пакетное чтение в согласованном снимке PostgreSQL; без полных текстов |
| `PUT /documents/{id}` | `required_for_readiness` меняет только владелец, с `expected_version` |
| `POST /documents/{id}/implementation` | Ответственный редактор; `revision_id`, `expected_version`, необязательные `comment`, `evidence_url` |
| `POST /documents/{id}/implementation/revoke` | Ответственный редактор; `implementation_event_id`, `expected_version`, обязательный `reason` |
| `GET /business-document-sources?query=&page=1` | Редактор пространства; доступные согласованные источники, страницы по 20 |
| `POST /documents/import` | Дополнительно принимает `kind=business_document`, `document_id`; прежний формат индексированных статей сохранён |

Новые поля добавляются аддитивно. Старые документы не включаются в обязательный
комплект и не считаются реализованными. В связях, влияниях и исторических основаниях
сохраняется токен факта источника; повторная миграция и прерывание смены уникального
индекса допускают восстановление. Сохранённые задания saved/approved совместимы.

## Проверки пакетов П1–П6

DoR: определены состояния, права, AC, воспроизводимые фикстуры и потребители
(HTTP, worker, UI, старые черновики, сохранённые задания и миграции).
DoD: соответствующие проверки ниже завершены, нет незакрытых дефектов ревью,
данные фикстур очищены; отсутствие окружения означает неполную проверку.

| Пакет / AC | Проверки |
| --- | --- |
| П1 / AC-1 | `test_linked_next.py`, HTTP; PostgreSQL: конкурентные встречные связи, согласованный снимок обзора; старый цикл и отсутствие вызова модели |
| П2 / AC-2 | Обзор 20/200 документов с постоянным числом запросов; Jest; Chromium: поиск, навигация, несохранённый текст, поздние ответы |
| П3 / AC-3 | HTTP-права ответственного/согласующего/читателя/постороннего; редакция и повторная отправка; Chromium: форма, ошибка сети, история после reload |
| П4 / AC-4 | Отмена, повторное подтверждение, устаревший кандидат, сохранение применённого текста и ручного раздела; восстановление/отмена worker |
| П5 / AC-5 | `test_linked_business_sources.py`; PostgreSQL: блокировка оригинала до завершения общей транзакции; история доказательств, удаление, неактивный пользователь, старый API черновиков |
| П6 / AC-6 | Обязательные транзитивные основания и необязательное ожидание; Chromium: настройка комплекта; `test_linked_documents_live.py` — единая цепочка с реальным worker и моделью |

Изолированный браузерный набор: `test/playwright/e2e/test_linked_documents_ui.py`,
собранный SPA, Chromium и синтетические HTTP-ответы. Реальный сценарий запускается
только через `test/integration/live_ragflow/runner.py` с этим checkout как source root,
собранным SPA и `test/playwright/e2e/test_linked_documents_live.py`. Он создаёт свой
PostgreSQL/Redis/MinIO/Elasticsearch/app, использует синтетическое согласование
Business Documents как входную фикстуру, настоящую модель и HTTP/UI применения.
Это не проверка полного согласования оригинала в интерфейсе Business Documents.
Runner удаляет собственные контейнеры, тома и сеть; рабочий сервер не переключается.

Публикация во внешние системы, обратная запись Business Documents, массовое применение
и графический редактор связей не входят в этот сценарий.
