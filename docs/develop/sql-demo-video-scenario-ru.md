## Исходный вопрос

> Покажи по поставщикам источников глоссария число уникальных источников и число уникальных полученных снимков. Учитывай только источники, у которых есть лицензионная проверка со статусом accepted_metadata_only и хотя бы один снимок. Одна строка — один поставщик. Используй весь доступный период. Сортируй по числу снимков по убыванию, затем по поставщику по возрастанию; максимум 10 строк. Не выводи содержимое снимков, ссылки, служебные payload и персональные данные.

Ожидаемые источники для контроля сценария: glossary_source, raw_glossary_source_snapshot и glossary_source_license_review из imba_translate. Это контроль результата, а не пользовательский ввод и не подсказка модели в коде. Шесть уникальных полей: source_id и provider источника, snapshot_id и source_id снимка, source_id и review_status проверки. Два JOIN по source_id; уникальные счётчики защищают от размножения строк.

Считаем уникальные источники и уникальные снимки, оставляем только источники с принятой проверкой и хотя бы одним снимком. Используем весь доступный период. Проверяем, что модель не добавила лишних условий. |
| 3 | Поиск по подтверждённым требованиям без дополнительного ввода; проверка источников и шести полей | По подтверждённым требованиям агент сам выделяет нужные данные. Имена таблиц вводить не нужно. Каталог нашёл источники глоссария, полученные снимки и лицензионные проверки. Сверяем описания и выбираем подходящие источники. Отмечаем поля для связей и расчёта, затем подтверждаем схему. |
| 4 | Принять схему; раскрыть граф и ключи | На схеме проверяем связи по идентификатору источника. У одного источника может быть несколько снимков и проверок. Поэтому обычный подсчёт строк соединения способен завысить показатели. Уникальные счётчики сохраняют согласованный смысл: каждый источник и каждый снимок учитываются один раз. |

Проверяем порядок: сначала число снимков по убыванию, затем поставщик по возрастанию. После проверки подтверждаем предложение. |
| 6 | Открыть проверенный SQL и параметры | SQL доступен для чтения. Здесь соединяются три таблицы, применяется согласованный статус и рассчитываются два показателя. | 7 | Проверить подключение; выполнить запрос | Проверяем доступный источник и профиль только для чтения. Перед запуском система повторно проверяет доступ и актуальность схемы. Выполняем запрос. Ожидание базы и модели в монтаже можно сократить, сохранив последовательность действий. |

| 9 | Сформировать вывод; проверить ссылки на ячейки и подтвердить текст | Модель подготовила короткий вывод по проверенным строкам. Сверяем числа с таблицей и указанными ячейками. В тексте сохранено предупреждение об ограниченной выборке. После проверки подтверждаем вывод: теперь его можно включить в документ. |
| 10 | Завершить первый READY-запуск; открыть документ | Завершаем первый проход. Сохраняется документ с задачей, запросом, проверками и подтверждённым выводом. Временные строки результата очищаются. Документ остаётся доступным; чтобы получить данные снова, потребуется выполнить запрос ещё раз. |
| 11 | Комментарий к SQL; запросить CTE; сравнить и принять предложение | Попросим сделать запрос удобнее для чтения: вынести отобранные строки в именованный подзапрос. Смысл расчёта, уникальные счётчики, параметры и сортировка сохраняются. Проверяем различия и статус проверки. Принятие создаёт новую версию SQL, а исходная остаётся в истории. |
| 12 | «Повторить запрос» → preflight → «Выполнить запрос»; сравнить результаты | Для новой версии нажимаем «Повторить запрос», проверяем источник и затем «Выполнить запрос». На том же стабильном наборе данных проверяем равенство строк, значений и порядка. Красивый SQL и успешная проверка текста ещё не доказывают равенство результатов: его подтверждаем по данным. |
| 13 | Открыть историю; выбрать обе версии; раскрыть контекст; скачать запрос | В истории видны обе версии и основания расчёта. Можно проверить требования и схему выбранного запроса, посмотреть различия и скачать нужную версию. Результат относится к своему запуску и SQL. Просмотр старой версии не заменяет текущий запрос. |
| 14 | Вернуться к текущей версии; завершить её запуск; перезагрузить | Сохраняем документ текущего запуска и открываем проект заново. Сохранились версии и принятые решения. Временные строки очищены. Для повторного получения данных снова выполняем запрос. |
| 15 | Итог на экране проекта | Мы получили сводку по трём связанным источникам, проверили данные и сохранили документ. SQL можно дорабатывать через комментарии, а историю решений — просматривать и проверять. |

## Контроль завершения

Два реальных запуска через профиль PostgreSQL только для чтения. После доработки SQL через комментарий сравниваем строки, значения и порядок с первым запуском и отдельным контрольным SELECT READ ONLY. Проверяем два ИИ-вывода с ссылками на числовые ячейки, историю версий, экспорт, два документа и сохранение состояния после перезагрузки.

Финальная проверка: частота и PTS захвата; разные кадры при движении; число кадров итогового файла равно сумме выбранных исходных кадров; полный декодирующий проход; синхронные субтитры, главы и звук. Предупреждение о возрасте метаданных сохраняется в кадре, перед выполнением проверяется живой источник.
