## Сценарий и проверяемый результат

Пользователь — аналитик с доступом к каталогу, созданию и изменению SQL-проектов
и выполнению запросов через профиль только для чтения. Отдельный проект репетиции:
«SQL-демо — полный проход 21.10.2026». Чужие проекты не изменяются.

Результат: вопрос → требования → три связанные таблицы → SQL → реальные строки →
проверка вывода → документ → доработка через комментарий → новый запуск → история.
Принимается только реально пройденный путь. Синтаксический разбор SQL не заменяет
проверку продуктом, а прямой контрольный запрос не заменяет выполнение через UI.

Основной сюжет: источники глоссария, их снимки и лицензионные проверки. Все три
таблицы найдены через каталог по точным именам, поля и схема приняты, запрос агента
выполнен в PostgreSQL. Поиск по обычным русским формулировкам не дал нужных таблиц
в первом проходе; в записи честно показываем уточнение технических имён.

Исходный сюжет про медленные ответы оставлен вне основного ролика. Прежний отказ
загрузки полей и HTTP 503 графа исправлены в локальной поставке 1.50.1.

## Точные вводы

**Исходный вопрос:**

> Покажи по поставщикам источников глоссария число уникальных источников и число уникальных полученных снимков. Учитывай только источники, у которых есть лицензионная проверка со статусом accepted_metadata_only и хотя бы один снимок. Одна строка — один поставщик provider. Используй весь доступный период. Сортируй по числу снимков по убыванию, затем по provider по возрастанию; максимум 10 строк. Не выводи содержимое снимков, ссылки, служебные payload и персональные данные.

**Поиск в успешном проходе:** три строки `glossary_source`,
`raw_glossary_source_snapshot`, `glossary_source_license_review`. Реплика:
«Уточняем поиск по известным именам таблиц». Первый пользовательский вопрос
остаётся обычным текстом без технических имён. Поиск по смыслу в этом дубле
не объявляется успешно подтверждённой возможностью.

**Принятые требования:** одна строка на provider; COUNT DISTINCT source_id и
snapshot_id; есть проверка accepted_metadata_only и хотя бы один снимок; весь
период; сортировка unique_snapshots DESC, provider ASC; LIMIT 10. NULL provider не
исключается. Содержимое снимков, URL, payload и персональные поля не выводятся.

**Ожидаемые таблицы:** imba_translate.glossary_source,
imba_translate.raw_glossary_source_snapshot,
imba_translate.glossary_source_license_review. Два соединения по source_id.
Несколько снимков и проверок одного источника не должны завышать счётчики.

**Комментарий для доработки:**

> Вынеси JOIN и отбор по статусу проверки в обычный нерекурсивный CTE
> eligible_snapshots с полями source_id, provider, snapshot_id. Во внешнем SELECT
> сохрани COUNT DISTINCT source_id и snapshot_id, группировку по provider, имена
> выходных полей, все значения и типы параметров, сортировку и внешний LIMIT.
> Внутрь CTE LIMIT не добавляй. Бизнес-смысл не меняй.

Если агент сразу дал CTE, запросить обратное преобразование в эквивалентный плоский
SELECT. Идентичное предложение не принимается ради демонстрации новой версии.

## Контрольные запросы

Это ожидаемые формы, не заранее подставленные ответы модели. Продукт проверяет
запрос по принятой схеме, пользователь проверяет смысл и параметры.

Плоский SELECT:

```sql
SELECT s.provider AS provider,
       COUNT(DISTINCT s.source_id) AS unique_sources,
       COUNT(DISTINCT rs.snapshot_id) AS unique_snapshots
FROM imba_translate.glossary_source AS s
JOIN imba_translate.raw_glossary_source_snapshot AS rs
  ON rs.source_id = s.source_id
JOIN imba_translate.glossary_source_license_review AS lr
  ON lr.source_id = s.source_id
WHERE lr.review_status = :review_status_value
GROUP BY s.provider
ORDER BY unique_snapshots DESC, provider ASC
LIMIT :row_limit
```

Эквивалентная форма CTE:

```sql
WITH eligible_snapshots AS (
    SELECT s.source_id AS source_id, s.provider AS provider,
           rs.snapshot_id AS snapshot_id
    FROM imba_translate.glossary_source AS s
    JOIN imba_translate.raw_glossary_source_snapshot AS rs
      ON rs.source_id = s.source_id
    JOIN imba_translate.glossary_source_license_review AS lr
      ON lr.source_id = s.source_id
    WHERE lr.review_status = :review_status_value
)
SELECT e.provider AS provider,
       COUNT(DISTINCT e.source_id) AS unique_sources,
       COUNT(DISTINCT e.snapshot_id) AS unique_snapshots
FROM eligible_snapshots AS e
GROUP BY e.provider
ORDER BY unique_snapshots DESC, provider ASC
LIMIT :row_limit
```

Параметры интерфейса:

```json
[
  {"name":"review_status_value","type":"text","value":"accepted_metadata_only"},
  {"name":"row_limit","type":"integer","value":10}
]
```

Для прямого psql параметры подставляются отдельно; двоеточия здесь относятся
к формату конструктора. Контрольный запрос выполняется в read-only транзакции
со statement_timeout 15 секунд. Сверяются все строки, типы и порядок, а не только
первая строка. Для эквивалентности требуется стабильный набор данных.

## Ограничения съёмки и дополнительные эпизоды

- Основной ролик не включает намеренную ошибку, повторное согласование порога,
  восстановление и пять почти одинаковых ручных шагов. Они не нужны для 9-минутного
  прохода возможностей. Пошаговый редактор можно показать отдельным учебным роликом.
- Для восстановления SQL сначала проверить совместимость с текущими требованиями
  и схемой. Восстановление создаёт новую compilation и требует нового запуска перед
  завершением. Автоматическая смысловая проверка старых порогов не обещается.
- Если изменился смысл требований, сначала согласовать задачу и данные, затем
  получить новое SQL-предложение. Предложение по старому контексту не принимается.
- Нельзя обходить каталог прямой подстановкой таблиц или ослаблять права ради кадра.
  Ошибка каталога, binding или модели фиксируется как незавершённый этап.
- Токены, пароли и персональные данные не попадают в кадр. Профиль показывается
  безопасным именем; реквизиты подключения не снимаются.
- Завершать только READY-запуск текущей compilation. Оно сохраняет документ и
  очищает временные строки собственного демонстрационного результата.
