# Примеры тестовых сценариев SQL-конструктора

Дата подготовки: 23.10.2026. Основа: checkout `f196689d8` с существующими
локальными изменениями. Статус всех сценариев: **подготовлен, не выполнен**.
LLM, API конструктора и запросы к БД при подготовке не запускались.

Цель — проверить путь от вопроса пользователя до согласованного запроса:
правильные таблицы и поля, уточнения, смысл фильтров и соединений, сортировку,
параметры и границы возможностей. Это набор примеров, а не полная регрессия.

## Основа и условия будущей проверки

Предметная область взята из существующего набора
[`sql_query_omd.v1.json`](../../agent/business_requirements/golden_dialogs/sql_query_omd.v1.json):
поисковые запросы, результаты и метрики контекста. Ниже задан **новый синтетический
набор данных**. Он не описывает содержимое рабочей БД и не использует историческое
число строк как эталон. Ожидаемые ответы рассчитаны по этим таблицам вручную.

При будущем прогоне использовать отдельный тестовый источник и согласованный
снимок каталога. Символические имена `qa.search_queries`, `qa.search_results`,
`qa.answer_context_metrics` обозначают отношения именно этого источника.
Он пока не создан. Типы идентификаторов и значения режимов ниже — часть
синтетического контракта, а не утверждение о текущей физической схеме.

Все даты имеют тип `timestamptz`; значения ниже указаны в UTC. Октябрь —
полуинтервал `[2026-10-01 00:00:00+00, 2026-11-01 00:00:00+00)`.

Для всех положительных случаев пользователь подтверждает предложенные требования,
схему и решения. Значения фильтров и лимитов передаются отдельными параметрами.
Допустимы разные алиасы и эквивалентная форма SQL; сравнивается смысл запроса.
Порядок строк считается частью ответа там, где он задан.

Основной будущий маршрут — проверка SQL и сохранение документа без выполнения:
`SPECIFICATION_ONLY`, выполнение `NOT_EXECUTED`, без выдуманных строк результата
и аналитических выводов. Таблицы ожидаемых ответов ниже предназначены для
отдельной будущей проверки на тестовой БД; они не являются результатами прогонов.
Выполнение требует отдельного действия пользователя и разрешённого read-only
профиля. Отказ в доступе к каталогу или профилю должен останавливать соответствующий
этап, не раскрывая чужие данные.

## 1. Простая выборка из одной таблицы

**Запрос пользователя:**

> Покажи три последних поисковых запроса за всё время. Нужны только идентификатор
> и время запроса. Сначала самые новые; при одинаковом времени — меньший ID.

**Ожидается:** одна таблица, два поля, `ORDER BY created_at DESC, id ASC`,
`LIMIT 3`. Соединения и дополнительные фильтры не нужны.

**Ожидаемые ID по порядку:** `108, 107, 109`.

**Что ловим:** лимит до сортировки, обратное направление сортировки,
добавление ненужных полей или периода.

## 2. Фильтр по периоду и его границам

**Запрос пользователя:**

> Покажи ID и время всех поисковых запросов за октябрь 2026 года по UTC:
> с 1 октября включительно до 1 ноября не включительно. По времени по возрастанию,
> затем по ID. Лимит 20 строк.

**Ожидается:** `created_at >= :date_from AND created_at < :date_to`.
Лимит — верхняя граница, а не требование получить ровно 20 строк.

**Ожидаемые ID по порядку:** `102, 103, 104, 105, 106, 109, 107`.

**Что ловим:** включение 108 через `BETWEEN`, потерю 102 на нижней границе,
подмену UTC локальным временем. Вариант периода без строк должен давать пустую
выборку с сохранёнными колонками, а не ошибку или выдуманный результат.

## 3. Числовой порог, равные значения и TOP-N

**Запрос пользователя:**

> Среди результатов поиска за всё время покажи пять самых медленных с задержкой
> не меньше 1500 миллисекунд. Выведи query_id и задержку. При равной задержке
> сначала меньший query_id.

**Ожидается:** только `search_results`, фильтр `latency_ms >= :min_latency_ms`,
сортировка `latency_ms DESC, query_id ASC`, лимит 5.

| query_id | latency_ms |
| --- | --- |
| 108 | 3000 |
| 104 | 2500 |
| 105 | 2500 |
| 101 | 2000 |
| 109 | 1800 |

**Что ловим:** путаницу секунд и миллисекунд, нестабильный порядок 104/105.
При увеличении лимита до 20 строка 102 с ровно 1500 мс должна присутствовать,
а 103 с 1499 мс — отсутствовать.

## 4. Соединение двух таблиц и несколько условий

**Запрос пользователя:**

> Покажи поисковые запросы за октябрь 2026 года по UTC, у которых есть результат
> с задержкой от 1500 мс. Нужны ID, время запроса и задержка. Сначала самые
> медленные, затем меньший ID. Лимит 20.

**Ожидается:** `INNER JOIN search_results ON search_queries.id = search_results.query_id`.
Период применяется к `search_queries.created_at`; порог — к результату.

**Ожидаемые пары `(ID, задержка)` по порядку:**
`(104, 2500), (105, 2500), (109, 1800), (102, 1500)`.

**Что ловим:** неверный ключ JOIN, потерю фильтра периода, декартово произведение.
Запрос 107 исключается из-за отсутствия результата; 108 — из-за периода.

## 5. NULL отличается от нуля и отсутствующей строки

**Запрос пользователя:**

> Среди записей метрик за всё время найди те, где доля шумового контекста
> не заполнена. Выведи query_id, режим и долю шума, по query_id по возрастанию.
> Нулевую долю шума не включай. Лимит 20.

**Ожидается:** одна таблица `answer_context_metrics`, фильтр
`noise_char_share IS NULL` без параметра для NULL.

**Ожидаемый ответ:** `(104, vector, NULL)`.

**Что ловим:** `= NULL`, замену NULL на 0, включение 105. Запросы 106 и 107
не попадают: строк метрик для них вообще нет, а JOIN здесь не запрошен.

## 6. LEFT JOIN с сохранением неполных данных

**Запрос пользователя:**

> Покажи все поисковые запросы за октябрь 2026 года по UTC и их задержки,
> включая запросы без результата. Если результата нет, задержку оставь пустой.
> Выведи ID и задержку, по ID по возрастанию. Лимит 20.

**Ожидается:** `search_queries LEFT JOIN search_results` по подтверждённому FK.
Фильтр периода относится к левой таблице. Пустая задержка остаётся SQL NULL.

**Ожидаемые пары `(ID, задержка)`:**
`(102, 1500), (103, 1499), (104, 2500), (105, 2500), (106, 900), (107, NULL), (109, 1800)`.

**Что ловим:** подмену LEFT JOIN на INNER JOIN, потерю строки 107,
несогласованную замену отсутствующей задержки на 0.

## 7. Агрегация по трём таблицам

**Запрос пользователя:**

> За октябрь 2026 года по UTC сравни режимы поиска: число запросов, среднюю
> задержку в мс и среднюю долю шумового контекста. Учитывай только запросы,
> у которых есть и результат, и запись метрик. NULL в доле шума пропускай
> при расчёте среднего, но сам запрос учитывай в количестве. Сначала режим
> с большей средней задержкой, затем название режима. Лимит 20.

**Ожидается:** два INNER JOIN по `query_id`, группировка по `effective_mode`,
подсчёт запросов и два AVG. Подтверждённая уникальность `query_id` в дочерних
таблицах гарантирует одну строку на запрос до группировки.

| effective_mode | query_count | avg_latency_ms | avg_noise_char_share |
| --- | --- | --- | --- |
| vector | 2 | 2500 | 0.00 |
| hybrid | 3 | 1599.666… | 0.35 |

**Что ловим:** среднее от уже усреднённых значений, целочисленное деление,
исключение 104 из количества из-за NULL, замену NULL на 0 при AVG.
Для средней задержки hybrid допустима числовая погрешность `0.000001`.

## 8. Неоднозначная бизнес-задача с обязательными уточнениями

**Первое сообщение пользователя:**

**Ожидается до уточнения:** открытые вопросы о периоде, порогах, гранулярности,
полях и ограничении результата. Не должно появиться окончательно принятого
SQL с молча придуманными значениями.

**Ответы пользователя, передаваемые по мере уточнений:**

- Одна строка — один поисковый запрос с результатом и метриками.
- Октябрь 2026 года, UTC, полуинтервал из сценария 2.
- Медленно — `latency_ms >= 1500`; плохо — `noise_char_share >= 0.25`.
- Вывести ID, задержку, режим и долю шума; текст запроса и ответа не выводить.
- Оба INNER JOIN подтверждены. Сортировка: задержка по убыванию, затем ID.
- Лимит 20; Python-постобработка не нужна.

**Ожидаемый ответ после согласования:**

| query_id | latency_ms | effective_mode | noise_char_share |
| --- | --- | --- | --- |
| 109 | 1800 | hybrid | 0.30 |
| 102 | 1500 | hybrid | 0.25 |

**Что ловим:** автоматическое подтверждение решений агентом, пропуск одного
порога, замену AND на OR, включение NULL/нуля как «плохого» контекста.
Строка 103 проходит порог шума, но не задержки; 104 и 105 — наоборот.

## 9. Доработка запроса через CTE без изменения результата

**Предусловие:** согласованный запрос сценария 8 и сохранённая исходная ревизия.

**Комментарий пользователя к запросу:**

> Вынеси отобранные поисковые запросы за октябрь в CTE, чтобы SQL было проще
> читать. Поля, параметры, соединения, пороги, сортировку и лимит сохрани.

**Ожидается:** предложение новой ревизии с CTE и доступным сравнением.
До принятия активна исходная ревизия. После принятия история содержит обе,
а проверка SQL относится к новой ревизии. Ранее полученный результат не должен
представляться как результат выполнения новой ревизии.

**Эталон смысла:** тот же набор параметров и две строки сценария 8 в том же
порядке. Внешний LIMIT сохранён; CTE не обрезает данные перед фильтрами/JOIN.
Равенство данных в будущем проверяется отдельным исполнением обеих версий
на одном неизменном наборе, а не только сравнением текста SQL.

**Что ловим:** перезапись истории, потерю параметра, применение предложения
до согласия, устаревшую отметку проверки или результата.

**Граница возможностей:** CTE проверяется через путь комментариев и ревизий.
Наличие CTE в разборе SQL не доказывает его поддержку первичным планировщиком;
успешность этого сценария текущей подготовкой не установлена.

## 10. TOP-1 внутри каждой группы с оконной функцией

**Запрос пользователя:**

> За октябрь 2026 года по UTC найди самый медленный поисковый запрос отдельно
> для каждого режима. Учитывай только запросы с результатом и метриками.
> При равной задержке выбирай меньший ID. Выведи режим, ID и задержку;
> режимы отсортируй по имени. Итоговый лимит 20 строк.

**Целевая логика:** два INNER JOIN, фильтр периода, затем
`ROW_NUMBER() OVER (PARTITION BY effective_mode ORDER BY latency_ms DESC, query_id ASC)`
в CTE/подзапросе и отбор первой строки каждой группы. Глобальный LIMIT
применяется после отбора победителей.

| effective_mode | query_id | latency_ms |
| --- | --- | --- |
| hybrid | 109 | 1800 |
| vector | 104 | 2500 |

**Что ловим:** глобальный TOP-1 вместо одного на режим, выбор 105 при равенстве,
независимые `MAX(query_id)` и `MAX(latency_ms)`, дающие поля разных строк.

**Граница возможностей:** расширенный целевой случай. В просмотренном
`query_planning.py` нет вида SELECT для оконной функции, а allowlist функций
первичного компилятора в `query_specification.py` не содержит `ROW_NUMBER`.
Поэтому успешную сборку через текущий первичный маршрут не следует ожидать
без отдельной проверки/доработки. Если маршрут не поддерживает такую задачу,
ожидается явное ограничение, сохранение требований и отсутствие ложного
`READY/PASS`. Выключать SQLGuard ради прохождения сценария нельзя.

## Как фиксировать будущий результат

Для каждого кейса сохранять исходный вопрос, уточнения и ответы, принятый снимок
схемы, SQL с отдельными параметрами, статус проверок и версии артефактов.
Если отдельно разрешено выполнение — добавить фактические строки и сравнение
с эталоном. Для 9 и 10 отдельно отмечать поддержку выбранного маршрута;
корректный отказ по отсутствующей возможности не считать успешной сборкой SQL.

Не сравнивать текст ответа или SQL побайтно. Проверять гранулярность, источники,
условия, поля, порядок, число строк и отсутствие неподтверждённых решений.
