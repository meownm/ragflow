# UI/UX/CX конструктора SQL-запросов

Дата: 2026-09-14. Статус: целевой опыт и контракт интерфейса, не заявление о
готовности реализации. Продуктовые состояния, агрегат и режимы определены в
[продуктовой спецификации](sql-query-constructor-product-ru.md), фактическое
покрытие — в [регрессионном документе](sql-query-constructor-regression-ru.md),
а владельцы server state, API и frontend-модулей — в
[архитектуре конструктора](sql-query-constructor-architecture-ru.md).

## 1. Три тезиса дизайна

### Визуальный тезис

Спокойный аналитический workspace: нейтральные поверхности действующей темы
RAGFlow, строгая типографика, один бирюзовый акцент действия и минимум chrome.
Главным визуальным объектом является текущая работа и её доказательства, а не
набор декоративных карточек.

### План содержания

1. Ориентация: какой проект открыт, где пользователь находится и что мешает
   продолжить.
2. Работа: один этап, одна доминирующая задача и один основной CTA.
3. Доказательства: каталог, решения и трассировка раскрываются рядом с объектом,
   который они объясняют.
4. Результат: SQL, проверка, данные и документ показываются как связанные
   ревизии одного проекта.

### Тезис взаимодействия

- Переход между этапами коротко сохраняет пространственный контекст, а не
  открывает новое большое модальное окно.
- Выбор требования подсвечивает связанные таблицы, поля, SQL-фрагменты и
  проверки; обратное выделение работает из SQL к требованию.
- Панель evidence раскрывается по запросу и не конкурирует с основной задачей.
  Длительные операции показывают конкретный этап и возможность отмены.

## 2. Цель опыта

Пользователь в любой момент должен понимать четыре вещи без чтения инструкции:

1. Что именно он сейчас собирает.
2. Какое следующее действие требуется.
3. Какие решения предложила LLM, а какие подтвердил человек.
4. Почему SQL можно или нельзя сформировать/выполнить.

Критический CX-инвариант:

> Ни один экран, статус или успешная иллюстрация не должен создавать впечатление,
> что запрос выполнен, если продукт только сформировал SQL.

## 3. Диагностика текущего интерфейса

Текущий экран полезен как редактор шаблона, но не как основной рабочий путь
аналитика:

- первое пространство занято техническими параметрами шаблона;
- пользователь одновременно видит 44 раздела и инспектор выбранного раздела;
- «Схема данных» и «SQL-запрос» выглядят вспомогательными действиями;
- основной SQL-сценарий разбит между несколькими большими диалогами;
- при отсутствии snapshot SQL-диалог сообщает о необходимости схемы, но не
  предлагает перейти к её подготовке;
- несколько равнозначных кнопок в header не показывают следующего шага;
- локальное сохранение создаёт слабое ощущение устойчивого проекта.

Решение: сохранить трёхпанельный экран только в административном редакторе
шаблонов, а корневой раздел сделать списком проектов с отдельным пошаговым
workspace.

## 4. Принципы UI/UX/CX

1. **Следующий шаг важнее полной структуры.** Показывать текущий этап и
   блокеры; весь документ доступен в preview, но не навязывается при вводе.
2. **Один основной CTA.** Вторичные действия визуально спокойнее и не
   конкурируют с продолжением сценария.
3. **Карточка используется только для выбора.** Обычные данные отображаются
   строками, таблицами и разделителями, а не мозаикой карточек.
4. **Естественный язык идёт первым.** SQL-фрагмент и технический ID — второй
   слой той же сущности.
5. **Нет необъяснимо disabled-кнопок.** Рядом указывается причина и действие,
   которое снимает блокировку.
6. **Нет скрытой автоподстановки.** Предложение LLM всегда маркировано до
   подтверждения пользователя.
7. **Ошибку можно продолжить.** Ввод и подтверждённые решения сохраняются при
   сбое каталога, модели, компилятора, БД или Python.
8. **Технические названия переводятся.** В основном UX используются понятные
   русские термины; внутренний код доступен во вторичной подписи.
9. **Права fail-closed.** Административные и создающие действия отображаются
   только при точном положительном capability, а не до загрузки прав.
10. **Доступность является частью контракта.** Цвет, hover и мышь не должны быть
    единственным способом понять или выполнить действие.

## 5. Сквозной путь клиента

| Момент | Цель пользователя | Основная поверхность | Успешный результат | Главный риск CX |
| --- | --- | --- | --- | --- |
| Вход | Найти или начать запрос | Список проектов | Понятен следующий проект/CTA | Попасть в редактор шаблона вместо рабочего сценария |
| Постановка задачи | Зафиксировать, что нужно получить | Требования | Принята атомарная ревизия | LLM переписала смысл или спрятала неоднозначность |
| Выбор данных | Понять, где лежат сущности | Данные + evidence | READY snapshot | Выбрать первую похожую таблицу без понимания гранулярности |
| Сборка запроса | Описать вывод, JOIN и фильтры | Структурированный query builder | Все clauses подтверждены | Перегрузиться SQL-деталями или потерять связь с требованиями |
| Проверка | Убедиться в полноте и безопасности | Coverage + SQL | SQLGuard PASS | Принять красивый SQL за доказательство соответствия задаче |
| Выполнение | Получить ограниченный результат | Preflight + run | ResultGate PASS | Не увидеть профиль, лимиты, truncation или реальный статус |
| Постобработка | Выполнить только необходимое преобразование | Result tabs + Python plan | Производный результат с lineage | Потерять raw result или дать Python доступ к источнику |
| Завершение | Передать проверяемый документ | Document preview | Immutable revision/export | Получить документ без открытых вопросов и статусов этапов |
| Возврат | Продолжить или повторить работу | Список + история | Понятна актуальная ревизия | Перезаписать результат старой вкладкой или не понять stale |

## 6. Информационная архитектура и навигация

### 6.1 Корневой раздел

В глобальной навигации остаётся один пункт «Конструктор». Он открывает проекты,
а не конкретный шаблон.

Внутренние вкладки раздела:

- `Проекты` — по умолчанию;
- `Шаблоны` — только при capability просмотра/управления шаблонами;
- `Источники SQL` — только superuser/администратору реестра.

Не смешивать административные вкладки с этапами проекта. Пользователь не должен
видеть «connector», «binding» или настройки лимитов до контекста выполнения.

### 6.2 Список проектов

Используется плотная таблица, а не dashboard-card mosaic.

```text
Конструктор SQL                                      [Новый SQL-запрос]
Создавайте проверяемые запросы из требований и данных каталога

[Активные 12] [Нужно решение 3] [Готовые 7] [Архив]     [Поиск        ]
────────────────────────────────────────────────────────────────────────────
Проект                    Статус          Следующий шаг   Источник  Обновлён
Медленные ответы          Нужно решение  Выбрать таблицу  bot       12 мин
Продажи по статусам       Готов SQL       Выполнить        dwh       вчера
Аномалии по месяцам       Документ готов  Открыть документ dwh       12.09
```

Колонки:

- название и короткая цель;
- статус с иконкой и текстом;
- следующее действие;
- безопасное имя catalog/data source, без connector secrets;
- автор для разрешённого командного просмотра;
- время последнего изменения;
- контекстное меню: открыть, дублировать, архивировать.

Строка целиком открывает проект. Отдельный CTA в строке не дублирует переход,
если не выполняет другое действие.

### 6.3 Пустое состояние

```text
Здесь появятся проекты SQL-запросов
Опишите нужный результат — конструктор поможет сопоставить сущности с каталогом,
уточнить условия и собрать проверяемый SQL.

[Создать первый запрос]   [Открыть демонстрационный пример]
```

Демонстрационный пример read-only, не создаёт записи и ясно помечен как пример.
Если `capabilities.create !== true`, creation CTA и весь ввод создания не
отображаются; остаётся доступный пользователю список.

## 7. Создание проекта

Создание минимально. Не спрашивать технический код, heading level, версию
шаблона и execution profile до появления необходимости.

```text
Новый SQL-запрос

Что вы хотите получить?
┌──────────────────────────────────────────────────────────────┐
│ Покажи по месяцам сумму оплаченных заказов корпоративных...  │
└──────────────────────────────────────────────────────────────┘

Название проекта                    [создаётся автоматически]
Источник знаний                     [Основной каталог ▾]

Дополнительные настройки ▸

[Отмена]                                    [Создать и разобрать требования]
```

Правила:

- название предлагается по исходному тексту, но остаётся редактируемым;
- выбирается опубликованный default template;
- режим определяется capability: compile-only по умолчанию, выполнение
  включается только при подтверждённой доступности;
- advanced settings раскрывают template version и dataset scope, но не
  connector secrets;
- после submit проект создаётся до вызова LLM, поэтому сбой модели не теряет
  ввод.

## 8. Каркас рабочего пространства

### 8.1 Desktop-композиция

```text
Конструктор / Медленные ответы      Нужно 2 решения     Сохранено 14:32   [⋯]
────────────────────────────────────────────────────────────────────────────
│  1 Требования  ✓ │                                                     │
│  2 Данные      2 │   Данные                                            │
│  3 Запрос      · │   Сопоставьте сущности с физическими таблицами       │
│  4 Проверка    · │                                                     │
│  5 Результат   · │   [Сводка snapshot и блокеров]                       │
│  6 Документ    · │   [Основная рабочая область]                         │
│                  │                                                     │
│  Открытые вопросы│                                                     │
│  • Заказ: 2 варианта                                                    │
────────────────────────────────────────────────────────────────────────────
│ [Назад]        Черновик сохранён          [Перейти к первому блокеру]    │
```

Постоянные области:

- **Project header:** breadcrumb, название, производный статус, autosave,
  history и спокойное overflow-меню.
- **Stepper:** этапы, завершённость и число блокеров; ширина около 240–280 px на
  большом экране.
- **Workspace:** гибкая центральная область без фиксированного узкого
  max-width для таблиц/SQL.
- **Evidence inspector:** 320–400 px, появляется справа при выборе сущности и
  не открыт постоянно без необходимости.
- **Action bar:** sticky-низ с `Назад`, состоянием сохранения и одним primary
  action.

Header глобального приложения и project header вместе не должны съедать первый
экран: название, статус и начало текущего этапа видны без прокрутки.

### 8.2 Поведение stepper

- Завершённый этап — check и короткая сводка при hover/focus.
- Текущий — бирюзовый marker и видимый заголовок.
- Этап с blocker — amber icon и количество.
- Stale — отдельная иконка обновления и действие `Перепроверить`.
- Будущий этап доступен для просмотра summary, но primary action объясняет
  незакрытые зависимости.
- Кнопка `Перейти к первому блокеру` перемещает фокус к конкретному полю/решению.

## 9. Этап «Требования»

### 9.1 Структура экрана

```text
Требования                                      10 принято · 2 требуют ответа
Зафиксируйте ожидаемый результат до выбора таблиц

Исходная формулировка                                             [Изменить]
Покажи, какие поисковые ответы были медленными и плохо...

Уточняющие вопросы
! Что считать «медленно»?
  (•) не менее [1500] [мс ▾]     ( ) другое правило
  [Подтвердить ответ]

Реестр требований                                     [Только нерешённые ▾]
REQ-001  Одна строка на поисковый запрос       Гранулярность  Подтверждено
REQ-002  latency_ms не менее 1500              Фильтр         Предложено LLM
REQ-003  Не выводить query и answer             Приватность    Подтверждено

[+ Добавить требование]
```

### 9.2 Поведение

- Исходный текст показан отдельно от разложения и не переписывается LLM.
- Каждая proposed-строка имеет `Принять`, `Изменить`, `Отклонить` в
  контекстных действиях.
- В строке сначала показываются `REQ-*`, формулировка и тип; технические ссылки
  скрыты в inspector.
- Вопросы расположены над реестром, поскольку именно они блокируют этап.
- Нельзя отвечать на вопрос неявным изменением SQL-формы на следующем экране.
- Массовое принятие допустимо только для явно выбранных неблокирующих
  предложений; система показывает количество и не включает неоднозначности.
- Изменение принятой ревизии открывает режим `Новая редакция` и заранее
  объясняет, какие downstream-этапы потребуют перепроверки.

Основной CTA:

- `Согласовать требования`, если блокеров нет;
- `Ответить на 2 вопроса`, если они есть;
- `Продолжить вручную`, если LLM недоступна.

## 10. Этап «Данные»

### 10.1 Сводка snapshot

Верхняя строка показывает:

```text
Основной каталог · обновлено 4 мин назад · 3 таблицы · 18 выбранных полей
[ER-диаграмма] [Обновить snapshot]
```

Fingerprint, catalog versions и технический FQN доступны в inspector, но не
доминируют в рабочей области.

### 10.2 Карта сопоставлений

```text
Сущность / требование      Выбранный объект             Состояние
Заказ                      dwh.order_fact                Подтверждено
Клиент                     dwh.customer_dim              Подтверждено
Статус                     2 варианта                    Нужно решение
Оплаченная сумма           paid_amount_rub               Подтверждено
```

Выбор строки раскрывает варианты. Карточки используются здесь, потому что
являются взаимоисключающим выбором:

```text
Статус заказа — выберите таблицу

( ) ref.order_status                         Рекомендуется
    Одна строка на статус · PK status_id
    Содержит status_code и status_name_ru
    Источник: OpenMetadata · актуально

( ) dwh.order_event_fact
    Одна строка на изменение статуса
    Может размножить строки заказа

[Ничего не подходит]                          [Подтвердить выбор]
```

Не показывать рейтинг как `93%`, если нет калиброванной вероятности. Объяснение
гранулярности и последствий важнее confidence badge.

### 10.3 Поля и ER-диаграмма

- Поля загружаются только после выбора таблицы.
- В таблице полей: business name, technical name, type, description, key/null,
  связанные требования и checkbox выбора.
- Поиск работает по business/technical names и описанию.
- `Показать только выбранные` помогает проверить scope.
- ER-диаграмма открывается в крупном рабочем canvas или side sheet, а не в
  маленькой карточке.
- Клик по таблице/связи в ERD выделяет соответствующую строку и evidence.
- Ошибка рендеринга Mermaid/PlantUML не блокирует этап: сохраняется и
  показывается исходный код диаграммы с доступным alert.

Основной CTA: `Подтвердить данные` либо `Решить 1 неоднозначность`.

## 11. Этап «Запрос»

Внутри этапа используются четыре вкладки с последовательным индикатором:

`Вывод` → `Соединения` → `Фильтры` → `Сортировка и лимит`.

Это подэтапы одного query specification, а не четыре самостоятельных маршрута.
На каждой вкладке видны число покрытых требований и следующая неполная запись.

### 11.1 Вывод

Плотная таблица:

| Поле результата | Источник | Преобразование | Алиас | Требование | Статус |
| --- | --- | --- | --- | --- | --- |
| Месяц | `o.created_at` | month bucket | `month` | REQ-004 | Подтверждено |
| Оплаченная сумма | `o.paid_amount_rub` | SUM | `paid_amount_rub` | REQ-005 | Предложено LLM |

Строки можно добавлять, удалять и упорядочивать явными controls. Drag-and-drop
не является единственным способом изменить порядок.

### 11.2 Соединения

Каждый JOIN показан одной строкой естественного смысла и раскрываемыми
техническими деталями:

```text
Клиент заказа
dwh.order_fact.customer_id = dwh.customer_dim.customer_id
INNER JOIN · многие к одному · неполные заказы будут исключены
REQ-006                                            [Подтвердить]
```

Предупреждения:

- `Возможное размножение строк`;
- `Кардинальность неизвестна`;
- `LEFT JOIN сохранит строки без справочника`;
- `Есть другой путь соединения`.

Тип JOIN подтверждается вместе с бизнес-последствием, а не отдельным
техническим select без объяснения.

### 11.3 Фильтры

Каждое WHERE-условие — отдельная раскрываемая карточка выбора, но список
остаётся компактным:

```text
REQ-009 · Медленные ответы не менее 1500 мс        Нужно подтверждение
Поле              latency_ms
Условие            больше или равно
Параметр           :min_latency_ms · integer · 1500
NULL               строки с NULL не проходят
SQL после compile  q.latency_ms >= :min_latency_ms
Evidence           OpenMetadata / latency_ms
                                      [Изменить] [Подтвердить]
```

Естественное описание всегда находится выше SQL. Значения дат редактируются
как период с timezone и визуализацией полуинтервала, а не двумя несвязанными
текстовыми полями.

Для `IN` показывается количество элементов и лимит, а чувствительные значения
могут быть скрыты. Boolean groups появляются только после поддержки capability;
нельзя отображать неработающий OR-builder как обычную возможность.

### 11.4 Сортировка и лимит

- ORDER BY показывается в приоритетном порядке и объясняет
  детерминированность.
- LIMIT имеет рекомендованное значение профиля и не допускает превышение policy.
- Pagination скрыта/помечена недоступной, пока её контракт не реализован.
- Формат, алиасы, единицы и округление проверяются здесь же.

Основной CTA этапа: `Сформировать и проверить SQL`.

## 12. Этап «Проверка»

### 12.1 Композиция

```text
Проверка запроса                              12/12 требований покрыто

Покрытие требований            │ SQL
✓ REQ-001 Гранулярность         │ SELECT ...
✓ REQ-005 Оплаченная сумма      │ FROM ...
✓ REQ-009 latency >= 1500       │ WHERE ...
────────────────────────────────┼────────────────────────────────
Параметры · Проверка SQL · Профиль выполнения

[Вернуться к запросу]                   [Выполнить read-only запрос]
```

Левая область содержит coverage matrix и группируется по статусам: сначала
blockers, затем warnings, затем verified. Правая — syntax-highlighted SQL с
копированием и отдельной таблицей параметров.

Выбор `REQ-*` подсвечивает связанные строки SQL. Выбор строки SQL показывает
требование, catalog evidence и решение пользователя. Если точное line mapping
недоступно, подсвечивается clause, а не создаётся ложная точность.

### 12.2 Проверки и CTA

Проверка SQL показывается понятными строками:

- `Одна read-only инструкция`;
- `Нет SELECT *`;
- `Все таблицы и поля входят в snapshot`;
- `Параметры отделены от SQL`;
- `ORDER BY и LIMIT заданы`;
- `Профиль выполнения найден` или `Выполнение недоступно`.

Не использовать один зелёный badge `PASS` без расшифровки.

Основной CTA зависит от режима:

- `Собрать документ` — в compile-only;
- `Выполнить read-only запрос` — при валидном binding;
- `Исправить 2 блокера` — если продолжение запрещено.

Вторичное действие `Собрать документ без выполнения` доступно автору при
недоступном execution profile и создаёт честный `NOT_EXECUTED`.

## 13. Предварительная проверка выполнения

Read-only запрос может быть дорогим, поэтому перед первым запуском показывается
inline preflight, а не внезапный запуск из меню:

```text
Перед выполнением
Профиль: OMD bot PostgreSQL RO
Таблицы: public.search_queries, public.search_results
Параметры: 4
Timeout: 15 секунд · максимум 1000 строк · 5 МБ

✓ Snapshot актуален
✓ Права и подключение проверены
✓ SQL прошёл проверку

[Назад]                              [Выполнить read-only запрос]
```

Если доступен только один профиль, пользователь не делает лишний выбор. Если
совместимых профилей несколько, отображаются только безопасные названия,
политики и область; connector identity и secrets отсутствуют.

## 14. Выполнение и результат

### 14.1 Операция

Во время выполнения отображается конкретный прогресс:

```text
Выполняется · 00:07                                      [Отменить]
✓ Проверены права и версии
✓ Открыта read-only транзакция
● Выполняется запрос
○ Проверяется результат
```

Не показывать бесконечный spinner без текущей стадии, elapsed time и cancel.
После отмены UI ждёт подтверждённый terminal status; закрытие вкладки не
выдаётся за отмену операции.

### 14.2 Результат

Верхняя строка использует компактные значения без карточной мозаики:

```text
35 строк   8 колонок   42 КБ   1,8 с   Полный результат   Проверка пройдена
```

Далее:

- вкладки `Исходный результат`, `Обогащённый`, `Python`, `История запусков`;
- data grid с sticky header, column type, NULL и горизонтальной прокруткой;
- видимый признак truncation и причина ограничения;
- предупреждения ResultGate над таблицей;
- кнопка скачивания результата только по действующей политике;
- выбор строки не раскрывает технический payload, исключённый privacy rules.

Raw result всегда первая и неизменяемая вкладка. Производные вкладки содержат
lineage и ссылку на исходный `run_id`.

### 14.3 Ошибки

- Timeout: `Запрос остановлен по лимиту 15 секунд. SQL и параметры сохранены.`
- Cancel: `Выполнение отменено. Успешный результат не создан.`
- ResultGate: `Результат получен, но не прошёл проверку: обнаружена лишняя
  колонка user_id.`
- Connection: `Источник временно недоступен. Проект и SQL сохранены.`

В каждом сообщении есть следующее безопасное действие: изменить запрос,
повторить preflight, собрать документ без выполнения или обратиться к
администратору с диагностическим ID.

## 15. Дополнительные данные для ID

Если справочник известен до запуска, lookup остаётся в подэтапе «Соединения».
После результата продукт не добавляет JOIN молча.

Баннер над raw result:

```text
В колонке status_id найдено 4 значения без расшифровки
Можно запросить названия из ref.order_status. Исходный результат не изменится.
[Не требуется]                         [Подготовить дополнительный запрос]
```

Дальше открывается компактный отдельный цикл с шагами:

1. Причина и связанные IDs — значения по умолчанию скрыты, показано количество.
2. Справочник, ключ и ожидаемое название с evidence.
3. SQL, параметры, лимит и SQLGuard.
4. Подтверждение и выполнение.
5. Проверка уникальности ключа и preview обогащённого результата.

В интерфейсе явно написано: `Создаётся производный результат; исходный набор
останется доступным`.

## 16. Python-постобработка

Вкладка Python по умолчанию показывает решение, а не редактор кода:

```text
Постобработка не настроена
Используйте Python только для преобразований, которые нельзя надёжно выполнить
в SQL. Код получит копию проверенного результата без доступа к БД и сети.

[Описать преобразование]
```

Порядок UX:

1. Пользователь описывает ожидаемое преобразование.
2. LLM предлагает линейный plan, входную/выходную схему и проверки.
3. Пользователь подтверждает plan.
4. Код показывается отдельно и остаётся `draft_only`, если sandbox недоступен.
5. При доступном sandbox показываются ресурсы/timeout и отдельный запуск.
6. ResultGate проверяет `result_df`; результат появляется отдельной вкладкой.

Кнопка никогда не называется просто `Запустить`. Использовать
`Запустить изолированную постобработку`.

Ошибка Python показывается как degraded-состояние этой вкладки; верхний статус
raw SQL result остаётся успешным.

## 17. Этап «Документ»

### 17.1 Preview

Preview занимает основную ширину. Слева остаётся product stepper; outline 44
разделов открывается отдельной панелью внутри документа и имеет поиск по номеру
или названию.

Статусы разделов:

- `Готов`;
- `Нужно решение`;
- `Не применимо` с причиной;
- `Не выполнялось`;
- `Требуется перепроверка`.

Фильтр `Показать проблемы` выводит только BLOCKED/STALE. Счётчик вида
`42 готовы · 1 не применим · 1 требует решения` информативнее общего процента.

### 17.2 Редактирование

- Канонические mappings, SQL, parameters, checks, run metadata и lineage имеют
  lock и не редактируются как текст.
- Для пояснений доступно `Добавить комментарий автора` рядом с разделом.
- Изменение канонического факта ведёт на owning stage через `Изменить источник`,
  создаёт новую ревизию и пересобирает документ.
- Generator instructions видны администратору шаблона, но не попадают в
  пользовательский документ.

### 17.3 Завершение

Перед созданием ревизии показывается короткая сводка:

```text
Готово к завершению
12/12 требований проверены
SQLGuard: пройден
Выполнение: не выполнялось / результат проверен
Python: выключен / выполнен / ошибка с сохранённым raw result

[Вернуться к проблемам]                 [Создать ревизию документа]
```

После успеха — спокойный confirmation state без confetti: номер ревизии, время,
author, доступные экспорты и действия `Открыть`, `Скачать`, `Передать на ревью`.

## 18. Редактор шаблонов

Текущий трёхпанельный паттерн подходит этому административному режиму после
разделения контекстов.

Изменения:

- header: `Шаблоны / Пошаговое проектирование SQL · v1.2.0 · Черновик`;
- убрать действия «Схема данных» и «SQL-запрос»;
- основные действия: `Предпросмотр`, `Проверить`, `Опубликовать`; import/export
  находятся в overflow;
- список 44 разделов получает поиск и фильтры `Обязательные`, `С ошибками`,
  `Без источника`, `Python`;
- right inspector остаётся для выбранного раздела;
- на ширине до 1440 inspector становится drawer, чтобы центральная структура не
  сжималась;
- template preview показывает completion rules и generator instructions в
  режиме `Метаданные шаблона`, но не смешивает их с видом будущего документа;
- опубликованная версия read-only; CTA `Создать новую версию`.

Публикация открывает validation summary, а не просто success toast. Ошибка
показывает раздел и позволяет перейти к нему.

## 19. Администрирование SQL-источников

Отдельная страница содержит три вкладки:

- `Подключения` — технические connectors и health;
- `Профили выполнения` — dialect, read-only policy и лимиты;
- `Сопоставления каталога` — catalog scope → profile/physical schema.

Таблицы предпочтительнее карточек. Секрет отображается только как
`Настроен`/`Не настроен`; чтение сохранённого значения невозможно.

Создание профиля — короткий guided flow:

1. Выбрать connector.
2. Задать dialect, allowlist и ресурсные лимиты.
3. Проверить summary и сохранить versioned policy.

Bindings редактируются отдельно, чтобы profile не превращался в смешанный
объект. Деактивация предупреждает, сколько активных проектов потеряют будущую
возможность run, но не удаляет их compilations/documents.

## 20. Язык интерфейса

### 20.1 Термины

| Внутренний термин | Основная русская подпись | Дополнительное пояснение |
| --- | --- | --- |
| QueryProject | Проект запроса | Один путь от требований до документа |
| Requirement | Требование | Проверяемая часть исходной задачи |
| Decision | Решение | Выбор пользователя при неоднозначности |
| Schema snapshot | Снимок схемы | Зафиксированные таблицы, поля и связи каталога |
| Query specification | Структура запроса | Вывод, соединения, фильтры и ограничения |
| SQLGuard | Проверка SQL | Read-only и catalog-bound проверки |
| Execution profile | Профиль выполнения | Разрешённый источник и лимиты |
| Binding | Подключение для выполнения | Сопоставление каталога с профилем |
| ResultGate | Проверка результата | Схема, объём, типы и безопасность результата |
| AdditionalDataRequest | Дополнительный запрос данных | Отдельный согласуемый lookup после результата |
| Python sandbox | Изолированная постобработка | Python без БД, сети и секретов |
| Stale | Требуется перепроверка | Источник изменился после подтверждения |

Техническое название можно показать мелкой вторичной подписью в admin/evidence,
но не использовать как единственный label.

### 20.2 Основные действия

Использовать глагол и ожидаемый результат:

- `Создать SQL-запрос`;
- `Разобрать требования`;
- `Подтвердить данные`;
- `Сформировать и проверить SQL`;
- `Выполнить read-only запрос`;
- `Подготовить дополнительный запрос`;
- `Запустить изолированную постобработку`;
- `Создать ревизию документа`.

Избегать общих `Применить`, `Продолжить`, `ОК`, когда действие меняет состояние.

### 20.3 Сообщения о блокировке

Формула текста: причина → сохранённое состояние → следующее действие.

- `Схема ещё не подготовлена. Введённые требования сохранены.`
  `[Подготовить снимок схемы]`
- `Не подтверждены 2 условия фильтрации. SQL пока не сформирован.`
  `[Перейти к условиям]`
- `Каталог временно недоступен. Выбранные решения сохранены.` `[Повторить]`
- `Модель не ответила. Можно продолжить с вариантами каталога вручную.`
  `[Продолжить вручную]`
- `Профиль выполнения не найден. SQL можно завершить без запуска.`
  `[Собрать документ без выполнения]`

Не выводить пользователю только `500`, stack trace или внутреннее имя exception.
Диагностический ID доступен в раскрываемой строке `Технические сведения`.

## 21. Визуальная система

### 21.1 Поверхности и цвет

- использовать существующие light/dark tokens RAGFlow;
- один action accent — действующий бирюзовый/teal;
- semantic colors ограничены состояниями: amber — решение/предупреждение,
  red — blocker/error, green — подтверждённый success, neutral — draft;
- цвет всегда сопровождается иконкой и текстом;
- разделители и изменение фонового тона предпочтительнее рамки вокруг каждого
  блока;
- градиенты, glow и декоративные dashboard tiles не используются.

### 21.2 Типографика и плотность

- один действующий product sans и monospace для SQL/FQN/IDs;
- заголовок экрана 22–26 px, этапа 18–22 px, основной текст 14 px,
  метаданные 12–13 px с достаточным contrast;
- строки рабочих таблиц примерно 44–52 px, с более плотным admin-режимом;
- формулировка требования переносится, технический ID не отнимает основную
  ширину;
- long FQN имеет middle ellipsis и полное значение по focus/tooltip/copy.

### 21.3 Иконки

Иконка используется для статуса или действия, а не как украшение. Иконки без
подписи допустимы только для общепринятых вторичных действий с accessible name:
copy, more, close. Основной CTA всегда имеет текст.

## 22. Motion и обратная связь

Motion короткий, функциональный и использует существующий стек. Новая тяжёлая
анимационная зависимость только ради этих эффектов не нужна.

1. Переход этапа: fade/translate 120–180 ms, сохраняющий положение header и
   stepper.
2. Cross-highlight requirement ↔ clause: одно мягкое выделение до 400 ms, затем
   стабильный selected state.
3. Evidence drawer: 160–200 ms с сохранением focus и возвратом его в вызвавший
   элемент при закрытии.

Autosave не вызывает toast на каждую запись: меняется компактный статус в
header. Toast используется для редкого завершённого события или ошибки.

При `prefers-reduced-motion` переходы отключаются без потери feedback. Никаких
постоянно пульсирующих badges и декоративных фоновых анимаций.

## 23. Responsive-поведение

| Ширина | Поведение |
| --- | --- |
| `>= 1440` | Stepper + workspace + optional evidence inspector |
| `1024–1439` | Stepper + workspace; evidence открывается drawer; template inspector также drawer |
| `768–1023` | Stepper сворачивается в горизонтальный progress/header; таблицы используют управляемую горизонтальную прокрутку |
| `< 768` | Безопасный review mode: статус, требования, простые решения, SQL/document preview и комментарии; сложное редактирование mapping/query явно предлагает desktop, а не исчезает |

MVP оптимизируется для desktop authoring от 1280 px. Mobile review mode является
честной границей первого выпуска; capability не должна молча скрываться только
из-за viewport.

## 24. Доступность

- WCAG AA contrast для текста, controls и selected/focus states;
- логичный heading outline и landmarks `nav`, `main`, `aside`;
- stepper и tabs доступны клавиатурой и объявляют текущий/завершённый статус;
- после ошибки focus переходит в summary, ссылки ведут к конкретным полям;
- динамические autosave/run statuses используют ненавязчивый `aria-live`;
- option cards являются radio group, а не div с click handler;
- таблицы имеют headers, accessible names и отдельные controls изменения
  порядка;
- code block поддерживает keyboard selection/copy и не кодирует связь только
  цветом;
- touch targets не менее 44 px в compact/mobile режимах;
- диаграмма имеет текстовое описание и исходный код fallback;
- zoom 200% не скрывает основные действия за фиксированными панелями.

## 25. CX доверия и объяснимости

Три источника решений визуально различаются:

| Источник | Маркер | Что означает |
| --- | --- | --- |
| Пользователь | `Подтверждено вами` | Решение вошло в принятую ревизию |
| Каталог | `Проверено каталогом` | Факт имеет catalog/version/evidence |
| LLM | `Предложено LLM` | Черновик, не закрывающий gate |

Интерфейс отвечает на `Почему?` рядом с решением:

- почему предложена таблица;
- почему выбран тип JOIN;
- какое требование создаёт фильтр;
- почему SQL заблокирован;
- почему snapshot стал stale;
- почему результат усечён или отклонён;
- почему Python недоступен.

Не использовать anthropomorphic copy вроде «Я решил» от имени LLM. Формулировки
нейтральные: `Модель предложила`, `Каталог подтвердил`, `Вы выбрали`.

## 26. CX совместной работы

MVP переиспользует существующие права и ревизии Business Documents, не создавая
вторую систему комментариев.

- Автор передаёт конкретную revision на ревью.
- Ревьюер видит тот же snapshot, requirements, decisions, SQL и statuses.
- Комментарий привязывается к `REQ-*`, clause или разделу документа.
- Изменение после комментария создаёт новую ревизию; старая ссылка остаётся
  воспроизводимой.
- Conflict старой вкладки показывает автора и время новой версии и предлагает
  `Перезагрузить`/`Скопировать несохранённый текст`, но не silent overwrite.
- История показывает значимые решения, а не каждый autosave keystroke.

Дублирование проекта создаёт новый `project_id`, копирует требования и
структуру, но требует повторной freshness/binding проверки перед compile/run.

## 27. CX поддержки и восстановления

Каждая внешняя зависимость имеет продуктовый fallback:

| Сбой | Что сохраняется | Действия пользователя |
| --- | --- | --- |
| LLM | Исходный текст, catalog evidence, принятые решения | Продолжить вручную или повторить |
| OpenMetadata | Ввод и предыдущий snapshot как stale | Повторить; открыть предыдущие доказательства; не выполнять |
| Binding registry | SQL и compile-only document | Повторить preflight или завершить без выполнения |
| PostgreSQL | Compilation и параметры | Повторить новый run; изменить запрос; собрать документ |
| ResultGate | Run diagnostics и закрытый technical artifact | Исправить спецификацию; обратиться по diagnostic ID |
| Python | Raw result | Изменить plan; повторить; завершить без постобработки |
| Diagram renderer | Исходный Mermaid/PlantUML | Посмотреть/copy source; документ не блокируется только рендером |

Support-copy не предлагает действия, которых у пользователя нет. Например,
автору без admin capability показывается `Обратиться к администратору` и
diagnostic ID, а не ссылка на закрытый registry.

## 28. Service blueprint

| Этап | Действие пользователя | UI | Application owner | Recovery evidence |
| --- | --- | --- | --- | --- |
| Создание | Отправляет исходную задачу | Создаёт project до AI | Query lifecycle | project ID и сохранённый source text |
| Требования | Принимает/редактирует REQ | Decision/requirement list | Requirements owner + LLM adapter | revision, prompt/model hash без raw secret data |
| Данные | Выбирает catalog objects | Mapping + evidence | Schema resolution | snapshot version/fingerprint/freshness |
| Запрос | Подтверждает clauses | Structured builder | Query specification/planner | spec revision и decision refs |
| Проверка | Просматривает coverage/SQL | Split coverage/SQL | Compiler + SQLGuard | compilation ID и checks |
| Preflight | Подтверждает run policy | Profile/limits summary | Registry resolver | binding/profile versions |
| Выполнение | Запускает/отменяет | Progress + cancel | Executor port | operation/run ID и terminal state |
| Результат | Проверяет таблицу | Raw/enriched tabs | ResultGate | raw result ID, checks, lineage |
| Python | Подтверждает plan/run | Plan/code/result | Python port | plan/run IDs, resource/cleanup status |
| Документ | Создаёт ревизию | Preview + blockers | DocumentAssembler | immutable document revision |

## 29. Телеметрия опыта

Не передавать в аналитику исходные требования, SQL, parameter values, result
cells, FQN с чувствительным контекстом или LLM prompt.

События содержат IDs, counts, enum statuses и durations:

- `constructor_project_created`;
- `constructor_stage_viewed/completed`;
- `constructor_blocker_opened/resolved`;
- `constructor_llm_fallback_used`;
- `constructor_snapshot_ready/stale`;
- `constructor_query_compiled/blocked`;
- `constructor_execution_started/cancelled/finished`;
- `constructor_result_gate_failed`;
- `constructor_document_revision_created`.

Основные UX-метрики после baseline:

- доля пользователей, нашедших следующий шаг без возврата/ошибочного клика;
- время и число возвратов до первого SQLGuard PASS;
- доля проектов, брошенных на каждой стадии;
- число неоднозначностей и доля разрешённых без поддержки;
- доля compile-only, ошибочно интерпретированных как executed по исследованию;
- восстановление незавершённого проекта после reload;
- число conflicts/stale и успешное восстановление;
- завершение документа без внешней ручной правки SQL.

## 30. План usability-проверки

До стабилизации визуальных деталей провести модерируемый тест минимум на трёх
типах пользователей: аналитики, data engineers/владельцы каталога и ревьюеры.
Использовать синтетическую одноразовую схему без рабочих данных.

Задания:

1. Создать запрос из расплывчатого требования и определить следующий шаг.
2. Выбрать между fact/event таблицами и объяснить последствия.
3. Настроить отдельные WHERE-условия и найти их SQL-фрагменты.
4. Понять, был ли запрос выполнен или только скомпилирован.
5. Восстановиться после LLM failure и stale snapshot.
6. Расшифровать неизвестные ID отдельным дополнительным запросом.
7. Найти raw result после ошибки Python.
8. Передать ревизию на проверку и определить незакрытый blocker.

Критерии первой проверки:

- участник без подсказки находит основной CTA каждого этапа;
- никто не принимает LLM proposal за подтверждённый факт;
- никто не считает compile-only статус фактом выполнения;
- таблица-кандидат выбирается на основании гранулярности/evidence, а не позиции;
- после ошибки участник находит сохранённый результат и безопасное действие;
- критические блокеры доступности и потери данных отсутствуют.

Процентные продуктовые цели задаются после первого baseline, а не подгоняются
под малую исследовательскую выборку.

## 32. Инкременты UI/UX

### UX1. Разделить персоны

- корень → список проектов;
- текущий экран → `/templates/:id`;
- registry → admin route;
- fail-closed navigation/capabilities.

### UX2. Создать каркас проекта

- project header, stepper, workspace, evidence drawer и sticky action bar;
- server autosave/conflict;
- empty/loading/error states.

### UX3. Требования и данные

- atomic requirements, inline questions, decision cards;
- mapping table, field selector, ERD и snapshot summary;
- cross-highlighting с evidence.

### UX4. Query builder и проверка

- четыре подэтапа;
- natural-language-first JOIN/WHERE;
- coverage ↔ SQL view;
- capability-aware CTA и compile-only completion.

### UX5. Выполнение и результат

- preflight, bounded progress/cancel;
- raw/result gate/history;
- additional-data cycle.

### UX6. Python и документ

- plan-first Python UX и degraded fallback;
- canonical document preview, annotations и immutable revision.

Каждый инкремент включает light/dark, desktop/compact, keyboard, loading,
empty, error, stale и permission states. Не откладывать эти состояния до
финальной полировки.

## 33. Definition of Done UI/UX/CX

- Корневой раздел открывает проекты, а не template editor.
- Новый пользователь понимает основной CTA и безопасные границы без инструкции.
- На каждом этапе ровно одно визуально доминирующее действие.
- Основной SQL-путь не требует цепочки больших модальных окон.
- LLM proposal, catalog fact и user confirmation различимы текстом, не только
  цветом.
- Каждый blocker имеет причину и deep-link к исправлению.
- Требование можно проследить до данных, clause, проверки и документа в обе
  стороны.
- Compile-only, execution, truncation, degraded и not-executed невозможно
  спутать по тексту статуса.
- Reload/conflict/stale сохраняют работу и понятное восстановление.
- Основной путь работает с клавиатуры, focus/error summary проверены,
  reduced-motion соблюдён.
- Нет административных действий до подтверждённой capability.
- UI использует текущую дизайн-систему RAGFlow без нового параллельного набора
  primitives и без decorative card grid.
- UX-01…16 имеют автоматическое покрытие на подходящем уровне, а runtime-cases
  не объявляются пройденными по route mocks.

Классификация будущей реализации: собственный frontend
`web/src/pages/business-documents/constructor` и минимальные изменения общих
routes/navigation; server-side состояния и capability остаются у владельца
`business_documents`. Массовое изменение общего layout или новая дизайн-система
не требуются.
