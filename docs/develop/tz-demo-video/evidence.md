# Доказательства живого прохождения и будущей записи

## Что доказывается

Запись экрана подтверждает действия и видимый результат. Снимки документа подтверждают сохранённый текст; отдельный сетевой след подтверждает обращение к реальному серверу. Успех провайдера модели подтверждается доступной штатной телеметрией фактического upstream-вызова, а не только POST чата. Если такой связи нет, писать «UI и backend подтверждены, upstream не подтверждён». Присутствие в репозитории кода не подтверждает версию работающего приложения.

БТ — основание содержания; эти документы описывают будущую CSV-функцию. Никакая запись редактора не доказывает выполнение POST /demo/v1, идемпотентность будущего CSV-сервера или отсутствие дублей в его реальной БД. В дикторском тексте говорить «правило описано/проверено в ТЗ», а не «мы загрузили CSV без дублей».

## Журнал событий

Копировать session-template.json в evidence-каталог одного run. Для каждого события заполнять: episode, timestamp_utc, runtime_source_id, workspace/document_id, request_id/attempt_id при наличии, метод и path без query-секретов, HTTP, before_revision, after_revision, before_version/after_version, outcome, semantic_status, evidence_status и ссылки на полные разрешённые снимки. Отдельно записывать frame/timecode исходного и смонтированного видео. Пока видео нет, оба значения null.

Числа редакции берутся из ответа/повторного чтения, не вычисляются по таймкоду. Чат, комментарий и сверка могут менять version без изменения revision. Для каждой текстовой правки зафиксировать proposal_id, base_revision, состояние предложения, результат apply и новое чтение документа. Применение без текстовой разницы может быть no-op.

Для сверок: ID проверки, ID и согласованные редакции БТ, candidate/basis fingerprints, coverage/consistency по всем фрагментам, quality_status/evidence_status, current/qualifies, фактическая причина отрицательного результата. Эталоны проверяющего и критерии не включаются в payload модели.

Для Eva: origin, project_id, document_id, remote_version до/после, номер отправленной локальной редакции, исход ответа и отдельно исход чтения страницы. Последующая локальная правка не должна приписываться ранее опубликованной редакции.

## Безопасный сетевой след

Не сохранять raw HAR, storage state, cookies, Authorization, личные токены, DSN и полные профили пользователя. Предпочесть штатные ID запросов, статусы и разрешённые телеметрические поля. Для доказательства тела сохранять отдельные синтетические снимки документов после allowlist-проекции. Для каждой сетевой записи достаточно: метод, путь без секретных параметров, статус, время, ID, хеш разрешённого тела. Хеш не доказывает смысл ответа без доступного снимка.

Если штатная телеметрия не связывает UI с моделью, отразить пробел. Новый перехватчик, прокси или запись провайдерских тел не включаются в этот комплект автоматически; их реализацию и хранение нужно проектировать отдельно. Не выводить скрытые рассуждения модели.

## Проверка ролей

В отдельном демонстрационном документе читателя повторить заведомо запрещённую запись через реальный API с его собственной сессией. Тело — тот же текущий текст плюс учебная правка. Ожидается серверный отказ без изменения документа; HTTP 200 с отказом в envelope также не равен успешной записи, фиксируются оба уровня. После запроса редактор читает документ заново и сравнивает снимок. Никакие cookies не копируются в отчёт. Отсутствие такого запроса ограничивает доказательство видимостью UI. Неавторизованный пользователь и пользователь другого проекта проверяются отдельно; чужое содержимое не должно возвращаться.

Точный маршрут записи: `PUT /api/v1/source-workspaces/{workspace}/technical-specifications/{document_id}`. Поля JSON: `version` из свежего снимка, `title` равен текущему названию с добавлением ` — проверка запрета`, `sections` равны полному текущему объекту из девяти строковых ключей. В запросе нет выдуманных ID, старой версии и некорректного формата: иначе отказ не доказывает запрета по роли. Разрешённый GET того же документа должен сначала сработать у читателя. После отказа редактор проверяет также неизменность title. Эта проверка относится только к собственному демонстрационному документу.

## Будущая запись

Сначала включить захват и журнал времени, затем выполнить реальные действия. Ожидание снимать непрерывно. После каждой главы сохранить исходник и его SHA-256, после монтажа — соответствие интервалов и отдельный SHA-256. Ожидания сокращаются с явной подписью. Озвучка описывает только фактически записанный результат. Исходник не заменяется успешной репетицией; неудачные попытки перечисляются. До отдельного поручения видеозахват, звук и монтаж не запускаются.
