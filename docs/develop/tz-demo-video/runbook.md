# Подготовка стенда и повторяемое прохождение

## Граница текущего комплекта

Комплект содержит синтетические документы и сценарий; он не создаёт данные в RAGFlow/Eva и не начинает запись. Нет фиктивных согласований, токенов, DSN или заранее записанных ответов модели. На стенд передаются только inputs/ и нужные запросы; expected/ остаётся у проверяющего. CSV-функция существует только как предмет ТЗ, её /demo/v1 не вызываются.

## Перед репетицией

1. Запустить `.venv/Scripts/python.exe -B docs/develop/tz-demo-video/check_assets.py` из корня репозитория. Результат — проверка комплекта, не приёмка работающего приложения.
2. Создать внешний по отношению к source каталог задачи штатным `deployment/local/temp.ps1 -Name <run>`; evidence писать туда. Итоговый уникальный результат сохранить в `.local/archives/<run>` перед `-Complete`; не хранить токены, HAR, cookies или профили браузера в архиве.
3. Зафиксировать HEAD и хеши затронутых локальных файлов, URL стенда, образ/source_id работающего приложения, профиль модели и его фактические параметры без секретов, версию браузера и viewport 1920×1080. HEAD грязного checkout не подтверждает состав runtime.
4. Подготовить две учётные записи: редактор и читатель выделенного рабочего пространства. Третья без доступа нужна для проверки прямой ссылки. Роли operator/reader в документе не создают ролей RAGFlow автоматически.
5. Сначала проверить справочник названий БТ: текущее создание выбирает catalog_entry_id и не позволяет произвольное название. Для этого комплекта требуется заранее разрешённая отдельная учебная запись с названием «БТ загрузки заявок CSV — учебное демо». Если её нет, сверка M03/M08 блокируется; нельзя выбрать несвязанную банковскую запись, менять обычный справочник или подменять согласование ради репетиции. После подготовки подходящей записи через действующий процесс БТ создать документ с точным телом inputs/01. При переносе сохранить все 15 разделов/подразделов, включая 5.2–5.5; 5.1 не добавлять. Блоки PlantUML — часть исходника. Дождаться доступности диаграмм в интерфейсе; их рендеринг отдельно отметить. Получить реальное согласование доступным уполномоченным пользователем. Зафиксировать document_id/revision_id/agreement_event_id/content_hash и сопоставить прочитанный текст с исходником. Если механизм импорта дополнил документ, проверить каждое дополнение; не объявлять точный исходник при отличии тела.
6. Подготовить страницу Eva в разрешённом демопространстве с точным Markdown inputs/02, без преамбулы перед разделом 1. Название хранится в названии страницы, а не H1 перед разделами. Записать origin/project/document_id/remote_version. Проверить личные права чтения и записи до съёмки, без показа токена.
7. Для каждого дополнительного активного документа выделить другую страницу. Повторять съёмку на новых документах и страницах с новым run; старые версии и историю не сбрасывать SQL-скриптами. Не снимать реальное обновление на обычных рабочих страницах.
8. Заполнить копию session-template.json фактическими ID; NOT_RUN переводится в результат только после соответствующего события. Во время подготовки проверить доступность БТ в каталоге оснований. Недоступное согласованное основание — блокирующий prerequisite, не повод подставить API.

## Ручной ввод и импорт

Создание: кнопка «Создать ТЗ», затем заголовок/разделы. В девять редакторов вставлять тела разделов без внешних заголовков `## 1...`; оставить внутренние `###` и fences. В RAGFlow не обещается кнопка загрузки Markdown. Для проверки выгрузить .md и сравнить через check_assets.py --stage initial --observed <файл>.

Импорт: на выделенной странице Eva хранится полный inputs/02 с девятью `##`-заголовками. Поиск по реальному URL, явный выбор найденной страницы, затем импорт. Если та же страница связана с БТ, основным документом прошлого прогона или недоступным документом, выбрать новую выделенную страницу; не снимать запрет активной связи.

Привязка: отдельное локальное ТЗ и отдельная пустая страница; после connect-eva проверить неизменность текста, затем publish-eva и readback. Привязка не равна импорту и не должна молча заменять локальные разделы.

## Точки контроля

| Код | Контроль | Критерий |
| --- | --- | --- |
| A00 | Исходник | Текст и структура inputs/02, реальное согласованное основание inputs/01 |
| A01 | Первая сверка | Нет подтверждённого соответствия; BR-03 MISSING/PARTIAL/UNDETERMINED с фактическим объяснением. Ожидается диагностированный пробел; UNDETERMINED показывает неопределённость, не доказанное обнаружение |
| A02 | Вопрос/область | Нет изменения sections/revision; отсутствие частичной записи. Успех запроса HTTP не равен успеху сценария |
| A03 | Выделение | Только точная замена в разделе 5; одна редакция |
| A04 | Исправление | Смысл expected/04; ключ ограничен организацией, срок и повторы согласованы; неизменные разделы сохранены |
| A05 | Повторная сверка | Новая фактическая проверка текущей редакции и прежних БТ, полный перечень требований; PASS и COMPLETE, qualifies/current=true для положительной приёмки |
| A06 | История/выгрузка | Полные старые снимки и актуальная выгрузка, обсуждение не попало в тело |
| A07 | Eva | Публикация конкретной редакции, тот же ID страницы, повторное чтение совпадает по телам разделов |
| A08 | Противоречие | Настоящее предложение 20/50 → apply → needs_resolution и неизменный документ; отказ генератора этого не подтверждает |
| A09 | Восстановление после ошибки | Новое исправленное предложение применено, ровно одна новая редакция, старое не применено |
| A10 | Объединение | Предел выбранной стороны во всех 4/5/8; обе независимые правки раздела 4 и duration_ms в 9 сохранены; остальные разделы прежние |
| A11 | Права | UI и реальный серверный отказ; после запроса исходный документ неизменён |

Положительный исход сверки не гарантируется наличием текста: реальная модель и полнота доказательства проверяются отдельно. INCOMPLETE не переименовывается в PASS. Идентификаторы фрагментов Rxxx назначаются из всего БТ, заголовков и абзацев; BR-03 не имеет постоянного номера строки отчёта.

## Сравнение результата

Для строгой проверки: `.venv/Scripts/python.exe -B docs/develop/tz-demo-video/check_assets.py --stage complete --observed <выгруженный.md>`. Этапы: initial, selection, complete, negative-candidate, negative-recovered, merge-base, merge-local, merge-eva, merge-choose-local, merge-choose-eva. negative-candidate проверяется только по сохранённому тексту предложения, не через выгрузку действующего документа. check_assets.py ничего не отправляет модели и ничего не записывает в приложение.

Строгое сравнение обнаруживает любое расхождение тел разделов, включая пробелы, и не является семантическим LLM-оценщиком. При стилистическом отличии результат строгой проверки остаётся FAIL до разбора. Проверяющий отдельно отмечает смысловую эквивалентность и все побочные изменения; исходный эталон не переписывается задним числом. У двух независимых добавлений при объединении допустим другой порядок: фиксировать как отличие строгого текста, затем проверить каждое добавление и сохранность прочего по A10. Дополнительный диалог означает другой путь; сохранить его, исходный комплект и фактические редакции.

## Остановка и повтор

Нет основания, прав, законченного ответа, подтверждённой записи, нужного предложения или свежего снимка Eva — остановить соответствующий эпизод. Не добавлять page.route/fulfill, мок-модель, replay готового ответа или DOM-статус успеха. Технический отказ логируется отдельно от смыслового замечания. При потерянном publish сначала читать страницу, затем принимать решение о повторе. Незавершённая глава не мешает статической готовности остальных файлов, но не даёт заявить полное живое прохождение.

После репетиции оставить отчёт, фактические снимки и очищенный журнал, перечислить созданные демонстрационные объекты. Их удаление — отдельное явно определённое действие только по зафиксированным ID; автоматического удаления внешних данных комплект не выполняет. Локальные временные файлы завершить штатным -Complete после сохранения уникального результата.
