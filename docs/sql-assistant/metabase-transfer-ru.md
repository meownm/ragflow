# SQL-чат: алгоритмы, архитектура и приёмка

Персона — аналитик данных, конечный пользователь. Один владелец реализации.
База разработки 29.10.2026: `4a05f022a`, общий dirty checkout.
Меняется локальное расширение SQL-помощника. Посторонние admin/document/UI-kit
изменения не входят в этот инкремент. Основа прежнего помощника и миграция
описаны в [конструкторе результата](result-builder-ru.md); текущий отчёт —
`.local/archives/sql-product-figma-20261029/REPORT.json`.

## Пользовательский путь

Один ввод: вопрос → необходимые уточнения → результат → дальнейшие вопросы
и изменения. При готовом результате данные слева, продолжающийся чат справа,
как в просмотренном живом Metabase и Figma `161:208`. Нет выбора между
«спросить» и «изменить SQL», обязательных карточек стадий и ручного прохождения
требований/схемы/компиляции. У результата доступны настройки представления,
фильтры, график, SQL, история и экспорт; редкие настройки раскрываются по запросу.
Новый вопрос может выполняться автоматически только через существующий
read-only executor, проверку каталога/профиля, guard и лимиты.

## Алгоритмы

1. Создание сохраняет исходный вопрос и ключ команды. Требования готовит
   существующий worker. Достаточный вопрос проходит дальше автоматически.
   Блокирующий вопрос показывается репликой; ответ сохраняется по его ID.
   Неизвестный показатель, период, источник или существенная неоднозначность
   не заменяются скрытой догадкой.
2. Схема разрешается действующим каталогом. Полные разрешённые схемы загружаются
   в worker до завершения задания. Неоднозначный источник уточняется в чате;
   рекомендация LLM не равна согласию на произвольный источник. Неполный каталог
   является ошибкой, а не разрешением строить SQL по вымышленным полям.
3. Проверенный read-only план принимается, компилируется и запускается сервером.
   Модель возвращает даты в ISO-формате с согласованным часовым поясом. Ошибка
   формата получает одну попытку исправления в том же общем сроке ожидания;
   схема и типизированные значения проверяются повторно теми же правилами.
   Ошибка сети или таймаут не запускают повторный вызов модели. Непроверенный
   план не принимается и не создаёт SQL/Run.
   План получает предел выдачи только из однозначно привязанного разрешённого
   источника. При отсутствии заданного лимита используется этот предел; явный
   запрос большего числа строк требует уточнения. Планировочный предел не
   заменяет повторную проверку профиля при допуске и исполнении SQL.
   Исследовательский расчёт не объявляется согласованным определением метрики.
   Совпавшие согласованные определения требуют смыслового выбора в чате.
   Их изменяемые параметры связываются с исходным вопросом и ответами пользователя,
   а не берутся молча из шаблона. Интерпретированные значения показываются перед
   запуском; подтверждение привязано к версии методики, черновику и выбранному Run.
4. Последующая реплика сохраняется и ставится в существующую durable очередь.
   Ограниченный LLM-план выбирает ответ по ячейкам, вычисление по сохранённым
   строкам, представление, изменение запроса или уточнение. Свободный текст
   модели не исполняет SQL или команды. Изменение запроса использует настоящий
   revision adapter, исходный SQL, типизированные binds и выбранную версию.
5. Числа LLM не вычисляет. Ответ по ячейкам использует существующий проверяемый
   протокол ссылок. Сумма/среднее/число строк вычисляются действующими серверными
   правилами по сохранённому отфильтрованному набору с точным decimal.
   SQL-агрегаты повторно не агрегируются; полный итог источника требует нового
   расчёта. Ограниченная выдача и неизвестная полнота явно обозначаются.
   Объяснение периода, условий SQL, NULL или области сохранённого результата
   является отдельной закрытой возможностью диалога. Модель выбирает только
   тему; фактические условия сервер берёт из SQL/binds выбранного Run и снимка
   представления. Объяснение не запускает новый SQL и не меняет результат.
   Причина выбора периода не выводится из самого предиката; сложные или
   непроверяемые условия направляют к «SQL и основания», без вымышленного ответа.
   Сохранённый план объяснения повторно проверяет права и срок хранения при чтении.
6. Изменение вида сохраняет view выбранного запуска. Нового SQL/Run не создаёт.
   Изменение периода, состава данных, группировки и drill-down создаёт кандидат.
   Активный результат меняется только после READY принадлежащего этому ходу Run.
7. У каждой реплики есть версия основы и контекст выбранного результата.
   Сохранённые READY-запуски образуют историю и не считаются параллельными
   расчётами. В проекте исполняется один запрос; общие пределы владельца —
   20 сохранённых/активных результатов и 100 МБ — сохраняются вместе с TTL.
   CAS и idempotency действуют на сервере. Источник условий — сохранённый
   SQL/binds/view запуска, а не память переписки. Исторический результат можно
   продолжить через уже существующий pinned-revision механизм.
8. Ошибка или отмена не заменяет прежний успешный результат. Отмена отзывает
   право задания публиковать ответ; поздний ответ не возобновляет ход.
   UNKNOWN исполнения не превращается в автоматический повтор SQL.
   Новая вкладка/новый контекст браузера восстанавливает подтверждённое
   состояние с сервера. Чужой диалог не наследует условия и строки.

## Архитектурные границы

- `business_documents/sql_conversation.py`: закрытый протокол намерения,
  выбор следующего шага и правила представления/сводки; без ORM, HTTP и bootstrap.
  Использует действующие `sql_assistant` и `sql_result_answer`, не дублирует
  decimal-вычисления и SQL guard.
- `api/apps/sql_assistant/`: application/infrastructure orchestration.
  Владеет сохранённым ходом в JSON существующей SqlAssistantSession, проверкой
  контекста и связыванием текущих сервисов. Новых таблиц/своего executor нет.
- Существующие SQL project/revision/run services владеют артефактами,
  source identity, tenant/ACL, версиями, компиляцией и исполнением.
  Очередь/lease/worker остаются существующими. В wiring добавляется только
  новая ограниченная задача диалога и продолжение принадлежащего ей pipeline.
- Завершение задания и постановка следующего шага выполняются в общей
  транзакции. Нет окна «задание уже завершено, продолжение ещё не записано».
  Вызов LLM и пакетная загрузка схем выполняются до этой транзакции.
- GET не запускает модель/SQL и не изменяет workflow. Браузер отображает
  серверное состояние и отправляет одну реплику/выбор/отмену; он не является
  движком автоматического прохождения стадий.
- UI использует действующие компоненты/темы и сервисные hooks. SQL, настройки,
  история и определения доступны по запросу. Общие UI-примитивы не меняются.

## Design review — до реализации

Самопроверка владельца против `4a05f022a` и текущего владеющего кода.

- Выявлено: прежний live-тест создаёт результат API-командами и только открывает
  браузер. Решение: реплики новых journeys вводятся настоящим composer; API
  используется для fixture setup и чтения доказательств.
- Выявлено: только история текста не гарантирует сохранения условий.
  Решение: основой служат неизменяемые Run/SQL/binds/view; версии проверяются
  до планирования и повторно перед публикацией.
- Выявлено: разрешить LLM суммировать числа текстом означало бы потерять
  проверяемость. Решение: повторно использовать точные серверные result_metrics.
- Выявлено: автоматическое продолжение из useEffect или GET теряет ход при
  закрытии вкладки и может дублировать SQL. Решение: durable серверный pipeline,
  атомарный completion/next job, неизменяемые ключи.
- Выявлено: принятие нового SQL до неудачного исполнения не должно менять
  активные данные. Решение: сохранять выбранный успешный Run; дальнейшее
  изменение опирается на его pinned SQL revision, поддержанную текущим сервисом.
- Выявлено: скрытие статусов/кнопок не является проверкой доступа.
  Решение: повторные ACL/source/context проверки при выполнении и экспорте;
  ошибки и UNKNOWN не понижаются до успешного пустого результата.

Checkpoint: архитектура и AC зафиксированы; реализация, diff-review, живые
проверки и деплой ещё не завершены. Сводное текущее evidence и следующий шаг
обновляются в существующем REPORT.json, без отдельного реестра прогресса.
