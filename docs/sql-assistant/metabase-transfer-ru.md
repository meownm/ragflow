# SQL-чат: алгоритмы, архитектура и приёмка

Персона — аналитик данных, конечный пользователь. Один владелец реализации.
База разработки 29.10.2026: `4a05f022a`, общий dirty checkout.
Меняется локальное расширение SQL-помощника. Посторонние admin/document/UI-kit
изменения не входят в этот инкремент. Основа прежнего помощника и миграция
описаны в [конструкторе результата](result-builder-ru.md); текущий отчёт —
`.local/archives/sql-product-figma-20261029/REPORT.json`.

## Пользовательский путь

Один ввод: вопрос → необходимые уточнения → результат → дальнейшие вопросы
и изменения. При готовом результате данные слева, продолжающийся чат справа,
как в просмотренном живом Metabase и Figma `161:208`. Нет выбора между
«спросить» и «изменить SQL», обязательных карточек стадий и ручного прохождения
требований/схемы/компиляции. У результата доступны настройки представления,
фильтры, график, SQL, история и экспорт; редкие настройки раскрываются по запросу.
Новый вопрос может выполняться автоматически только через существующий
read-only executor, проверку каталога/профиля, guard и лимиты.

## Алгоритмы

1. Создание сохраняет исходный вопрос и ключ команды. Требования готовит
   существующий worker. Достаточный вопрос проходит дальше автоматически.
   Блокирующий вопрос показывается репликой; ответ сохраняется по его ID.
   Неизвестный показатель, период, источник или существенная неоднозначность
   не заменяются скрытой догадкой.
2. Схема разрешается действующим каталогом. Полные разрешённые схемы загружаются
   в worker до завершения задания. Неоднозначный источник уточняется в чате;
   рекомендация LLM не равна согласию на произвольный источник. Неполный каталог
   является ошибкой, а не разрешением строить SQL по вымышленным полям.
3. Проверенный read-only план принимается, компилируется и запускается сервером.
   Модель возвращает даты в ISO-формате с согласованным часовым поясом. Ошибка
   формата получает одну попытку исправления в том же общем сроке ожидания;
   схема и типизированные значения проверяются повторно теми же правилами.
   При изменении календаря для timestamptz модель задаёт локальные границы и
   имя часового пояса; PostgreSQL выполняет преобразование через `AT TIME ZONE`.
   Модель не прибавляет и не вычитает UTC-смещения. При продолжении структурированного
   запроса типы date/datetime/decimal берутся из принятых фильтров, а не угадываются
   по строкам сериализованного результата компиляции.
   Ошибка сети или таймаут не запускают повторный вызов модели. Непроверенный
   план не принимается и не создаёт SQL/Run.
   План получает предел выдачи только из однозначно привязанного разрешённого
   источника. При отсутствии заданного лимита используется этот предел; явный
   запрос большего числа строк требует уточнения. Планировочный предел не
   заменяет повторную проверку профиля при допуске и исполнении SQL.
   Исследовательский расчёт не объявляется согласованным определением метрики.
   Совпавшие согласованные определения требуют смыслового выбора в чате.
   Их изменяемые параметры связываются с исходным вопросом и ответами пользователя,
   а не берутся молча из шаблона. Интерпретированные значения показываются перед
   запуском; подтверждение привязано к версии методики, черновику и выбранному Run.
4. Последующая реплика сохраняется и ставится в существующую durable очередь.
   Ограниченный LLM-план выбирает ответ по ячейкам, вычисление по сохранённым
   строкам, представление, изменение запроса или уточнение. Свободный текст
   модели не исполняет SQL или команды. Изменение запроса использует настоящий
   revision adapter, исходный SQL, типизированные binds и выбранную версию.
   Явное «добавь условие» соединяет его с прежними через AND, включая
   корректный пустой результат. «Вместо прежнего условия» удаляет заменённый
   предикат и сохраняет остальные договорённости. Сам по себе пустой результат
   не является основанием спрашивать разрешение изменить заданный отбор.
5. Числа LLM не вычисляет. Ответ по ячейкам использует существующий проверяемый
   протокол ссылок. Сумма/среднее/число строк вычисляются действующими серверными
   правилами по сохранённому отфильтрованному набору с точным decimal.
   SQL-агрегаты повторно не агрегируются; полный итог источника требует нового
   расчёта. Ограниченная выдача и неизвестная полнота явно обозначаются.
   Объяснение периода, условий SQL, NULL или области сохранённого результата
   является отдельной закрытой возможностью диалога. Модель выбирает только
   тему; фактические условия сервер берёт из SQL/binds выбранного Run и снимка
   представления. Объяснение не запускает новый SQL и не меняет результат.
   Причина выбора периода не выводится из самого предиката; сложные или
   непроверяемые условия направляют к «SQL и основания», без вымышленного ответа.
   Сохранённый план объяснения повторно проверяет права и срок хранения при чтении.
6. Изменение вида сохраняет view выбранного запуска. Нового SQL/Run не создаёт.
   Изменение периода, состава данных, группировки и drill-down создаёт кандидат.
   Активный результат меняется только после READY принадлежащего этому ходу Run.
7. У каждой реплики есть версия основы и контекст выбранного результата.
   Сохранённые READY-запуски образуют историю и не считаются параллельными
   расчётами. В проекте исполняется один запрос; общие пределы владельца —
   20 сохранённых/активных результатов и 100 МБ — сохраняются вместе с TTL.
   CAS и idempotency действуют на сервере. Источник условий — сохранённый
   SQL/binds/view запуска, а не память переписки. Исторический результат можно
   продолжить через уже существующий pinned-revision механизм.
8. Ошибка или отмена не заменяет прежний успешный результат. Отмена отзывает
   право задания публиковать ответ; поздний ответ не возобновляет ход.
   UNKNOWN исполнения не превращается в автоматический повтор SQL.
   Новая вкладка/новый контекст браузера восстанавливает подтверждённое
   состояние с сервера. Чужой диалог не наследует условия и строки.

## Архитектурные границы

- `business_documents/sql_conversation.py`: закрытый протокол намерения,
  выбор следующего шага и правила представления/сводки; без ORM, HTTP и bootstrap.
  Использует действующие `sql_assistant` и `sql_result_answer`, не дублирует
  decimal-вычисления и SQL guard.
- `api/apps/sql_assistant/`: application/infrastructure orchestration.
  Владеет сохранённым ходом в JSON существующей SqlAssistantSession, проверкой
  контекста и связыванием текущих сервисов. Новых таблиц/своего executor нет.
- Существующие SQL project/revision/run services владеют артефактами,
  source identity, tenant/ACL, версиями, компиляцией и исполнением.
  Очередь/lease/worker остаются существующими. В wiring добавляется только
  новая ограниченная задача диалога и продолжение принадлежащего ей pipeline.
- Завершение задания и постановка следующего шага выполняются в общей
  транзакции. Нет окна «задание уже завершено, продолжение ещё не записано».
  Вызов LLM и пакетная загрузка схем выполняются до этой транзакции.
- GET не запускает модель/SQL и не изменяет workflow. Браузер отображает
  серверное состояние и отправляет одну реплику/выбор/отмену; он не является
  движком автоматического прохождения стадий.
- UI использует действующие компоненты/темы и сервисные hooks. SQL, настройки,
  история и определения доступны по запросу. Общие UI-примитивы не меняются.

## Design review — до реализации

Самопроверка владельца против `4a05f022a` и текущего владеющего кода.

- Выявлено: прежний live-тест создаёт результат API-командами и только открывает
  браузер. Решение: реплики новых journeys вводятся настоящим composer; API
  используется для fixture setup и чтения доказательств.
- Выявлено: только история текста не гарантирует сохранения условий.
  Решение: основой служат неизменяемые Run/SQL/binds/view; версии проверяются
  до планирования и повторно перед публикацией.
- Выявлено: разрешить LLM суммировать числа текстом означало бы потерять
  проверяемость. Решение: повторно использовать точные серверные result_metrics.
- Выявлено: автоматическое продолжение из useEffect или GET теряет ход при
  закрытии вкладки и может дублировать SQL. Решение: durable серверный pipeline,
  атомарный completion/next job, неизменяемые ключи.
- Выявлено: принятие нового SQL до неудачного исполнения не должно менять
  активные данные. Решение: сохранять выбранный успешный Run; дальнейшее
  изменение опирается на его pinned SQL revision, поддержанную текущим сервисом.
- Выявлено: скрытие статусов/кнопок не является проверкой доступа.
  Решение: повторные ACL/source/context проверки при выполнении и экспорте;
  ошибки и UNKNOWN не понижаются до успешного пустого результата.

Checkpoint: архитектура и AC зафиксированы, реализация и diff-review выполнены.

### Добавление связанной таблицы при уточнении запроса

Проверенный запрос по прежней схеме требует одного вызова модели. Если
предложение заблокировано и использует новую связанную таблицу, worker проверяет
текущий доступ к каталогу и неизменность исходной схемы, находит однозначную
таблицу по реальным FK и загружает её полные актуальные поля. Неоднозначные,
не названные пользователем посторонние, недоступные и устаревшие таблицы
автоматически не принимаются.

Допускается одно исправление с замечаниями проверки и подтверждённой схемой;
обе генерации и чтение каталога ограничены общим временем. Исходными остаются
выбранные SQL, параметры и реплика пользователя. NULL и пустая строка в ключах
группировки сохраняют разный смысл. Новая неизменяемая схема сохраняется вместе
с принятым SQL после повторной проверки; неиспользованные таблицы не добавляются.
Ошибка, отмена и устаревшее завершение не меняют прежний Run и его основания.


### Замена источника и продолжение результата из истории

Полное имя каталога в исходной реплике пользователя или выбранная им ссылка
на таблицу позволяют загрузить её проверенную схему без связи FK со старой.
Полный FQN проверяется прямым запросом к живому каталогу: кэш списка таблиц
не должен скрывать недавно созданный источник или подменять его старым ID.
Текст ячейки, дополненный контекст строки, предложение модели и история
другого изменения этим основанием не являются. Исходный выбор источника
текущего изменения сохраняется при уточнении года или другого параметра;
ответ модели не расширяет этот выбор. Блокирующие проверки каталога,
схемы и SQL сохраняются. Если новый SQL использует только явно названный новый
источник, неиспользованный прежний источник удаляется из новой схемы. При её
принятии сбрасывается прежний профиль: выполнение заново разрешает привязки
источника и не переносит старые credentials на другую таблицу. Предыдущие
артефакты, результаты и их профили остаются неизменяемыми.

Продолжение выбранного Run передаёт серверу ID его сохранённой компиляции.
Сервер проверяет всю цепочку требований, схемы и SQL и текущий доступ; эта
цепочка служит основой модели. Схема повторно проверяется worker до вызова
модели. Перед принятием повторяются авторизация и CAS относительно текущего
проекта. Прежние требования и схема становятся основой нового расчёта только
после принятия; ошибка, отзыв доступа и отмена не переключают профиль или
источник. Обычные команды редактирования SQL сохраняют проверку текущей схемы.


### Проверки после ревью их обоснованности

Каталог 24 сценариев / 42 вариантов сохраняется как расширенная регрессия.
Число вариантов не является обязательным gate каждой промежуточной поставки.
Живой браузер и qwen3.8 проверяют два основных пути, обычные продолжения,
точные результаты и действия после ответа. API/worker/БД проверяют
авторизацию, CAS, идемпотентность, отмену, поздний ответ и retention; UI-проверки
дополняют эти границы там, где значим пользовательский переход.
Два разных набора данных нужны для SQL-семантики: JOIN/fanout, SUM без DISTINCT,
NULL/пустая строка/ноль/decimal и календарные границы. Эти различия не требуют
двойного полного LLM-прохождения каждого независимого от данных ACL-сценария.
Используется подготовленное QA-окружение с изолированными данными и учётом
ресурсов; новые стеки не создаются для каждого небольшого пакета без причины.
Защита и восстановимость ресурсов при закрытии сохраняются.

Коррекция 2.2.11 устраняет два наблюдаемых дефекта 2.2.10: умножение
счётчиков при соединении двух независимых дочерних таблиц и блокировка новой
реплики после ошибки автоматического принятия SQL-кандидата. Неудачный кандидат
текущего хода отклоняется, подтверждённые артефакты и выбранный Run сохраняются;
кандидаты ручного конструктора и другого задания не затрагиваются. Новая реплика
проходит прежние проверки версии и прав. Проверка C13 сначала подтверждает приём
новой команды, затем ожидает её результат. C18 проверяет запрет создания через
кнопку/Enter и сервер, не требует неактивного поля ввода. Ошибка DNS до действия
Stop не считается проверкой отмены. Номер версии в исходниках не доказывает её
установку: состояние поставки и исходные результаты находятся в существующем отчёте.

C12 проверяет явное добавление несовместимых границ как успешные 0 строк,
а затем явную замену порога — как новый непустой результат с сохранением
истории и остальных условий. Обязательный вопрос при явном добавлении был
необоснованным ожиданием прежнего теста. Не определённое пользователем
бизнес-решение по-прежнему требует существенного уточнения.

C01 начинается кратким вопросом про оплаченные заказы и поля, без подсказок
про LIMIT, grain, SQL и read-only. C02 просит «итог» без искусственной фразы
о том, что метрика не выбрана. Фактическое время ответа сохраняется в proof;
до живого прохождения и согласованной границы задержки скорость не доказана.
Технически подробные golden-вопросы проверяют воспроизводимую SQL-семантику
и не заменяют пользовательскую проверку.


### Формат плана поиска источников

Планировщик возвращает экземпляр закрытого контракта: `schema_version` и
массив `searches` с бизнес-терминами и поисковыми запросами. Инструкция показывает
форму экземпляра и отделяет её от JSON Schema, которая служит только проверкой.
Ответ с описанием схемы вместо данных отклоняется прежним валидатором;
он не превращается в поисковый план и не расширяет доступ к каталогу.
Краткий вопрос C01 явно задаёт направление сортировки, поскольку его oracle
проверяет порядок строк. Это уточнение входного теста, а не новое правило
обязательного вопроса или неявного выбора направления в продукте.

## Исправление алгоритма ревизий — 31.10.2026

База c9fac7ed3, локальная версия 2.2.13. Полная хронология вопроса и ответа
сохраняется с reply_to (ID сообщения и вопроса); совпадение текста вариантов
не используется как подтверждение других решений. В чате показывается
формулировка активного вопроса вместе с пояснением, остальные вопросы остаются
контекстом. Модель просят задавать один существенный вопрос за раз; новых
ограничений количества и длины ответов нет.

Каталог и генерация имеют одного координатора: общий таймаут включает проверку
снимка и максимум два модельных вызова суммарно для формата/SQL. Отмена
распространяется, ошибка провайдера не повторяется, общий таймаут получает
безопасный SQL_REVISION_UNAVAILABLE. Приведение ответа не управляет повторами.

Технический PASS не подтверждает изменение принятых условий. Чистая функция
сравнивает исходный SQL и значения параметров с предложением. Добавление
измерения и фильтра структурированно выбранной группы допускает автоприменение
при сохранении прежних условий, показателей и совместимой сортировки. Остальные
изменения отбора, показателей, источников, группировки или лимита доступны через
однократное применение с SQL/parameter diff. Автор может применить, оставить
прежний результат или уточнить правку текстом; новый запрос опирается на прежнюю
принятую версию. Отсутствие сравнения не разрешает автоприменение.

Это сравнение принятых частей, а не доказательство любого намерения свободного
текста. Эквивалентные сложные переписывания могут потребовать просмотра;
дополнительного SQL allowlist, произвольных лимитов и нового DSL нет. Источники,
права, транзакции и физическое read-only исполнение остаются у прежних владельцев.

повторы и таймауты; фронтенд — diff и действия автора/читателя. Живой месячный
