# Проверки SQL проектов

Корпус проверяет изменения запроса в диалоге, параметры, связанные таблицы,
детализацию строк и ER-представление. Приёмка разделена на проверки приложения,
браузера, точных результатов PostgreSQL и реальной модели. Успех одной группы
не заменяет остальные.

## Экспорт и повторный доступ

SQL с типизированными параметрами, результат и ER скачиваются через серверный
`POST /business-documents/sql-query/projects/<id>/export`. Копирование SQL
использует тот же вход. Сервер проверяет владельца, tenant, неизменную цепочку
requirements/schema/query/compilation и текущую видимость фактических таблиц.
Отзыв доступа закрывает также повторное чтение строк. Изменение версии каталога
само по себе не удаляет право прочитать старый результат: его исходные SQL,
параметры и версия профиля сохраняются.

Результат JSON использует `typed-cells-v1`: NULL, пустая строка, false и ноль
различаются; integer и decimal сохраняются текстом без округления JavaScript.
Для новых SQL результатов сохраняется PostgreSQL OID столбца; у старых результатов
отсутствующие типы явно обозначены неизвестными. SVG содержит легенду, связанные
таблицы, список связей и полные JSON metadata. Непринятый кандидат экспортируется
отдельной частью с подписью «ещё не принято». Клиент отменяет скачивание при смене проекта,
версии или уходе со страницы.

Сервисные тесты `test_sql_query_exports.py` используют настоящий HTTP handler,
SQLite и контролируемый каталог; они не заменяют реальный auth middleware.
Браузерные download/copy/ER/history/revocation проверки находятся в
`test_sql_connection_ui.py` и используют собранный SPA с управляемым транспортом.
Точность OID/decimal/timestamp проверяется отдельным тестом
`test_driver_types_and_download_preserve_postgres_precision` на disposable
PostgreSQL. Отсутствующий QA PostgreSQL означает незавершённую проверку этой границы.

## Срок хранения результата

Временные результаты хранятся 30 суток от неизменяемого времени создания
запуска. Чтение и повтор команды срок не продлевают. Производный результат
ограничен также сроком исходного SQL. На границе срока просмотр и экспорт
возвращают `SQL_RESULT_EXPIRED`/410 с `Cache-Control: no-store`.

Очистка выполняется при обращении и в существующем цикле обслуживания worker.
Она атомарно удаляет строки, columns/checks, временные выводы и их копии в
журнале повторных команд. Ключ и hash команды сохраняются: повтор не создаёт
второй эффект и не возвращает прежний успешный результат. Отдельно подбираются
поздние производные записи уже истёкшего SQL. Принятые требования, схема, SQL,
неизменяемые документы и аудиторские метаданные запуска сохраняются.

Открытый интерфейс использует серверный deadline, очищает данные и отменяет
чтение/скачивание при истечении срока. Возврат из фоновой вкладки повторно
проверяет время. Обновление статуса сохраняет смонтированную SQL/ER-панель.
Смена источника и поздний ответ не восстанавливают строки. Новый Run остаётся
отдельным действием с обычной проверкой прав и подключения.

`test_sql_result_retention.py` проверяет политику/HTTP/границы и изоляцию на
SQLite. `test_sql_result_retention_postgres.py` использует настоящие отдельные
PostgreSQL-базы: каскад, позднюю запись, tenant scope и rollback при ошибке
очистки. Два соединения проверяют обе очередности очистки и публикации вывода:
конкурирующая транзакция действительно ожидает PostgreSQL row lock. После
очистки публикация отклоняется; при завершении публикации первой очистка удаляет
также вывод и копию ответа команды. Базы удаляются и отсутствие проверяется. Браузерные случаи находятся
в `test_sql_connection_ui.py`; часы и серверные ответы контролируемые.

## Золотой корпус

Структурированный план поддерживает необязательный `top_per_group` для первых N
детальных строк в каждой группе: aliases групп, отдельный порядок выбора с
правилом равенства и лимит на группу. После нормализации aliases заменяются
ссылками на пункты SELECT. Компилятор строит ROW_NUMBER, отбирает победителей
по отдельному bound-параметру, затем применяет итоговые ORDER BY и LIMIT.
Агрегаты и date buckets в этом режиме отклоняются. Старые планы без поля
сохраняют прежнее поведение. PostgreSQL-проверка покрывает TOP-1/TOP-2,
равные значения и общий лимит, который не должен обрезать вход ранжирования.

`golden.py` содержит 80 именованных случаев: 56 одиночных и 24 диалога
с несколькими ходами. Для предложения заданы SQL-эталон, типизированные параметры,
физические сущности, имена столбцов и точные строки. Эталоны написаны независимо
от ответа модели; scorer не требует посимвольного совпадения SQL.

Восемь синтетических таблиц описаны в `fixtures/schema.sql`. Данные включают
одинаковые суммы у разных заказов, отсутствие клиента, NULL и пустой регион,
несколько платежей и позиций, разные роли покупателя/плательщика, иерархию
сотрудников и границы периода. Это позволяет обнаруживать fan-out, неправильный
DISTINCT, потерю строк при INNER JOIN и небезопасный NOT IN с NULL.

Второй набор `discriminators.py` добавляет строки ровно на границе порога,
другой регион, отсутствие клиента и отменённые заказы в другом периоде.
Каждое SQL-предложение выполняется на обоих наборах. Совпадения на исходных
данных недостаточно для успеха.

Scorer проверяет вид ответа, отсутствие мутации в пояснении/уточнении, реальный
guard, сводку изменения, типы и значения binds, сохранение существующих имён,
физические источники, состав и кратность строк, NULL и точные decimal.
Обязательный ORDER BY проверяется отдельно: направление, NULLS и дополнительные
ключи. Допускаются эквивалентные aliases, ordinal и написание defaults PostgreSQL.
Неуточнённые столбцы разрешаются по каталогу: псевдоним результата имеет приоритет,
неоднозначный JOIN отклоняется. Регистр некавыченных имён нормализуется по правилам
PostgreSQL; кавычки сохраняют регистр. Позиционный ORDER BY допускается guard только
для существующего выходного столбца; числовые значения в WHERE и оконной сортировке
по-прежнему требуют параметров.

Отрицательные контроли специально подают неверные SQL и ответы: утраченные
статус/сортировку, строгий вместо включительного порог, лишний фильтр,
неправильные binds, источники, столбцы, значения и количество строк.
`test_adapter_oracles.py` использует управляемые ответы через настоящий parser
и guard; это проверка контракта, а не качества модели.
PostgreSQL lane дополнительно прогоняет все 40 вариантов через revision adapter,
берёт SQL и параметры из его фактического ответа и выполняет их на обоих наборах.
Так проверяется стык parser → guard → execution → scorer без вызова модели.

## Запуск детерминированных проверок

Из корня репозитория на Windows:

```powershell
.venv\Scripts\python.exe -B -m pytest -q test/evals/sql_projects
```

Для реальных SQL-эталонов нужен собственный одноразовый PostgreSQL на loopback.
Подставьте его порт; не используйте кластер приложения. Контекст создаёт случайные
базы, загружает fixtures, удаляет базы и проверяет удаление. DSN с удалённым
host/hostaddr, несколькими hosts или libpq service отвергается до соединения.

```powershell
$env:SQL_PROJECT_TEST_DISPOSABLE='1'
$env:SQL_PROJECT_TEST_POSTGRES_DSN='postgresql://postgres@127.0.0.1:<QA_PORT>/postgres'
.venv\Scripts\python.exe -B -m pytest -q test/evals/sql_projects test/integration/test_sql_projects_postgres.py
```

Назначайте `cache_dir`, JUnit и браузерные артефакты в заранее зарезервированный
каталог через `deployment/local/temp.ps1`. Не завершайте временную задачу до
сохранения нужных результатов: `-Complete` удаляет её рабочий каталог.

В CI шаг `SQL project golden requirements` запускает весь детерминированный
корпус и PostgreSQL lane на одноразовом сервисе текущего job. JUnit сохраняется
в preflight artifacts и при неудаче. Этот шаг не вызывает реальную модель.

## Браузерные проверки

`test/run_browser_regression.py` поднимает локальный HTTP-сервер собранной SPA.
API перехватываются тестами; неизвестный API не пересылается в приложение.
Граф строится настоящим projector по фикстурам каталога. Проверки охватывают:

- участие таблиц и предложенные добавления/удаления; FK, JOIN, CTE и aliases;
- глубину связей, альтернативные ключи, поиск, список и 100 узлов;
- историческую SQL-версию и соответствующий ей ER;
- светлую/тёмную тему, контраст, Tab/Enter, выбор FK клавишами и Space для
  раскрытия полей, компактную ширину и fullscreen;
- CSS-масштаб 100/200% на ширинах 390/1440: список, инспектор, достижимые
  полноэкранные кнопки и Escape без изменения SQL. Это не проверка системного
  browser zoom и связанных с ним media queries;
- восстановление личного вида, drag/depth, конфликт и ошибку сохранения;
- обновление метаданных при ещё не завершённом сохранении координат;
- отмену запросов графа/вида при уходе со страницы и безопасный reload;
- запоздалый ответ каталога, ошибку и Retry;
- пояснение/уточнение без SQL-мутации, редактируемый выбор ответа и reload;
- сохранение профиля соединения и reload без новой SQL-версии; отображение базы,
  схем и режима чтения; конфликт сохранения и поздний ответ другого проекта;
- явную замену недоступного профиля, запрет изменения для reader и сохранение
  прежнего источника READY-результата после выбора следующего подключения;
- отдельную проверку подключения при ошибке SQL/компиляции, ручной повтор после
  network/auth/TLS/timeout-ошибки, отмену при выборе другого проекта;
- прежний полный сценарий комментариев, принятия SQL и итогового документа.

- режим читателя: текущий SQL и история, ER и READY-строки доступны после reload;
  изменение запроса/источника, завершение, удаление строк и постобработка недоступны;
  принятие/отклонение ожидающего предложения запрещено;
- поздний ответ другого проекта с отличающимися SQL, JOIN и профилем не меняет
  выбранный проект, URL, SQL, ER и подключение.
- редактирование SQL при сохранённом READY-результате: Apply и reload сохраняют
  прежние строки и источник, отмечают предыдущую проверенную версию; новый запуск
  получает новую compilation, а прежний результат доступен через историю запусков.

Для ролей одной таблицы отдельно проверяются buyer/payer у customers и
employee/manager в self-join employees. Узлы QUERY и инспектор различают aliases;
обсуждение удаления называет выбранный alias, не изменяя SQL. Этот тест не
принимает удаление: Apply и качество SQL-предложения проверяются отдельно.

Полный исторический контекст загружается явно через
`POST /business-documents/sql-query/projects/<id>/query-history/context`.
Источник выбирается либо парой `compilation_id`/`query_artifact_id`, либо
`artifact_id` принятой версии требований/схемы, включая версии без SQL.
Сервер проверяет tenant/owner и hash артефактов; для раскрытия схемы заново
проверяет текущую видимость всех её таблиц. Старый снимок не заменяется новым
каталогом. Показаны все требования, вопросы/ответы и разобранные поля/ограничения
схемы. Закрытие, смена источника и pagehide очищают данные и отменяют загрузку.
`test_sql_history_context.py` и реальные HTTP handlers на SQLite проверяют эту
границу с контролируемой identity/каталогом; `test_sql_history_ui.py` проверяет
собранный SPA. Эти проверки не заменяют живой auth/catalog/worker lane.

`test_sql_ready_revisions.py` отдельно проверяет сервисы на одноразовой SQLite:
READY разрешает ручную/диалоговую правку и возврат к схеме/требованиям;
QUEUED/RUNNING/CANCEL_REQUESTED блокируют правку, включая принятие уже готового
предложения. Документ с прежним результатом и текущим SQL отклоняется; квота трёх
сохранённых результатов остаётся. Карточка проекта читает метаданные запусков без
загрузки строк. Это не подтверждает конкурентные транзакции настоящего PostgreSQL.

`test_sql_reader_authorization.py` проверяет 26 прямых команд для читателя,
чужого owner и чужого tenant на одноразовой SQLite. Отказ происходит до вызовов
каталога/компилятора/источника и оставляет все SQL-таблицы без изменений.
Отдельно проверены разрешённое чтение и запрет idempotent replay после отзыва роли.
Браузер не запускает автокомпиляцию для читателя; кнопки, скрытые в UI, не заменяют
серверную авторизацию. Автор с правом редактирования сохраняет работу с документом
и Python, а lookup в БД требует также права выполнения SQL.
`test_sql_reader_http.py` дополнительно вызывает 26 настоящих HTTP-обработчиков
с настоящими сервисами и проверяет 403/неизменность состояния. В этом lane
идентичность пользователя контролируемая, а dispatch выполняется в потоке теста:
login/session middleware и соединения PostgreSQL в рабочих потоках он не проверяет.

Для каждого движка используйте отдельные артефакты. Пример для графа:

```powershell
$env:PW_ARTIFACTS_DIR='S:\tmp\ragflow\<reserved-task>\chromium'
$env:PW_TRACE='1'
.venv\Scripts\python.exe -B test/run_browser_regression.py --browser chromium --dist-root <built-SPA> --suite test/playwright/e2e/test_sql_workspace_ui.py -- -q
```

Дополнительные SQL suites: `test_sql_candidate_graph_ui.py`,
`test_sql_view_continuity_ui.py`, `test_sql_graph_races_ui.py`,
`test_sql_dialogue_ui.py`, `test_sql_exit_cancellation_ui.py`,
`test_sql_revision_ui.py`, `test_sql_connection_ui.py`,
`test_sql_prequery_connection_ui.py`, `test_sql_project_registry_ui.py`,
`test_sql_history_ui.py`.
Все доступны через `--suite`. Проверки до создания QUERY открывают принятую
схему без артефакта SQL: проверка источника, выбор, сохранение и reload
не вызывают компиляцию, preflight, агента или Run. Отдельно проверяются
узкий экран, reader и отмена проверки при переключении проекта.
Повторите для `firefox` и `webkit`. Ошибки страницы приводят к падению теста;
неудача сохраняет HTML, screenshot, trace и диагностический журнал.

Проверки истории также открывают полные принятые требования и схему без SQL,
сравнивают версии и восстанавливают запрос новой записью. Длинные ответы проверяются
по ширине самого блока. При выходе, смене аккаунта во второй вкладке и `pagehide`
всё SQL-поддерево удаляется; возврат назад начинает новое чтение с сервера.
SQL HTTP-ответы, включая ошибки доступа и истечения результата, имеют `no-store`.
Контролируемый `pageshow(persisted=true)` проверяет обработчик восстановления;
сам факт размещения страницы браузером в BFcache этим не подтверждается.

CI устанавливает только группу `test` из frozen export с проверкой хешей.
В неё явно включены parser SQL, dotenv для тестового входа и JSON Schema validator
для браузерных фикстур документов. При установке экспортированного файла
`uv pip install --no-config --require-hashes` предотвращает повторное применение
нефиксированных проектных constraints поверх уже разрешённых зависимостей.

Снимки двух тем сопровождаются версией браузера, viewport и хешем build index.
Текущая автоматизация проверяет стили и контраст; сравнение с утверждёнными
пиксельными эталонами ещё не реализовано.

## Запуск реальной модели

`run_live.py` предназначен для настроенного локального QA-окружения RAGFlow
с явно выбранным QA tenant. Он вызывает настоящий revision adapter, guard и
PostgreSQL; проекты, задания и профили приложения не создаёт и не меняет.
После успешного предложения harness явно принимает его только в контексте
следующего хода. Каждый повтор начинается с исходного запроса.

```powershell
.venv\Scripts\python.exe -B test/evals/sql_projects/run_live.py --tenant-id <QA_TENANT> --out <new-external-evidence-dir> --repeats 3
```

По умолчанию выполняются три повтора всего корпуса; `--case` позволяет отладить
отдельный случай. Каталог evidence должен быть новым и вне checkout.
`--model <имя>` выбирает модель на настроенном Ollama endpoint только для этого
QA-прогона. Сохранённый профиль и настройки приложения не меняются; фактически
отправленное имя и параметры фиксируются в execution audit. Разные модели
сравниваются отдельными прогонами на одинаковых исходниках и входных заданиях.

Для сопоставимости стенд запрашивает фиксированный бюджет ответа 4096 токенов
через аргумент конструктора `RAGFlowLLMAdapter(max_output_tokens=4096)`;
это не меняет лимиты рабочего приложения. Ограничение применяется к настоящему
provider request, остаётся не выше настроенного потолка и свободного контекста.
Бюджет не передаётся в JSON задачи модели. Проверки используют настоящий
адаптер с контролируемым provider и сверяют отправленные generation parameters.
Контроль неизменности модели и параметров генерации остаётся обязательным.
Инициализация стенда загружает только каталог моделей, без запуска поиска,
хранилищ и настройки аутентификации приложения.

`turns.jsonl`
содержит ответы, результаты и ошибки; `summary.json` — хеши источников, состав
прогона, повторяемость настроек и проверку cleanup. Изменение provider/model,
temperature/top_p/reasoning/enable_thinking/output budget во время прогона отклоняется.

Полная матрица пока получает `INCOMPLETE`, частичная — `PARTIAL`, ошибка — `FAIL`.
Код возврата 2 означает неполную квалификацию, 1 — ошибку. Независимые доказательства
свежей инференции и семантической правильности пояснений/уточнений ещё нужны;
application audit сам по себе их не доказывает.

Утверждённые ответы на начальные вопросы передаются обоим агентам отдельно
от канонического текста требований: это сохраняет принятые fingerprint схемы.
Проверки сервисов и настоящих адаптеров сверяют передачу ответов без изменения
артефактов. Отдельный контроль на реальной модели с годом/UTC из ответа пользователя
выполнен на двух одноразовых PostgreSQL-наборах с точными пограничными строками
и другим часовым поясом сессии. Он не заменяет 80 диалоговых случаев и R01:
в нём нет настоящего проекта, auth middleware, очереди и worker.

## Границы приёмки

`acceptance.py` фиксирует 88 продуктовых браузерных сценариев и восемь сценариев
реального стека. `automated_by` указывает существующую автоматизацию,
`AUTOMATION_SCOPE` ограничивает её фактический охват. Связь с тестом сама по себе
не означает его успешный запуск или полное покрытие требования.

Восемь real-service journeys остаются планом. Для полной приёмки нужны
одноразовый стек с настоящими API/ACL/каталогом/worker/моделью/БД, проверки
управления соединением, экспорта, retention и конкурентных действий. Mocked
браузерные ответы и детерминированные SQL-эталоны эти границы не закрывают.

## Единый SQL-чат: браузер и живая модель

Целевой сценарий от 29.10.2026: один ввод для вопроса, существенного уточнения,
изменения условий, ответа по результату и изменения представления. После
открытия данных результат находится слева, продолжающийся диалог справа.
Это контракт предложенного интерфейса Figma `161:208`, а не утверждение,
что текущий `/sql-assistant` уже поддерживает такой путь. Текущий интерфейс
разделяет вопрос по результату и изменение SQL; существующий
`test_sql_assistant_live.py` выполняет расчёт API-командами и только затем
открывает его в браузере. Он не заменяет новые проверки.

Набор [chat_browser_cases.json](chat_browser_cases.json) содержит 24 сценария:
реплики/действия, ожидаемый результат, сохраняемые условия, приоритет,
автоматизацию и её пробелы. В
`test/playwright/e2e/test_sql_assistant_chat_live.py` подготовлены 7 нативных
pytest/Playwright-тестов для C01–C08; C01/C05 проверяются одним полным journey.
Остальные 16 случаев имеют статус `gap`, а не pass/skip. Сборка тестов не
доказывает исполнимость нового пути: привязки проверяются на реализации целевого
интерфейса. Применять к старому UI обход через этапные API-команды запрещено.

| Сценарии | Что проверяется |
| --- | --- |
| C01–C02 | Полный вопрос сразу даёт данные; неопределённый показатель сначала уточняется |
| C03–C05 | Замена и снятие фильтра; ответ по строкам без нового SQL; reload и новый browser context |
| C06–C08 | Группировка/drill-down, график без нового запуска, изоляция двух диалогов |
| C09–C12 | Границы периода и timezone, год, длинный диалог, противоречие условий |
| C13–C16 | Ошибка SQL, отмена/поздний worker, потерянный ответ и повтор, конфликт вкладок |
| C17–C20 | Источник старого результата, reader/tenant, отзыв прав, retention |
| C21–C24 | Пустая выдача, типизированный экспорт выбранной версии, фрагмент/полный итог, fan-out JOIN |

Для C01–C08 повторно используется `real_sql_catalog` существующего disposable
runner: три собственных заказа `(1,paid,12.50)`, `(2,cancelled,99.00)`,
`(3,paid,7.25)`. Независимые итоги: paid = **19.75**, все = **118.75**.
Фильтр amount >= 10 внутри paid оставляет только заказ 1; замена на < 10 —
только заказ 3. После снятия порога оба paid-заказа возвращаются, cancelled
не появляется. SQL результата обязан читать собственную физическую таблицу;
SELECT с придуманными константами не принимается за выполнение по источнику.

Для C09–C24 применяются уже существующие golden fixtures и второй набор
`discriminators.py`. За сентябрь 2026 UTC с paid первый набор даёт
**240.00**, второй — **490.00**. Ожидания не вычисляются из SQL модели.
Необходимо независимо зарегистрировать эти таблицы в собственном живом
QA-каталоге и связать с read-only профилем. Прямой `run_live.py` проверяет
адаптер, но не заменяет такой браузерный прогон.

### Подготовка и запуск

Проверка сбора без браузерных/модельных вызовов из зарезервированной задачи:

```powershell
$chatTask = .\deployment\local\temp.ps1 -Name sql-chat-browser-tests
.venv/Scripts/python.exe -B -m pytest --collect-only -q `
  -o "cache_dir=$chatTask/pytest-cache" `
  test/playwright/e2e/test_sql_assistant_chat_live.py
```

Живой запуск выполняется на зафиксированном образе целевого интерфейса. Укажите
источник с этими тестами и соответствующую ему проверенную SPA/archive;
образ/исходники, frontend receipt и реальные prerequisites обслуживает
[существующий runner](../../integration/live_ragflow/README.md).
Переменные ниже обозначают заранее подготовленные пути, а не скачивание
или сборку произвольного frontend:

```powershell
.venv/Scripts/python.exe -B test/integration/live_ragflow/runner.py `
  --source-root $chatSource `
  --dist-root $chatDist `
  --frontend-archive $chatFrontendArchive `
  --evidence-dir "$chatTask/live" `
  --chat-model qwen3.8:latest `
  --worker-service --openmetadata-network openmetadata_app_net `
  test/playwright/e2e/test_sql_assistant_chat_live.py
```

Нужны Docker Desktop, доступный приватный OpenMetadata и его QA-авторизация
через переменные окружения, proxy `127.0.0.1:11435`, qwen3.8 и свободная
пара loopback-портов runner. Пароли/токены не помещаются в команды и evidence.
Профили, каталог, пользователи и данные создаются только в собственном
одноразовом стеке; runner обязан подтвердить cleanup, включая внешний
синтетический сервис каталога. Общие рабочие данные не используются.

Все вопросы и изменения отправляются через видимый composer и кнопку формы.
API-записи разрешены только для fixture setup; API-чтение проверяет сохранённые
SQL, binds, выбранный запуск, строки и view. Ни ответы LLM, ни ответы API
не перехватываются. Реальный upstream audit qwen3.8 обязан иметь уникальные
fixture-маркеры, успешный upstream request и отсутствие cache/dedup.
Наблюдаемые задания связываются с отдельным worker. Новый browser context
получает только авторизацию: результат и история должны читаться с сервера.

В evidence сохраняются реплики, последовательность состояний, точные строки,
SQL/binds/view, идентификаторы диалога/запуска/артефакта, модельные транзакции
и снимки после проверенных шагов. `outcome_seconds` — время от нажатия отправки
до первого проверенного серверного исхода; это не TTFT и не согласованный SLO.
Расширенные сценарии находятся в `test/playwright/e2e/test_sql_chat_*_live.py`;
общая подготовка полного каталога — в `sql_chat_relation_fixture.py` в том же
каталоге. Они собираются в 33 варианта: два полных набора данных и отдельная
проверка изоляции C08. Основной набор остаётся в `test_sql_assistant_chat_live.py`.
Временные файлы `.local/archives` для импорта тестов не нужны.

Пакеты запускаются последовательно с неизменным пределом в 20 сохранённых
результатов владельца. Не повышайте квоту ради тестов. Отдельный пакет использует
собственный одноразовый стек; исходные fixtures и точные ожидаемые строки не
сокращаются. Collection и lint подтверждают только пригодность автоматизации.
Общий бюджет длинного browser-пакета задаётся у runner через
`--browser-timeout-seconds 7200` (по умолчанию 1800, допустимо 60–7200).
Он записывается в identity и журнал команды; лимиты отдельного действия,
ожидания результата и вызова модели не меняются. Прерванный общим лимитом
пакет сохраняется как незавершённый, даже если часть случаев уже прошла.

Перед настройкой моделей и запуском браузера runner ждёт готовности Compose
services, включая отдельный worker. Его healthcheck проходит через nginx,
который entrypoint запускает после API: готовый API при упавшем nginx ещё не
означает работающий worker. Ошибка старта завершает подготовку с сохранением
логов; она не засчитывается как проверка диалога.

Каталог из 24 сценариев / 42 вариантов — расширенная регрессия, а не обязательный
полный прогон каждой промежуточной поставки. Набор выбирается по изменённым
границам: живые браузер и qwen3.8 проверяют пользовательский путь и SQL-семантику,
API/worker/БД — права, транзакции, повторы и конкуренцию. После исправления
повторяются упавший случай и проверки затронутого поведения. Два набора данных
нужны для различающихся числовых и календарных контрпримеров; повторять на них
независимый от данных ACL-диалог не требуется. Три полные серии относятся к
отдельной оценке устойчивости модели. Частичный smoke не закрывает непроверенные
сценарии, а прежний `live_pass` не подтверждает изменённые байты новой версии.
Проверки Feature-поставки 2.2.10 относятся к source `f17bddf94533`. Текущая
поставка, результаты отдельных проверок, ограничения и точные receipts перечислены в
`.local/archives/sql-product-figma-20261029/REPORT.json`; исходная ошибка теста
или инфраструктуры сохраняется отдельно от результата повторной проверки.

Для C13–C20 нужны реальные контролируемые отказы/сроки/QA-персоны в одноразовом
стеке. Для C22 файл скачивается браузером и разбирается с проверкой typed cells.
Эти действия автоматизированы в расширенных модулях; наличие кода не заменяет
реальный прогон. Старые mocked-тесты и текстовый отчёт не закрывают их. После прогона сохранить
уникальное evidence в `.local/archives`, затем завершить только свою задачу
через `temp.ps1 -Name sql-chat-browser-tests -Complete`.
