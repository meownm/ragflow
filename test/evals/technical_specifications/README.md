# Приёмка ТЗ на реальной модели

`golden.v1.json` задаёт девять синтетических сценариев до запуска модели:

| Сценарий | Наблюдаемый результат |
| --- | --- |
| C01: вопрос о лимите | Ответ содержит 20 файлов, правок нет |
| C02: изменение названия кнопки | Меняется только запрошенная фраза раздела 5 |
| C03: правка цитаты | Меняется цитата, окружение и другие разделы сохранены |
| C04: запрос вне выбранной области | Правок нет, ответ объясняет смену контекста |
| C05: инструкция во внешнем тексте | Она не исполняется, действующий лимит сохранён |
| V01: разные величины без противоречия | Лимиты пакета и хранилища не смешиваются |
| V02: разные лимиты одного пакета | Проверка отклоняет результат и объясняет расхождение |
| M01: выбор локальных значений | Связанные упоминания согласованы; независимые правки обеих сторон сохранены |
| M02: выбор значений Eva | То же для противоположной стороны конфликта |

У M01/M02 дополнительно проверяется результат обычного семантического
верификатора. Согласованный результат с неверным выбранным значением не проходит
детерминированную проверку. Значения модели и сообщения об успехе не заменяют
проверку фактического содержимого. Для двух контролируемых объединений также
проверяется точный ожидаемый текст всех разделов: присутствия выбранных значений
недостаточно, если рядом остались старые ограничения или добавлен посторонний
текст. Это критерий данного синтетического корпуса, а не универсальный запрет
переформулирования в продукте. Негативные проверки самого оценщика:

```shell
python -B -m pytest -q test/evals/technical_specifications/test_live_quality.py
```

## Локальный прогон

Требуются работающий локальный контейнер `ragflow-local-ragflow-cpu-1`, отдельный
QA-профиль `Business Documents nightly QA` с настроенной моделью Ollama и новый
каталог доказательств вне checkout:

```shell
python -B test/evals/technical_specifications/run_live.py --evidence-dir <new-outside-source-directory>
```

Прогон исполняет снимок текущих модулей AI, прикладных правил и формата в отдельном
процессе контейнера. Исходники приложения в контейнере не подменяются, сервис
не перезапускается. Документы, комментарии, проекты и настройки не записываются.
Вызывается реальная модель через штатные бюджетирование, транспорт и разбор
потока RAGFlow; ответы модели не подменяются. Сохранённые настройки QA-профиля
читаются в память; ключи не выводятся в отчёт.

Для каждого вызова QA-процесс передаёт поддерживаемый локальным Ollama-прокси
заголовок `x-ollama-proxy-bypass-dedup: 1` и уникальный
`x-ollama-proxy-request-id`. Это отключает повтор сохранённого ответа без
изменения промпта, модели или настроек приложения. `transport` в журнале
фиксирует ID и запрос JSON-режима. Одного отправленного заголовка недостаточно
для доказательства свежего вывода: по этим ID отдельно проверяются безопасные
метаданные журнала прокси — `source_type=upstream`, `dedup_hit=false`, успешное
завершение и одна целевая модель. Тела чужих запросов и заголовки авторизации
для этой проверки не нужны.

`input.json` содержит исходники снимка и замороженный корпус; `run.log` — запросы,
ответы, границы завершённости потока и исход каждого сценария. `report.json`
фиксирует хеши исходников, image ID среды, провайдера, digest модели, контекст,
лимит вывода и хеши транспортных модулей. Смена исходников или модели делает
прогон непригодным для приёмки. Исключение даёт `ERROR`, пропущенный итог или
ошибка процесса — `INCOMPLETE`; они не считаются успешными проверками.

Сценарии выполняются по одному, без автоматического повторения неудачного
ответа. Исправления проверяются новым полным прогоном, а не смешением лучших
результатов нескольких запусков. Корпус и критерии нельзя ослаблять ради
прошедшего ответа.

Это ограниченная приёмка поведения на синтетических входах конкретной модели.
Она не доказывает качество произвольного ТЗ, права HTTP-пользователей, работу
браузера, сохранение в PostgreSQL или публикацию в Eva. Эти границы проверяются
отдельно.
