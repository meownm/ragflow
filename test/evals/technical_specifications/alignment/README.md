# Проект проверки соответствия ТЗ согласованным БТ

## Приёмочный результат

Автор выбирает доступные согласованные редакции БТ и сохранённое ТЗ. Проверка
возвращает отдельные решения о полноте реализации, отсутствии противоречий,
новых бизнес-правилах и совместной выполнимости ограничений. Все девять разделов
ТЗ, включая примеры API, настройки, таблицы и диаграммы, участвуют в проверке.
Верное упоминание не отменяет конфликтующее упоминание в другом разделе.
Техническая детализация допустима, если она не меняет бизнес-поведение.

`PASS` документа требует полного покрытия, отсутствия противоречий и
необоснованных бизнес-правил, актуальности обоих снимков и проверенных
доказательств исполнения. Одно `UNDETERMINED` блокирует подтверждение.
Пустые основания, пустой перечень результатов и ссылка «см. БТ» не дают PASS.
Средний балл не компенсирует провал обязательного сценария.

Входной перечень формируется до модельного вызова из всех исходных фрагментов,
включая заголовки. Он **не является доказательством выделения атомарных требований**:
проверяются все условия каждого фрагмента. Разбиение и объединение абзацев не
должны менять смысловой вердикт. Для составных требований нужны отдельные
семантические контрольные примеры, а не только совпадение ID строк.

Основание фиксирует document_id, revision_id, agreement_event_id, content_hash
и точные исходные диапазоны. Текущий несогласованный черновик не заменяет
согласованную редакцию. Перед сохранением и при чтении результата повторно
проверяются доступ, актуальность оснований и редакция ТЗ. Восстановление старого
текста является новой редакцией и не оживляет старый вердикт. Обсуждение без
изменения текста не инвалидирует проверку. Результат не меняет ТЗ автоматически.

## Независимые статусы

| Ось | Значения | Правило |
| --- | --- | --- |
| Исполнение | COMPLETE / INCOMPLETE | Доступность провайдера, срок, отмена, завершение |
| Отчёт | COMPLETE / INCOMPLETE | Схема, все ID, валидные цитаты и снимки |
| Качество документа | PASS / FAIL / UNKNOWN | Соответствие конкретного ТЗ основаниям |
| Модельный тест | PASS / FAIL / INCOMPLETE | Сравнение ответа с независимым эталоном |
| Доказательства | VERIFIED / INCOMPLETE | Сохранность входа, параметры, модель, usage |
| Квалификация | true / false | Только полный обязательный набор с VERIFIED |

Корректно обнаруженное противоречие: документ FAIL, модельный тест PASS.
Завершённый ответ с пропущенной строкой: ошибка контракта модели, модельный
тест FAIL. Ошибка сети или неизвестная причина завершения: INCOMPLETE, качество
UNKNOWN. Успешный тест управляемого повреждения не повышает качество модели.

## Матрица требований к лимитам

Это обязательный перечень приёмки, а не утверждение, что все строки уже закрыты.

| Группа | Обязательные проверки |
| --- | --- |
| LLM-BTZ-01—05, вход | Пустой ввод; полная сериализация system/БТ/ТЗ/схемы/обёрток; размеры на границе −1/0/+1; Unicode и кириллица; отличие оценочного и точного токенизатора |
| LLM-BTZ-06—10, контекст | Лимиты приложения, объявления модели и загруженного сервера проверяются отдельно; автоматическое усечение, выпадение начала/середины/конца и неизвестная сохранность входа запрещают квалификацию |
| LLM-BTZ-11—15, вывод | Резерв для полного отрицательного отчёта; ограниченный максимум схемы; reasoning и видимый ответ учитываются по контракту провайдера; length/неизвестное завершение; валидный JSON с недостающими строками |
| LLM-BTZ-16—20, контракт | Дубли JSON-ключей до нормализации; повторные/чужие/переставленные ID; ложные цитаты; неверный снимок; дополнительные бизнес-правила без поддельного ID основания |
| LLM-BTZ-21—25, общий бюджет | Число вызовов, суммарные токены и срок; ожидание очереди/конфигурации/генерации/финализации; монотонное время; retry/repair не сбрасывает бюджет; повтор после рестарта не повторяет оплаченный вызов автоматически |
| LLM-BTZ-26—30, ресурсы | Отмена и поздний ответ; фактическая остановка backend либо продолжающийся учёт; освобождение соединений и слотов; отказ при перегрузке; независимость документов и организаций |
| LLM-BTZ-31—35, доказательства | Фактические wire-параметры; стабильный digest и конфигурация; неизвестный usage не равен нулю; источник/образ/корпус/реализация; раздельные NATURAL_MODEL / CONTROLLED_FAULT / DETERMINISTIC |

Все fault-сценарии должны проверять причину отказа, отсутствие публикации PASS,
отсутствие скрытого повторного вызова и корректный остаток ресурсов. Один тест
«qualifies=false» недостаточен: он может пройти по посторонней причине.
Закрытие клиентского сокета само по себе не доказывает остановку инференса.

## Смысловые эталоны и реальные прогоны

`corpus.py` хранит независимые входы и ожидаемые решения. Эталонные метки не
передаются модели. Покрываются отрицание, только/все/любой, роли, регионы,
порядок действий, идемпотентность, деньги, каналы, обязательность, единицы,
границы, эквивалентный пересказ, технические детали, новые правила и конфликт
между текстом и машинным представлением.

Критерий покрытия: IMPLEMENTED — все условия; PARTIAL — хотя бы одна часть или
непустое подмножество допустимых случаев; MISSING — ни одной подтверждённой
части. Он независим от consistency. В ролевых случаях явно записаны разрешённая
и запрещённая группы, включая успешный и запрещённый ответы API в BTZ-25a.
В BTZ-28 общий лимит 100 МБ нарушает требование принимать любой допустимый
пакет: первая строка PARTIAL/CONTRADICTED и совместный результат CONTRADICTED;
ограничение размера отдельного файла само по себе соблюдено.

Для завершения полного проекта обязательны также пары с несколькими БТ,
совместными ограничениями, конфликтующими основаниями, исключениями, внешними
ссылками, инъекциями в исходниках, редакциями/отзывом согласования, длинными
контекстами и перестановкой разделов. Нужны независимый закрытый holdout и
повторные прогоны для оценки вариативности. Изменение спорного эталона требует
явной смысловой аргументации и новой версии корпуса; подгонка под ответ модели
запрещена.

Реальные проверки REAL-BTZ должны включать полный обычный набор, границы
контекста, большой отрицательный отчёт, reasoning/output limit, таймаут и
отмену, смену модели/параметров, повторяемость и подтверждение пути через proxy.
Локальный HTTP stub проверяет транспортный контракт и не заменяет инференс.
Найденная модельная ошибка сохраняется как результат проверки, а не скрывается
изменением эталона или исключением случая из знаменателя.

## Метрики и дашборд

Показываются отдельно: выполнено/ожидалось, полнота отчётов, модельный pass rate,
пропущенные противоречия, ложные блокировки, полнота реализации, необоснованные
правила, совместная выполнимость, доля UNKNOWN, квалификация и актуальность
доказательств. Для precision/recall/F1 показываются числитель и знаменатель;
пустой знаменатель означает N/A. Время, токены, ошибки лимитов и отмены —
операционные показатели. Неизвестный usage — N/A, а не 0.

`metrics.semantic_metrics` вычисляет показатели из текущего независимого
эталона и заново валидирует полные модельные отчёты. Знаменатель фрагментов
фиксируется по выбранным случаям до оценки ответов. Отсутствующий, чужой или
некорректный отчёт не создаёт смысловой прогноз и не уменьшает знаменатель:
показываются unscored и N/A. Завершённый ответ UNDETERMINED учитывается отдельно
и не обнаруживает эталонное противоречие. Поэтому при известном противоречии
он входит в FN; при сетевом сбое FN не начисляется.

| Показатель | Числитель / знаменатель |
| --- | --- |
| Точность полноты реализации | Верные coverage-метки / все эталонные фрагменты |
| Точность непротиворечивости | Верные consistency-метки / все эталонные фрагменты |
| Precision противоречий | TP / (TP + FP) |
| Recall противоречий | TP / все эталонные противоречия |
| F1 противоречий | 2 × TP / (2 × TP + FP + FN) |
| Ложные блокировки | Корректные по эталону ТЗ, ошибочно признанные FAIL / все корректные ТЗ |
| Необоснованные бизнес-правила | Найденные нарушения / явно размеченные случаи BTZ-23 |
| Совместные конфликты | Найденные конфликты / явно размеченные совместные конфликты BTZ-28 |
| Доля неопределённости | Фрагменты с UNDETERMINED / все эталонные фрагменты |
| Подтверждение условия цитатой | Цитаты нужного условия / явно размеченные условия BTZ-53/54/55 |

Доля появляется только после получения всех отчётов, необходимых для этой
метрики; нулевой знаменатель остаётся N/A. Цитатный показатель не заявляет
семантическую проверку всех цитат корпуса: для остальных случаев отдельно
проверяются точное вхождение цитаты, раздел и снимок. Precision новых правил
не выдумывается для случаев без закрытой разметки отсутствия таких правил.
В UI видны TP/FP/FN/TN, оценённые и неоценённые фрагменты, значения и дроби.
История использует метрики выбранного запуска. Сохранность входа и
квалификация исполнения показаны отдельно от качества наблюдённых ответов.
Публичная проекция пересчитывает дроби из ограниченных числовых фактов и
полноты соответствующей подвыборки. Согласованная арифметика сама по себе
недостаточна: уменьшенный знаменатель или числовая доля при неполноте
отклоняются. Старые сводки без необходимых фактов остаются без оценки.

Рейтинг ТЗ появляется только для полностью завершённой кампании без ошибки
каталога, с успешным baseline и полными квалифицированными запусками всех
моделей. Обязательны одинаковые снимки исходников, корпуса, промпта и
параметров. Для изменённых исходников нужен SHA-256 снимка, для чистых —
полная Git-ревизия. При неполных или несопоставимых доказательствах результаты
остаются видимыми, но места в рейтинге не назначаются.

Серии БТ и ТЗ разделены ключом document_type во всех API, запросах UI,
идемпотентности, расписании и хранении доказательств. Метрики рабочих заданий
БТ не выдаются за эксплуатационные метрики ТЗ. История и сравнение моделей
учитывают границы исходников, корпуса, промпта, параметров и модели. Сырые БТ,
ТЗ, ответы и исключения не попадают в общую административную проекцию.

## Ночь, ресурсы и выпуск

Ночной слот — после 02:00 Europe/Moscow, месячный — после 03:00 первого числа
с догоняющим запуском. Слот дедуплицируется отдельно для каждого продукта.
Используется существующая выделенная QA-организация. Проверки не меняют её
настройки и не используют пользовательские документы. Очередь сохраняется;
зависший baseline одного продукта не блокирует готовые задания другого.
Поздний worker не перезаписывает результат другого состояния/поколения.

Независимый read-only endpoint `/api/v1/admin/document-quality/health`
обнаруживает отсутствие ночного слота, неполную кампанию и превышение срока.
Он не вызывает scheduler и не создаёт отсутствующий слот при чтении. Сам
endpoint ещё не доказывает, что внешний монитор настроен и присылает сигнал.

Независимый внешний runner:

```powershell
python tools/quality/check_document_quality_night.py --base-url <origin-сервиса>
```

Значение заголовка Authorization читается из `DOCUMENT_QUALITY_ADMIN_TOKEN`
(либо переменной, указанной через `--token-env`); токен не передаётся аргументом
и не включается в результат. Runner выполняет только GET health для БТ и ТЗ,
не вызывает scheduler, не следует redirect, ограничивает размер ответа и
время чтения. Свежесть observed_at, точное совпадение ожидаемого ночного слота
(с 02:15 по Москве), продукт, envelope и согласованность статуса проверяются
отдельно. PENDING/RUNNING после 12 часов от начала слота даёт ALERT даже при
ошибочном OK сервера. Общая чистая политика расписания находится в
`common/document_quality_schedule.py`; внешний процесс запускается из копии
репозитория с этим модулем и не загружает сервер или базу. Exit 0 означает исправный контроль, 1 — ALERT, 2 —
недоступные/устаревшие доказательства, 3 — отсутствующую конфигурацию. Внешняя
система мониторинга может выполнять команду каждые пять минут и обрабатывать
ненулевой exit. Реальная установка расписания, admin credential и доставка
уведомления ещё не подтверждены; тестовый HTTP server их не заменяет.

Доказательства хранятся вне исходников; последняя завершённая запись каждого
продукта защищена от вытеснения другим продуктом. Релизный gate пересчитывает
результаты по текущему корпусу и требует совпадение исходников и точного образа.
FULL и все обязательные случаи нужны одновременно. Частичный набор,
DIAGNOSTIC, усечение, неполный отчёт или неподтверждённый вход не дают PASS.

## Воспроизведение и текущая граница доказательств

```powershell
.venv/Scripts/python.exe -B -m pytest -q test/unit_test/technical_specifications
.venv/Scripts/python.exe -B -m pytest -q test/unit_test/admin/test_technical_specification_quality.py test/unit_test/admin/test_document_quality_runs.py test/unit_test/admin/test_document_quality_routes.py test/unit_test/admin/test_document_quality_evidence.py
.venv/Scripts/python.exe -B -m pytest -q test/unit_test/tools/quality/test_release_evidence.py
.venv/Scripts/python.exe -B test/evals/technical_specifications/alignment/run_live.py --evidence-dir <новый-каталог-вне-репозитория>
```

Текущий native Ollama adapter сохраняет фактические параметры, digest, finish
reason и usage, но **не подтверждает точное отсутствие усечения входа**.
Поэтому его естественный ответ может пройти смысловой эталон, однако
квалификация остаётся INCOMPLETE. Не заменять это ограничение утверждением
VERIFIED по факту отправки JSON или успешного ответа на контрольный вопрос.
В нативном запросе явно заданы `truncate=false` и `shift=false`: адаптер
не разрешает усечение истории или сдвиг контекста при генерации. Поля входят
в хеш полного wire и не переопределяются модельным планом. Их наличие не
доказывает исполнение сервером; переполнение и игнорирование опций остаются
отдельными проверками. Контракт подтверждён по
[API Ollama v0.32.14](https://github.com/ollama/ollama/blob/v0.32.14/api/types.go).
Релизная проверка отклоняет wire с разрешённым усечением или сдвигом, даже
если прочие флаги отчёта утверждают PASS. Старый запуск без этих полей не
подтверждает текущий протокол.
Запуск внедрённых модулей в существующем контейнере доказывает исполнение
зафиксированных модулей, но не соответствие полного candidate image.

Наличие проекта и passing unit tests не означает закрытие полной матрицы:
реальные границы контекста, backend cancellation, точный tokenizer/loaded ctx,
полный расширенный корпус/holdout, эксплуатационная телеметрия ТЗ и внешний
монитор требуют отдельного подтверждения перед полной приёмкой.

## Договор исполнения проверок

Ночь и релиз используют один `evidence.verify_execution`: он заново проверяет
полный перечень, результаты каждого случая, реальные лимитные пробы, параметры,
входные хеши и общий бюджет. Флаги `PASS`, `qualifies` и `VERIFIED` сами по себе
недостаточны. Ночной PASS дополнительно требует код завершения процесса 0.
Диагностический запуск одного случая не квалифицирует полный набор.

Каждая платная REAL-проба сверяется с принадлежащими ей payload и wire-планом:
уникальный request ID среди обычных и лимитных вызовов, те же модель и digest,
неизменные веса до/после, фактические параметры и допустимый usage. Выходная
проба требует length при ровно восьми токенах; игнорирование num_predict
не засчитывается. Отмена требует связанного backend-подтверждения и расхода;
клиентское закрытие не заменяет эти доказательства. Общий профиль задаётся
независимо от отчёта: 4 000 000 токенов, число случаев + 3 вызова и
(число случаев × 300 + 180) секунд. Увеличить эти лимиты полями отчёта нельзя.

После таймаута с неизвестным завершением backend следующие реальные вызовы
прекращаются. Неисполненные случаи остаются INCOMPLETE; неизвестный расход
сохраняет резервацию. Проверка исчерпания на копии бюджета не создаёт фиктивный
вызов в фактическом ledger. Идентификатор запроса и резервация бюджета
сохраняются контрольной точкой до обращения к
провайдеру, чтобы отсутствие ответа не теряло связь с proxy-транзакцией.
Итоговое время включает лимитные пробы; неизвестные суммарные токены не
подменяются известным расходом только смысловой части серии.
До вызова резервируется полное запрошенное окно контекста: оценочный tokenizer
не ограничивает фактический расход модели. Если общий бюджет не вмещает это
окно, inference не начинается. После известного native usage списывается
полученный расход; отсутствие usage сохраняет резерв всего окна.

Типизированный HTTP 400 `exceed_context_size_error` с целочисленными
`n_prompt_tokens > n_ctx`, совпадающим запрошенным окном и кодом 400 распознаётся
как `MODEL_CONTEXT_REJECTED`. Число предложенных входных токенов не считается
потраченными токенами. Обычный HTTP 400, текстовое упоминание контекста,
некорректные счётчики, чужое окно и повреждённый JSON не подтверждают защиту.
REAL-BTZ-03 сохраняет наблюдаемый отказ отдельно; без usage его статус остаётся
INCOMPLETE, резерв сохраняется, последующие реальные вызовы прекращаются.
Ни отказ, ни его диагностические счётчики не заменяют точный tokenizer,
retention evidence или подтверждение остановки backend.

Попытка, оставшаяся PROCESSING после падения процесса, через 360 секунд
становится INCOMPLETE при чтении истории с проверкой версии. Восстановление
не меняет содержание ТЗ и не повторяет оплаченный вызов. Поздний исполнитель
не публикует результат поверх истёкшей попытки. Панель не подтверждает старую
редакцию или ТЗ с несохранёнными правками; восстановленная служебная версия
принимается редактором только при совпадении содержательной редакции.

## Отдельная приёмка длинных входов и reasoning

В полном корпусе 56 случаев. BTZ-53/54/55 содержат три смысловых требования и
длинное техническое описание; нарушенное требование находится соответственно
в начале, середине и конце. Требуется точное решение по всем трём строкам.
Эти натуральные случаи запускаются общим evaluator и входят в фиксированный
знаменатель. Их наличие ещё не означает успешный реальный прогон.

Дополнительно обязательны следующие доказательства; они остаются незакрытыми
до реального выполнения, даже если короткие пары и fault-пробы прошли:

| Проверка | Вход и наблюдаемый результат | Условие неполноты |
| --- | --- | --- |
| NATURAL-BOUNDARY | Смысловая пара с фиксированными требованиями, полный wire-запрос на границе admission −1/0/+1, достаточный резерв отрицательного отчёта; допустимые входы реально оцениваются, +1 отклоняется до inference | Только оценочный tokenizer либо нет backend retention evidence |
| REAL-REASONING | Thinking включён явным поддерживаемым параметром; малый и достаточный общий reasoning/output budget; зафиксированы скрытый и видимый расход по контракту сервера | Неизвестно, включает ли usage reasoning; обрезанный reasoning/ответ; неподтверждённый параметр |
| HOLDOUT | Отдельный независимый набор после фиксации промпта и корпуса; эталоны не используются для настройки; фиксируются владелец, версия, хеш и полный знаменатель | Набор создан или просмотрен тем же циклом настройки; отсутствует независимая разметка |
| REPEATS | Несколько полных запусков неизменных входов и параметров; показываются разброс и частота критических ошибок по случаям | Подмена повторов усреднением только удачных ответов |

Отчёт должен явно разделять наличие исполняемого сценария, его фактическое
выполнение, смысловой результат и квалификацию backend. Известная недоступность
доказательств требует INCOMPLETE, а не исключения проверки из знаменателя.

Исполняемые дополнительные эксперименты:

```powershell
.venv/Scripts/python.exe -B test/evals/technical_specifications/alignment/run_live.py --experiment REPEATS --evidence-dir <новый-каталог-вне-репозитория>
.venv/Scripts/python.exe -B test/evals/technical_specifications/alignment/run_live.py --experiment ADMISSION --evidence-dir <новый-каталог-вне-репозитория>
.venv/Scripts/python.exe -B test/evals/technical_specifications/alignment/run_live.py --experiment REASONING --evidence-dir <новый-каталог-вне-репозитория>
```

REPEATS запускает два полных прохода корпуса, всего 112 ожидаемых попыток с
одним ledger. По каждому случаю сохраняются числитель ошибок, знаменатель 2,
неисполненные и неизвестные попытки, варианты меток и полного ответа. Смена
модели/параметров или повтор request ID делает сравнение неполным; неизвестный
расход сохраняет резерв и останавливает следующий проход. Неудачные ответы
не отбрасываются. Два прохода дают наблюдаемую вариативность, но не устойчивую
статистическую оценку редких ошибок.

ADMISSION сохраняет полный смысловой вход и находит минимальное допускаемое
окно контекста приложения. Окно −1 отклоняется без inference; точное окно и
окно +1 реально проверяются тем же AlignmentAI. Это проверка **оценочной
границы приложения**, а не точных backend-токенов NATURAL-BOUNDARY. Отсутствие
точного tokenizer и retention attestation остаётся незакрытым требованием.

REASONING читает `/api/show`, фиксирует поддерживаемый thinking control либо
ограничение CAPABILITY_ONLY и отправляет его явно. Запускаются общий выходной
лимит 8 и 8192, проверяются actual wire, digest до/после, usage, thinking field,
полный отчёт и смысловые метки. Количество символов thinking не выдаётся за
токены; отдельный или суммарный reasoning-расход без подтверждённого контракта
остаётся NOT_ATTESTED. Сырые рассуждения не добавляются в публичный audit.

Эксперименты имеют scope EXPERIMENT и не квалифицируют FULL ни при каких
наблюдённых метках. NIGHTLY/MONTHLY задания ТЗ вызывают evaluator с `--nightly`:
последовательно собираются REPEATS, ADMISSION, REASONING и затем FULL. Каждый
эксперимент имеет отдельный фиксированный ledger; неизвестный расход,
незавершённая серия, смена модели или повтор request ID останавливают следующие
серии. Долг остаётся в исходном отчёте и не сбрасывается новым ledger. FULL с
контролируемой отменой идёт последним. Срок scheduled-задания и stale detection
учитывают весь сбор. Это реализованное поведение очереди; установка обновлённого
кода и успешная реальная ночная серия ещё не подтверждены.

В дашборде и выбранной исторической записи показываются ожидаемые/исполненные
случаи, качество и полнота доказательств каждого эксперимента. Неизвестный
расход — N/A. Даже если все наблюдённые ответы верны, текущая ночная квалификация
остаётся INCOMPLETE: ADMISSION не подтверждает точные backend-токены,
REASONING не подтверждает раздельный reasoning-расход. Известная модельная
ошибка даёт FAIL; отсутствие аттестации не превращается в PASS.

Host сохраняет точные host/child scripts, хеш снимка модулей и ledger после
каждого изменения, включая списание после последнего ответа без final report.

## Независимый holdout

Набор `bt-tz-independent-holdout-v1` содержит 16 синтетических пар и 17
атомарных абзацев БТ. Его создал отдельный QA-разметчик без доступа к текущему
промпту, корпусу и модельным ответам; метки зафиксированы до инференса.
Владелец разметки — `independent-qa-curator`, метод —
`SYNTHETIC_INDEPENDENT_AGENT`. Экспертная проверка человеком не проведена.

Набор хранится вне репозитория: `inputs.json`, `oracle.json`, `manifest.json`
и отдельный `approval.json`. Manifest фиксирует ID, размеры и SHA-256 входов
и разметки. До инференса обязателен PASS независимого аудита разметки,
привязанный к точному хешу manifest; отсутствующий, отвергнутый или устаревший
аудит останавливает запуск. Содержимое спорного случая не исправляется по
ответу модели: до первого инференса выпускается новый зафиксированный пакет.
`holdout.load_bundle` проверяет входы и запрещает поля с разметкой во входном
объекте, не читая oracle. В контейнер отправляются только входы. Oracle читает
host после завершения всех модельных вызовов, заново проверяя хеши, снимки,
строки, цитаты, совместность и новые правила. Изменение файлов, неполный набор,
неизвестный расход или смена идентичности не дают квалификацию.

```powershell
.venv/Scripts/python.exe -B test/evals/technical_specifications/alignment/run_live.py --holdout-dir <зафиксированный-набор> --evidence-dir <новый-каталог-вне-репозитория>
```

Это отдельная серия HOLDOUT, не замена FULL и не доказательство качества на
реальных бизнес-документах. Все ошибки остаются в отчёте. Если результаты
использованы для настройки промпта, набор становится регрессионным и перестаёт
считаться закрытым; для следующей независимой оценки нужен новый набор.

## PostgreSQL: продуктовые данные и гонки завершения

Миграция `document_type` выполняется транзакционно для обеих таблиц качества.
Она восстанавливает nullable-колонку после прерывания: заполняет только NULL
значением БТ, сохраняет уже записанные ТЗ, восстанавливает NOT NULL и индекс.
Повторное выполнение сохраняет данные и историю. SQL DEFAULT не добавляется:
текущие подтверждённые writers используют ORM default; совместимость старого
бинарного writer без поля этим тестом не обещается.

Stale reclassifier использует CAS по status и started_at; для baseline также
по отсутствию результата. Завершившийся PASS и новая попытка RUNNING не
перезаписываются старым снимком. Дочерние задания меняются только после
успешного CAS baseline. `test/integration/test_document_quality_postgres.py`
проверяет эти границы на runtime pooled driver, отдельных соединениях и
временных схемах; общий `migrate_db` на рабочей базе не вызывается.

## Эксплуатационные показатели

Обычные проверки соответствия сохраняют отдельную анонимную строку попытки
атомарно с состоянием ТЗ. До inference записывается резерв бюджета; завершение,
отмена и восстановление после утраты исполнителя обновляют ту же строку.
Повтор запроса не создаёт вторую попытку, поздний ответ не заменяет завершённое
состояние. Ошибка записи наблюдения откатывает изменение ТЗ. Тексты, цитаты,
названия документов, ключи и идентификаторы участников в таблицу не попадают.

Административный `/document-quality?document_type=technical_specification&days=7`
возвращает точную когорту зарегистрированных попыток, принятых за 1/7/30 дней.
Дашборд показывает исполненные проверки и полные отчёты со знаменателем всех
терминальных попыток; активные и просроченные активные попытки учитываются
отдельно. Среднее и nearest-rank p95 вычисляются SQL по всем измеренным строкам,
в одном снимке транзакции. Восстановленная после сбоя попытка не выдаёт время
предварительного резерва за конечную длительность.

Известная часть usage и резерв показаны отдельно. Неизвестный reasoning-расход,
отмена без подтверждённого завершения backend или отсутствующие измерения
оставляют полный расход N/A. История до установки учёта не восстанавливается
из текстов документов; это показатели зарегистрированной когорты, а не оценка
смыслового качества и не заявление о полноте всей исторической статистики.

HTTP 429/503 от провайдера, включая запрос метаданных модели, возвращает
`MODEL_PROVIDER_OVERLOADED`, INCOMPLETE и UNKNOWN без скрытого повторного
вызова. В audit сохраняется только числовой HTTP-статус, без тела ошибки.
Неизвестный расход удерживает резерв. Повтор того же пользовательского запроса
читает сохранённую попытку, а HTTP-сессия закрывается после отказа.
`test_alignment_transport.py` проверяет этот путь через настоящий loopback HTTP,
хранилище и повтор запроса; 401/500 остаются транспортными ошибками. Это проверка
протокола отказа и ресурсов клиента, а не измерение предельной нагрузки GPU
или доказательство освобождения внутренних слотов backend.

`test_alignment_telemetry.py` проверяет атомарность, replay и отмену;
`test_technical_specification_operations.py` — полный SQL-знаменатель и p95
на 5001 строке. PostgreSQL lane проверяет откат при серверной ошибке, сохранение
долга после expiry и согласованность агрегатов при конкурентном завершении.
