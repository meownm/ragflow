# Нагрузка «Бизнес-документы»: 50 пользователей, эмуляция LLM

Локальное тестовое расширение. Рабочие API, модели, настройки и worker не меняются.
По умолчанию 50 **разных авторизованных пользователей**, один документ на человека,
плавный старт за 5 секунд. `--rounds 3` повторяет сценарий трижды с паузой
`--think-seconds 2` между документами одного пользователя.

Сценарий: создать документ → `REQUEST_INTAKE_ASSESSMENT` → дождаться `COMPLETED`
у конкретного задания → прочитать вопрос эмулятора из протокола → удалить документ.
Используется поддерживаемый create-контракт v1: уникальные заголовки позволяют
50 людям одновременно работать без конфликта уникальности названия L5-каталога.
Данные синтетические, `dataset_ids=[]`, EVA и поиск по базе знаний не задействованы.
Это нагрузка API, БД и очереди анализа вводных. Генерация полного документа,
изменения, экспорт, браузер, качество модели и ACL-матрица в этот сценарий не входят.

## Ориентир одной H200

Модель: **Qwen3.8-27B**, предполагается FP8, без thinking и MTP, прогретый сервер.
Профиль является **оценкой**, а не замером данной машины:

| Параметр | По умолчанию |
| --- | ---: |
| Общий prefill | 5 000 токенов/с |
| Decode одного запроса | до 85 токенов/с |
| Общий decode | до 600 токенов/с |
| Одновременно обслуживаемые генерации | 8 |
| Минимальный моделируемый выход | 512 токенов |

Ориентир: [первичные измерения IndieRouter от 11.10.2026](https://indierouter.ai/blog/h200-part-02-qwen38-27b-first-model/)
для Qwen3.8-27B FP8, vLLM 0.31.0, FP8 KV: однокарточная реплика — 11.5 мс
на выходной токен для короткого одиночного запроса и около 5.3K входных токенов/с
для длинного запроса. Здесь эти величины округлены вниз до 85 и 5 000.
**600 суммарных токенов/с и 8 слотов — наши консервативные допущения**,
не опубликованный результат этого измерения. У Qwen3.8 thinking включён по
умолчанию ([карточка модели](https://huggingface.co/Qwen/Qwen3.8-27B)); этот профиль
его не моделирует. Для BF16, GGUF/Ollama, других длин и reasoning параметры
нужно откалибровать по фактическим TTFT/TPOT/throughput целевого сервера.

Вход оценивается по полному массиву сообщений как `ceil(символы / 3)`;
это приближение, не токенизатор Qwen. Выход — максимум из такой оценки
синтетического ответа и `--output-tokens`. Число выхода входит в задержку и usage,
но фактический JSON намеренно остаётся коротким фиксированным вопросом.
Очередь общая: максимум 8 активных запросов, prefill последовательно делит
один бюджет; скорость decode уменьшается с числом активных генераций.
Prefill и decode могут перекрываться; это приближённая модель обслуживания,
не симулятор GPU, KV-cache или continuous batching. Остальные запросы ждут слот.
Для 12K входных и 512 выходных токенов одиночный вызов занимает примерно
`12000/5000 + 512/85 = 8.4 секунды`, ожидание очереди добавляется отдельно.

Число пользователей не равно числу LLM-вызовов. В одном процессе API работает
ограниченный пул Business Documents worker. `BUSINESS_DOCUMENT_WORKER_CONCURRENCY`
задаёт размер от 1 до 8, по умолчанию 4; предел действует на каждый API-процесс.
Каждому потоку принадлежат свои AI/evidence/SQL-адаптеры и уникальный lease owner.
DB leases, heartbeat, retry и проверки версии/авторизации остаются общими для
API и worker. Один поток держит общий lock восстановления зависших заданий
и очистки экспортов. После `CancelledError` операция освобождает heartbeat,
поток остаётся в пуле и отдаёт lock другому участнику; просроченный lease
восстанавливается прежним механизмом retry. При выходе потока lock также
освобождается. Повторный старт заменяет умершие потоки, сохраняя живые
и установленный размер пула. Соединение БД освобождается после каждого poll/job,
в том числе после ошибки. При остановке
процесса потоки перестают брать новые задания через общий stop event;
запущенное задание завершается на прежних безопасных границах. Idle wait
ограничен `BUSINESS_DOCUMENT_WORKER_POLL_SECONDS` (по умолчанию 2 секунды).
С одним worker 50 заданий могут исполняться несколько минут; заданию даётся
1800 секунд. Настоящая пропускная способность модели проверяется отдельно.

## Подготовка изолированного API-контура

Контур и 50 пользователей можно создать автоматически (нужны Docker Compose,
доступный совместимый образ приложения и локальные образы зависимостей):

```powershell
.venv/Scripts/python.exe -B test/load/run_disposable.py `
  --app-image 'совместимый-локальный-образ-ragflow' `
  --evidence-dir S:/ragflow-load-new-run --users 50 `
  --worker-concurrency 4 --compare-single-worker
```

Каталог evidence должен быть новым и находиться вне репозитория. Скрипт создаёт
проверяемую копию текущих исходников, монтирует её только для чтения, запускает
отдельные контейнеры и тома, регистрирует пользователей через HTTP, подключает
эмулятор к управляемому каталогу моделей и собирает Docker/SQL-метрики. Токены
и пароли остаются в памяти, логи очищаются от сгенерированных секретов.
По завершении удаляются только ресурсы данного Compose-проекта; исходники и
evidence сохраняются. Порты 19581 и 19582 должны быть свободны.
Всегда запускается один API-процесс. `--worker-concurrency 4` задаёт четыре
worker-потока в нём, без дублирования API. `--compare-single-worker` сначала
запускает сценарий с одним worker, затем после завершения и очистки документов
пересоздаёт только тестовый API-контейнер с выбранным размером пула. Исходники,
образ, сервисы данных, 50 учётных записей и профиль LLM остаются одинаковыми.
После readiness пользователи входят заново. Результаты сохраняются отдельно:
`load-workers-1.json`, `load-workers-4.json`, `llm-stats-workers-*.json`.
Строки `metrics.jsonl` содержат фазу `load-1`, `load-4` или `restart`, поэтому
метрики старта API не нужно смешивать с нагрузкой. Без флага сравнения
выполняется только один прогон выбранного пула. Это не deployment рабочего
контура; все операции ограничены случайным тестовым Compose-проектом.
Логи API каждой фазы сохраняются до пересоздания контейнера в
`app-workers-1.log` и `app-workers-4.log`. Поле `runtime_lifecycle_errors`
должно быть равно нулю: ошибки закрытого/чужого event loop и неисполненных
корутин делают прогон неуспешным даже при завершении всех HTTP-сценариев.

Использовать отдельный тестовый экземпляр RAGFlow с собственными БД/очередью.
Не направлять тест в общий пользовательский контур. Сам генератор
`business_documents.py run` не разворачивает и не перенастраивает существующую
инсталляцию.

1. В отдельном терминале запустить эмулятор из корня репозитория:

   ```powershell
   .venv/Scripts/python.exe -B test/load/business_documents.py mock-llm --host 0.0.0.0
   ```

   Для контейнера RAGFlow на Docker Desktop адрес провайдера:
   `http://host.docker.internal:18081/v1`. Для приложения на хосте:
   `http://127.0.0.1:18081/v1`. `--host 0.0.0.0` нужен для доступа из контейнера;
   эмулятор предназначен для тестовой сети, аутентификацию он не реализует.
   `/v1/models` поддерживается, `/stats` возвращает профиль, идентификаторы
   документов и хеши запросов без их текстов и токенов авторизации.

2. Для **каждой из 50 тестовых учётных записей** с правом создания документов
   настроить default Chat через существующие настройки провайдера
   `OpenAI-API-Compatible`: модель `bd-loadtest-qwen3.8-27b`, указанный base URL,
   произвольный тестовый API key, окно контекста 65536. Это имя обозначает
   эмулятор; реальные веса модель не загружает. Сначала закончить проверку
   подключения модели, затем запускать нагрузку. Другие потребители в данном
   контуре тоже должны использовать только синтетические данные.

3. Сохранить вне репозитория JSON-массив из 50 разных значений заголовка
   `Authorization` **web-сессий** после обычного входа. Значения передаются
   ровно как получены от login API; это не SDK API keys и не пароли.
   Тест вызывает `/users/me` и проверяет 50 разных ID до создания документов,
   а также имя default-модели. Пример структуры файла: `["session1", "session2"]`.

4. Сохранить токен отдельного администратора тестового контура в
   `$env:BD_LOAD_CLEANUP_TOKEN`. Автору документа может быть запрещено удаление;
   именно поэтому очистка использует отдельную сессию администратора.

## Запуск

```powershell
.venv/Scripts/python.exe -B test/load/business_documents.py run `
  --base-url http://127.0.0.1:19382 `
  --users-file C:/temp/bd-load-users.json `
  --users 50 --rounds 1 `
  --report C:/temp/bd-load-50.json
```

Отчёт: p50/p95/p99 полного сценария (до очистки), HTTP по операциям,
ошибки, завершённые сценарии/с, попытки worker, LLM-вызовы для созданных
документов с ожиданием/TTFT/полным временем, результаты очистки, профиль,
HEAD/dirty и SHA-256 генератора/фикстуры. HEAD относится к генератору;
для выводов о RAGFlow отдельно сохранить source/image ID тестового сервера.
Время прогона включает ramp-up, think time и очистку. Это закрытая модель
нагрузки: каждый пользователь ждёт свой результат, прежде чем создать следующий.

Код выхода 0 — все сценарии без ошибок, для всех документов есть завершённые
вызовы эмулятора, очистка успешна. `--max-p95-seconds` задаёт критерий задержки.
Порог latency по умолчанию не придуман:
PASS означает функционально успешный прогон, а не выполненный SLO.
Несовпадение LLM-evidence или ошибка очистки всегда проваливают прогон.
`--fail-every 10` у эмулятора добавляет HTTP 503 на каждый десятый вызов
для отдельного сценария проверки retry; ошибки нельзя считать успешным
baseline. `--slots 1` позволяет моделировать последовательный inference.

Для калибровки эмулятора доступны `--prefill-tps`, `--decode-tps`,
`--aggregate-decode-tps`, `--output-tokens`, `--slots`.
Не увеличивать SLO/таймауты для сокрытия результата. При timeout/сбое сетью
сервер может уже создать документ, не вернув его ID; проверить документы
с префиксом `load-<run_id>-` в отдельном контуре. Документы с известными ID,
которые не удалились, перечислены в отчёте. После принудительного завершения
генератора также проверить остатки в этом контуре.

## Проверка самого теста

```powershell
.venv/Scripts/python.exe -B -m pytest -q test/load/test_business_documents.py
ruff check test/load
```

Локальные проверки используют HTTP fake API и настоящий HTTP-эмулятор;
они проверяют генератор на 50 клиентах, ответы, ошибки и очистку.
**Они не являются результатом нагрузки RAGFlow или бенчмарком H200.**
Ни unit-тесты, ни эмулятор не подключаются к рабочим данным или реальной LLM.

Жизненный цикл SDK отдельно проверяется командой:
`python -B -m pytest -q test/unit_test/rag/llm/test_async_client_lifecycle.py`.
Эти проверки используют локальный HTTP/1.1-провайдер и настоящий TCP-транспорт:
сохраняют исходные 503/cancellation при сбое cleanup и проверяют завершение
закрытия до выхода worker loop после повторной отмены, включая сбой cleanup.
Одного флага SDK `is_closed()` для этой гарантии недостаточно.
